# Breeze P2P 強化計画（P2P_PLAN）

目的: Breeze を「P2P メッセンジャーとしても続ける」（2026-11-14、mi の指示）。中継サーバーへの依存と費用を減らし、端末同士で直接届く割合を上げる方向を、段階3（量子耐性 PQXDH、`docs/PQ_STAGE3_PLAN.md`）と並ぶ軸として育てる。本書の実態記述は全て現行 main（`8361bbf`、段階3 Step 2 取り込み済み）の実コードで裏を取ったものだけを書く。行番号は漂うため、根拠は関数名・CONFIG キー・ファイル名で示す。

前提の資産: 段階1（メールボックス DO 化・WS 起床）・段階2（置き場所を選べるリレー、複数ホームリレーへの冗長預けとシグナリング fan-out）は完了。段階3は実装中（Step 1・2 完了）。シェア獲得計画（`docs/SHARE_PLAN.md`）の段階4〜7とは対象が重なる箇所があり、第3節で所有権を切り分ける。

## 1. 現在の P2P の実態（実測）

### 1.1 全体像

直接配送は既にある。ただし現行の配送モデルは「直接か中継か」ではなく **常時二重配送** である: 1:1 でもグループでも、メッセージは DataChannel で直接送られ、**同時に** Sealed Sender でメールボックスへも預けられる。受信側は msgId の重複排除（`_replayCache` ＋ IndexedDB の既読確認、ラチェット側の `seenMsgIds`）で二重を落とす。直接でも中継でも運ばれる暗号文は同一（Double Ratchet の封筒）で、P2P は経路の違いに過ぎない。

| 対象 | 直接（P2P） | 中継（リレー） | 根拠 |
|---|---|---|---|
| 1:1 メッセージ | DataChannel `breeze-msg`（ordered、negotiated id 0）で封筒を直送 | **常時併用**: Sealed Sender でメールボックスへ預け（不在・取りこぼしの保険） | `sendMessage` の "P2P direct (preferred)" 節と続く無条件の `relaySend` |
| グループ メッセージ | 接続中の各メンバーへ同じ Sender Key 暗号文を直送 | **常時併用**: 全メンバーへ Sealed Sender 預け | `sendMessage` の "Dual-path delivery" 節 |
| ファイル | バイナリ分割（`CONFIG.CHUNK_SIZE` 16KB）で直送。**192KB 超は P2P でしか送れない**（中継は 256KB 上限のためクライアントが拒否） | 192KB 以下は封筒に載せて預け可能 | `_sendFile`、`sendBinaryFile`、i18n `toastFileNeedP2P` |
| 通話（1:1 音声・ビデオ） | 別 `RTCPeerConnection` でメディア直通（DTLS-SRTP） | シグナリングのみ中継。メディアの中継は TURN 経由時のみ | `startCall`、`getCallICEConfig` |
| グループ通話 | **無い**（検索ヒット 0 件） | — | `docs/SHARE_PLAN.md` §1 と同じ実測 |
| 入力中・既読・在席 | 状態チャネル `breeze-state`（unordered、`maxPacketLifeTime` 200ms、id 1） | 接続前はシグナリングルーム経由でも運ばれる | `connectPeer` の `setupDC`、sigPoll の typing/read 処理 |
| 第三者ピア経由の預かり | 接続中の別ピアが暗号文を預かり（メモリ内、上限20件/宛先、TTL 1時間）、宛先がオンラインになったら渡す | 本来のメールボックスとは別の機会的経路 | `handlePeerRelayRequest`、`deliverPeerRelayQueue` |

### 1.2 接続確立の流れ

- 開始条件は3つ: (a) 会話を開いたとき（`openConversation` 相当の箇所で未接続なら `connectPeer`）、(b) 在席ポーリング（`CONFIG.PRESENCE_INTERVAL_MS` = 30秒）が相手のオンラインを検知したときの自動再接続、(c) ネットワーク復帰イベント（`window._reconnectAllPeers`）。
- 発起人は決定的に1人だけ: `myPubB64 > contact.pubB64`（公開鍵の辞書順）で決まる。競合時は Perfect Negotiation（impolite 側が自分の offer を守り、polite 側が譲る）。
- チャネルは2本とも `negotiated: true` で事前合意され、DCEP ハンドシェイクを省く。
- 状態機械は INIT → SIGNALING → ICE → CONNECTED（→ RECONNECTING → CLOSED）を `peerState.transition` で管理し、CLOSED で全タイマーを一括解除する。
- 接続タイムアウトは30秒。切断時は `restartIce()`、失敗時は指数バックオフ（`RECONNECT_BASE_MS` 1秒〜 `RECONNECT_MAX_MS` 60秒、最大 `RECONNECT_MAX_ATTEMPTS` 8回）で作り直す。
- 健全性監視: 状態チャネルで10秒間隔 ping/pong（3回連続無応答で ICE 再起動）、15秒間隔（`HEALTH_CHECK_MS`）で `getStats()` を読み、RTT 5秒超で ICE 再起動。会話画面には経路種別（Direct／STUN／TURN／TURN relay-only）と RTT が表示される。

### 1.3 シグナリング

- 置き場所は **リレーの KV**（`_worker.js` の `handleSignal`、`sig:{room}` キー、保持は最大50件・TTL 5分、poll は読み取り＝消費）。WebSocket は使わない。メールボックス用の WS（段階1）は「新着の合図」専用で、シグナリングは運ばない。
- ルームは `dm:{2人のIDのソート済みペア}`（通話は `call:{...}`）。段階2 Step 6 で、送信は自分の主リレー＋**相手のホームリレー群**へ fan-out され、poll も相手のホームリレー群をマージして読む（重複は sender|type|data で排除）。
- クライアントは `connectPeer` ごとに **2秒間隔のポーリング**（`sigPoll`）を回し、接続が閉じるまで止まらない。接続後も typing/read の受け口として走り続ける。
- SDP は Ed25519 署名つきで送られ（`_sendSignedSDP`）、受信側は署名検証と署名鍵の TOFU ピン留めをしてから `setRemoteDescription` する。未署名（旧形式）は互換のため受理される。
- dm:/call: ルームは Worker 側でも認証される: ルーム名に埋まった2 ID のどちらかでなければ 403、登録済み ID には `breeze-sig:{room}:{sender}:{ts}` 署名を要求。
- 通話シグナリングの暗号化（`_wrapCallSignal`）は実装済みだが `CONFIG.CALL_E2E_SIGNAL: false` で**既定 OFF**（この既定の変更は `docs/SHARE_PLAN.md` 段階5 Step 1 が所有する。本書では扱わない）。

### 1.4 ICE／STUN／TURN

- ICE 設定はメッセージ用と通話用で共用（`getCallICEConfig`）。STUN は Google と Mozilla（TURN 資格情報が返る場合はサーバー提供の配列に差し替え）。`iceCandidatePoolSize` は `CONFIG.ICE_CANDIDATE_POOL_SIZE` = 4。セッションごとに新しい ECDSA P-256 証明書を生成（指紋対策）。
- プライバシー保護のため、**生 IP の host 候補は破棄**される（mDNS の `.local` 候補のみ残る）。`_settings.relayOnly`（相手に IP を見せない設定）では srflx/prflx も破棄し `iceTransportPolicy: 'relay'` を強制する。
- TURN 資格情報は Worker の `/api/turn` が発行し、優先順位は (A) Cloudflare Calls TURN（運営者が `TURN_KEY_ID` 等を設定した場合、$0.05/GB)、(B) 自前 coturn 向け HMAC 資格情報、(C) 静的資格情報、(D) **無設定時のフォールバック: metered.ca Open Relay の無料公開資格情報（20GB/月）**。発行は登録済みユーザーに限る（`TURN_REQUIRE_AUTH`、既定 ON）。
- 既定インスタンスで A〜C のどれが設定されているかは repo から確認できない（Pages の secret は所有者だけが見える。`docs/SHARE_PLAN.md` §0-3 と同じ留保）。無設定なら、全利用者の TURN が第三者の無料枠に乗る。

### 1.5 直接が成立する条件・しない構造的理由

- **両者オンラインが必須**: DataChannel は同時接続が前提。不在側への配送はメールボックス（と機会的なピア預かり）が担う。
- **ランデブーはリレー必須**: 新規接続の SDP/ICE 交換はリレーの KV を介する。招待リンクや QR が運ぶのは identity の鍵であり SDP ではないため、**リレーが落ちている／届かない環境では、同じ LAN にいても新規の直接接続を始められない**（確立済みの接続は継続する。「サーバー不達でも P2P は動く」バナーはその範囲の話）。
- **NAT の相性**: 対称型 NAT 同士などでは srflx 同士が通らず TURN 中継に落ちる。TURN も失敗すれば接続自体が成立しない（30秒タイムアウト→再試行→上限で諦め、表示は「オフライン／中継」になる）。
- **グループはメッシュではない**: グループ配送は「メンバーごとの 1:1 DataChannel の集合」であり、グループ専用の接続はない。グループ上限は `GROUP_MAX: 100`。

## 2. 弱点の棚卸し

| # | 弱点 | 実態と影響 |
|---|---|---|
| W1 | **直接配送が中継費用を下げていない** | 常時二重配送のため、両者オンラインでも全通がメールボックスに預けられる。直接率が上がっても既定インスタンスの書き込み・保存は減らない。P2P 強化の費用効果は、まずこの構造を変えないと出ない |
| W2 | **シグナリングの恒常ポーリング** | 接続中の相手ごとに2秒間隔で `/api/signal` を poll し続ける（typing/read の受け口を兼ねるため）。会話数が増えるほど Worker リクエストと KV 読み取りが線形に増える。状態チャネル（接続後は typing/read を運べる）が既にあるのに、シグナリング側の poll は止まらない |
| W3 | **ランデブーの単一障害点** | 新規接続はリレーの KV が必須（§1.5）。段階2で相手ホームリレーへの fan-out は入ったが、「どのリレーにも届かない2端末」は接続を始められない。手動交換（QR／コピペで SDP を渡す）手段が無い |
| W4 | **既定 TURN が第三者の無料枠** | 無設定時のフォールバックは metered.ca Open Relay の公開資格情報で、上限（20GB/月）は全世界の利用者と共有される公開枠。通話・対称 NAT の配送・relayOnly（IP 秘匿）モードの成立が、運営者の管理外の枠に依存する。既定インスタンスの設定実態は未確認（§1.4） |
| W5 | **成功率が測れていない** | 経路種別と RTT はその場の UI 表示のみで、集計が一切ない（無テレメトリ原則のため当然でもある）。「直接が何割届いているか」が分からないままでは、強化の優先順位も効果判定もできない |
| W6 | **同一 LAN の扱いが偶然頼み** | LAN 発見機能は無い。生 IP の host 候補はプライバシーで破棄され、mDNS 候補が解決できる環境でのみ LAN 直通になる。同一 Wi-Fi の2台でも、環境によっては WAN を回る／TURN に落ちる |
| W7 | **グループ通話が無い** | `docs/SHARE_PLAN.md` の「致命的な不足」4件目と同一。「通話だけ他アプリに戻る」が残ると移行が完了しない。グループ配送が 1:1 接続の集合である現構造では、大人数メッシュは帯域的に成立しない（各自が N-1 本に送信）ため、人数上限を切った設計が要る |
| W8 | **ピア預かりの揮発性** | 第三者ピアの預かりはメモリ内のみ（タブを閉じれば消える）、20件/宛先・1時間 TTL。機会的経路としては妥当だが、「預かった」ことへの送信側の保証はなく、配送保証はあくまでメールボックスが担う。この線引きは UI からは見えない |

## 4. 強化の段階計画

各ステップは単独でマージ可能に切り、完了条件は実測で証明できる形にする。順序は「測る → 費用の構造を変える → ランデブーを分散する → 規模を広げる」。

### Step 1 — 端末内計測: 直接率を見えるようにする

接続試行ごとに、結果（成立／失敗／タイムアウト）、確立経路（direct／srflx／TURN）、確立までの時間、二重配送の実績（直接で届いた通数・預けた通数）を端末内（IndexedDB／localStorage）に集計し、利用者が自分で見られる表示（/security 系の画面か専用コマンド）を足す。サーバーへの送信は一切しない（§0-3）。

- 先行可能部分: 集計ロジックとテストは `src/` 側の切り離しモジュールで先に作れる。配備（index.html への組み込みと表示）は削減パス後。
- **Done when.** 2台の実機（または実ブラウザ2プロファイル）で、集計値が実際の接続結果と一致することを確認できる。集計が個人を特定する形で外部送信されないことがコードで確認できる。

### Step 2 — 直接優先の本格化: 二重配送を「保険つき片道」に変える

現行の常時二重配送（W1）を、**直接で届いた確認が取れたら預けない**形に変える。具体的には、DataChannel 上のアプリ層 ack（受信側が保存完了後に返す）を待ち、ack が来たらメールボックス預けを省略、タイムアウト／未接続なら従来どおり預ける。多端末の self-sync は別経路（fan-out）であるため、この省略とは独立に維持する。グループも同じ規則（メンバーごとに ack を見て預けを省略）。

- 前提: Step 1 の計測で現行の直接到達率を把握していること。ack の追加は封筒の形を変えるため、旧版との混在は「ack が無ければ預ける」側に倒して互換を保つ。
- **Done when.** テストで「ack あり→預け0件」「ack なし→預け1件」「未接続→従来どおり」が固定され、両者オンラインのシナリオでメールボックスへの書き込みが実質ゼロになることが計測（Step 1）で示せる。取りこぼし（直接で送ったが相手に残らない）が再現テストで否定される。

### Step 3 — シグナリングポーリングの削減

接続確立後の sigPoll（W2）を止める／大幅に間引く。typing/read は確立後の状態チャネルが運べるため、接続後の poll が必要なのは ICE 再交渉の候補だけに限れる。確立前も固定2秒ではなくバックオフ付きにする。代替として、メールボックス WS の合図チャネルにシグナリング到着を相乗りさせる案は、Worker 側の変更範囲と併せて本ステップで比較し、小さい方を選ぶ。

- **Done when.** 接続1件あたりの `/api/signal` リクエスト数（確立前／確立後）が Step 1 の計測で before/after 比較でき、確立後の恒常 poll が消えている（または合図駆動になっている）。typing/read の表示が従来どおり動くことをテストで固定。

### Step 4 — ランデブーの分散: SDP の手動交換（サーバーレス接続）

招待リンク／QR の仕組みを応用し、offer/answer の SDP を QR コードまたはコピペ文字列で直接交換して、**リレーを一切介さず** DataChannel を開ける経路を足す。対象は「同じ場所にいる2台」「リレーが遮断された環境」。署名つき SDP の検証は既存の仕組みをそのまま使う。identity の交換（招待）と接続情報の交換（本ステップ）は別画面にし、混同させない。

- **Done when.** リレーへの通信を遮断した2端末（同一 LAN）で、QR の往復（またはコピペ往復）のみで接続が開き、メッセージが往復することを実機で確認できる。リレー使用時と暗号の強度が同一であること（同じ封筒・同じ署名検証）。

### Step 5 — TURN の自前化と選択肢の固定

(a) 既定インスタンス: Cloudflare Calls TURN（優先順位 A）を設定する手順を所有者手順として固定し、接続が TURN 経由かどうかが §1.2 の経路表示で利用者にも分かる状態を維持する。(b) 段階2のリレー運営者向けに、自分の TURN（coturn ＋ HMAC、優先順位 B）を Worker の env で配る手順を `docs/SELF_HOSTING.md` に追う。(c) Open Relay フォールバック（W4）に依存している場合は、その旨と無料枠の性質をプライバシー説明に正直に書く。

- 本ステップは Worker のコード変更を必須としない（env と手順と文書が中心）。index.html に触らない。
- **Done when.** 既定インスタンスで優先順位 A の TURN が返ることが `/api/turn` の応答で確認でき（所有者の設定作業を含む）、SELF_HOSTING の手順どおりに立てた自前リレーで TURN 経由の通話が成立する。

### Step 6 — グループ通話（メッシュ、小規模限定）

SHARE_PLAN 段階5のグループ通話の P2P 側設計。小人数（目安4〜6人まで）に限ったフルメッシュ音声から始める。各参加者が N-1 本の PeerConnection を張る現行 1:1 通話の部品を再利用し、上限を超えたら「この人数では未対応」を明示する（黙って劣化させない）。ビデオと画面共有は本ステップの範囲外。シグナリングは既存のグループ配送経路に相乗りさせるか、メンバーごとの `call:` ルームを使うかを、実装時に実測して決める。

- **Done when.** 4端末で同時通話が成立し、各端末の送信帯域の実測が想定（音声ビットレート × (N-1)）と一致する。上限超過時の表示が固定される。1:1 通話への退行がない。

### Step 7 — LAN 内の扱いの確定（発見はしない、という決定を含む）

ブラウザからは mDNS 発見を能動的に行えないため、Web 版での LAN 発見は**やらない**と決める。その代わり: (a) mDNS 候補で LAN 直通になる条件を実測し、成立する環境では表示（経路種別）で分かるようにする、(b) LAN で確実に直通させたい場合は Step 4 の手動交換が公式の答え、と文書と UI の言葉を揃える。ネイティブ版（Tauri／Capacitor）での mDNS 発見は、配布形態側の判断として別途記録し、本書では実装しない。

- **Done when.** 同一 LAN の2端末での経路種別の実測結果が文書に残り、手動交換への案内がアプリ内から辿れる。

## 5. 費用との接続

費用の正本は別途作成中の費用試算（`docs/COST_MODEL.md`）とし、本書では P2P 側のレバーだけを接続する。

- **Step 2 が最大の費用レバー**: 現行は直接率が上がってもメールボックス書き込みが減らない（W1）。ack 連動の預け省略が入ると、両者オンラインの通信量に比例して既定インスタンスの書き込み・保存が減る。効果の測り方は COST_MODEL 側の単価に Step 1 の計測値（直接到達率）を掛ける形になる。
- **Step 3** は Worker リクエスト数と KV 読み取りの削減として効く。**Step 5** は TURN の GB 単価を運営者の管理下に置く話であり、無料枠の消尽リスク（W4）を費用の見通しに変える。
- 逆向きの注意: TURN 中継に落ちる接続は「P2P でない」のではなく「P2P の経路が中継サーバーを通っている」もので、費用は TURN の GB 課金として出る。直接率の計測（Step 1）では direct／srflx／TURN を分けて数え、TURN 比率を費用試算へ渡す。

## 6. 範囲外・未確認事項

- **範囲外**: 暗号方式の変更（段階3の領分）、通話シグナリング E2EE の既定変更（SHARE_PLAN 段階5）、グループ配送の暗号（Sender Key）の変更、大人数グループ通話（SFU 等のメディアサーバー導入は「サーバーレス運用」の前提を変えるため別判断）、ネイティブ版の LAN 発見。
- **未確認**: 既定インスタンスの TURN 設定（A〜C の有無）と本番フラグの実態（repo から確認不能、所有者のみ確認可能）。実際の NAT 環境分布と直接到達率（Step 1 の計測が入るまで不明）。ピア預かり（§1.1）の実利用頻度（計測なし）。
