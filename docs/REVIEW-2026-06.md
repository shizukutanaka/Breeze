## 4. Implemented this pass

- **W2 fixed.** `src/crypto/ratchet.js` reverted to its pre-item-92 surface (group +
  X3DH only). The inline at-rest helpers in index.html now mirror `atrest.js`:
  record `{ v, kdf:'pbkdf2', hash, iter, salt, iv, ct }`, AAD `breeze-atrest-v1:<slot>`
  (slot = `keys` / `signing`), `iter` DoS guard (≤ 10,000,000), and
  `_atRestIsWrapped`/`_atRestLoadKey`/`_atRestMigrate` matching the module. `/keywrap`
  enable uses `migrate` (nested `wrapped`, plaintext `priv` removed); disable unwraps
  and restores plaintext. Redundant ratchet.test.js at-rest tests removed —
  `atrest.test.js` (20 tests) is the canonical coverage.
- **W3 fixed.** `dhRatchetStep` now resets `recvCounter` alongside `sendCounter`.

### Update (item 94)

- **W4 falsified.** Socratic claim: *"the inline ratchet advances `recvChainKey`/`recvCounter`
  and populates `skippedKeys` before the AES-GCM decrypt, so a forged ciphertext desyncs the
  chain."* Falsified by reading the persistence boundary: `getSession` → `dbGet` returns a
  fresh IndexedDB structured clone every call (no shared in-memory session), and `saveSession`
  runs **only after a successful decrypt** (and the skipped-key hit). On a decrypt throw the
  mutated `sess` is never written back, so IDB keeps the pre-message state and the next genuine
  message re-derives correctly. The ordering is fragile but **not** a live desync. Left as-is;
  the clean ordering lands with the G4 ratchet-module port (tested).
- **W5 fixed.** `encryptFor` no longer compresses plaintext before AES-GCM (CRIME/BREACH-class
  length side-channel, I15). Messages are sent uncompressed (flags bit0 = 0); the receive path
  retains decompression for legacy flag-set messages, so the change is wire-compatible in both
  directions. Matches `src/crypto/ratchet.js` (`frameEncrypt` default `compressMin: Infinity`).

### Update (item 95 — Trusted Types enforcement, Phase 2d)

**Research source.** Qiita and Zenn articles validate a phased Trusted Types + CSP rollout:
the Zenn team's own production CSP introduction (`team_zenn/introduced-csp-to-zenn`) shows
the default-policy safety-net pattern; multiple Qiita/MDN references confirm
`require-trusted-types-for 'script'` covers `innerHTML` / `insertAdjacentHTML` / `outerHTML`
/ `iframe.srcdoc` / `document.write` / `eval` / `new Function` / `setTimeout(string)`.

**Audit.** Breeze has 98 raw HTML sinks (88 `innerHTML` + 6 `insertAdjacentHTML` + 4
`outerHTML`, all from `renderReactions`) and **zero script-creating sinks** — no `eval`, no
`new Function`, no `setTimeout(string)`, no dynamic `<script>` injection, no `iframe srcdoc`,
no `document.write`. So a single `createHTML` policy covers the whole attack surface.

**Fix.**
- Register a **`default` Trusted Types policy** alongside the existing named
  `breeze-sanitizer`. Both call the same `sanitize()` function (DOMParser + tag/attr
  allowlist + `javascript:` href strip). The default policy is the browser's safety net
  for any raw `el.innerHTML = stringValue` site, so the 98 untargeted sinks become
  sanitized transparently rather than throwing SecurityError under enforcement.
- Add `default` to the `trusted-types` directive in BOTH `_headers` and the inline
  `<meta http-equiv="Content-Security-Policy">`, and add
  `require-trusted-types-for 'script'` to enforce. Browsers without TT support (Firefox,
  Safari) silently ignore the directive; behavior is unchanged for them.
- Hot-path cost: the sanitizer's fast path (`if (!/</.test(html)) return html`) returns
  in one regex test for plain text — which is the common case after `esc()`. Only HTML
  containing `<` triggers the DOMParser walk.

### Update (item 96 — Service Worker cache hardening)

**Research sweep (round 2).** Audited the surfaces a Qiita/Zenn sweep flagged (Cloudflare
KV cost, WebRTC reconnection, IndexedDB perf, SW/PWA caching) against the code. Most were
already mature — worker presence cache + 5-min KV write batching (`handlePresence`), the
lossless +1ms poll cursor (`handleMsgSend`/`handleMsgPoll`), the shell-preserving SW cache
trim, and a complete PWA manifest (share_target / protocol_handlers / shortcuts /
edge_side_panel). So the prior roadmap's Phase-3 items (KV pressure, same-ms poll loss) are
**already addressed**. Net: one concrete gap remained.

- **SW `Cache.put()` pitfall fixed.** Both fetch-handler put sites guarded with `if (resp.ok)`,
  but `resp.ok` is **true for 206 Partial Content**, and `Cache.put()` throws on a partial
  response; the put was also unawaited/uncaught, so a 206 (range request) or a
  `QuotaExceededError` (storage full) became an unhandled rejection. New DRY `cachePut()`
  helper caches only `status === 200 && type === 'basic'` responses (skips 206, opaque, CORS)
  and wraps the write in `.catch(() => {})`. 5 new `tests/sw.test.js` cases via the existing
  mocked-global harness.

### Update (item 97 — modal a11y + button i18n)

**Research sweep (round 3 — accessibility).** Audited modals/menus against the ARIA APG
dialog pattern and live-region guidance. Breeze already uses native `<dialog>` +
`showModal()` (role=dialog, aria-modal, focus trap, ESC, focus-restore for free), a
`role=menu` context menu with arrow-key nav, and an `aria-live` SR announcer — so the
structural pieces were present. Two gaps:

- **Accessible name missing.** `showPrompt`/`showConfirm` dialogs had no `aria-labelledby`
  (nameless dialog to a screen reader) and the prompt `<input>` had only a placeholder.
  Fixed: unique `titleId` on the title, `dlg.aria-labelledby = titleId`, input
  `aria-labelledby = titleId`.
- **Hardcoded English buttons.** "Cancel"/"OK"/`aria-label="Cancel"` bypassed `t()`. Added
  `cancel`/`ok` i18n keys (EN+JA); buttons now use `t('cancel')` / `opts.okText || t('ok')`;
  dropped the redundant aria-label (translated text is the accessible name). 33 call sites.

### Update (item 98 — peer-heartbeat interval leak)

**Research sweep (round 4 — memory leaks).** Audited every `setInterval` against its
teardown. Most are tracked in `_intervals` (cleared on account switch) or are
lifecycle-scoped (`_callTimerInterval`, `_recTimer`, cleared at call/recording end). One
genuine leak: the account-switch teardown (`_messengerCleanup`) cleared each peer's
`_healthTimer` but **not** its sibling `_heartbeat`. `_heartbeat` is otherwise cleared only
by the connectionstatechange handler — and `pc.close()` does not fire that event (per
spec) — so after every account switch each peer's heartbeat kept firing against a closed
DataChannel, pinning the old `peerState` graph against GC. Fixed by clearing `p._heartbeat`
in the teardown loop (symmetric with `_healthTimer`). Inspection-verified (no unit harness
for the inline WebRTC peer path).
