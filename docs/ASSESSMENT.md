## 1. 長所(実証済みのもののみ)

- **広告ゼロ・トラッキングゼロ・登録ゼロ。** 鍵そのものがIDであり、メールも電話番号も
  Passkeyも要らない。「アカウント作成が面倒」という不満に対する解が *作成という工程の削除* に
  なっている。
- **送信者がリレーから暗号学的に隠れる(Sealed Sender v2)。** 送信者ID・公開鍵・表示名・
  署名鍵・返信プレビュー・マルチデバイス標識を受信者の鍵へ封印(ephemeral X25519 → HKDF
  `breeze-seal-v2` → AES-256-GCM、AADが宛先と時刻を束縛)。初回接触のX3DHヘッダが送信者の
  identity鍵を生バイトで露出していた欠陥も封印済み — **盗聴E2E(`seal.spec.js`)が実バイトを
  検査**して証明している。
- **マルチデバイスが実際に動く。** 受信の両デバイス配送、帰属(副デバイス送信が相手の同じ
  会話に入る)、自己同期(新品のPCが会話ごと復元)、編集・削除の伝播、添付のfan-out —
  すべて `multidevice.spec.js` の5幕で実ブラウザ実証。
- **暗号状態がリロードを生き延びる。** 1:1のDouble Ratchetもグループのsender keyも、
  リロード後に復号・送信が継続する(`lifecycle.spec.js`、本セッションで新規実証)。
- **主張とコードの一致を機械が守る。** ミラードリフト検査(インライン実装 vs 参照実装)、
  CSPハッシュピン留め、死にi18nキー検出、到達不能関数検出 — いずれも**歯があることを
  実証済み**(意図的に壊して BLOCKED を確認してから戻す運用)。
- **「静かなメッセンジャー」の設計。** 返信不要マーク(未読を増やさない)、遅延既読、
  集中モード、端末内だけの重要度判定。LINEが構造的に真似できない差別化(向こうの収益源は
  エンゲージメント)。

## 2. 短所(正直に、原因の所在で分類)

### 2-1. 外部要因で待つもの(こちらで閉じられない)
- **CIが未稼働。** 796+32+39のゲートが自動実行されていない。自動化アカウントに GitHub の
  `workflows` OAuthスコープが無く `.github/workflows/*` をpushできないため。
  手順とワークフロー内容は `docs/CI-SETUP.md` に保全済み。**メンテナが有効化すれば即動く。**
- **ポスト量子(PQXDH)未展開。** ML-KEM のブラウザ実装待ち(~2027)。`src/crypto/pq.js` は
  テスト済みだが未配線。今日の鍵合意は古典的(X25519)。

### 2-2. 意図的な設計上の制限(理由つきで選んだもの)
- **グループ送信はプライマリ端末限定。** 副デバイスを名簿に載せると、メンバー数×端末数の
  肥大とエポックchurnを招く。**黙って捨てず明示的に拒否**し、入力テキストを返す実装。
- **履歴同期なし。** 新しくリンクした端末は空から始まる(Signalと同じ判断)。`/backup` が移行経路。
- **root端末を失うとデバイス管理が不能。** 登記簿の署名者がrootのみ。既存端末のメッセージングは
  継続する。

### 2-3. 残る弱点(内部要因 — 改善余地あり)
- **sealed キューは best-effort(ただし回復あり)。** Cloudflare KV は last-write-wins で
  トランザクションが無く、同一宛先への同時書き込みで封筒を失いうる — しかも両送信者に200が返る
  ため**損失が不可視**だった。送信側で**書き戻し確認と再追加**を実装(送信は3秒ポーリングに比べ
  低頻度なので読み取り1回の増加で済む)。教科書的な「封筒ごとにキーを分ける」は競合を根絶するが、
  最ホットパスの `get` 1回を `list`+メッセージ数分の `get` に置き換えるため、無料枠(書き込み
  1000/日)で presence 書き込みまで絞っている本製品では割に合わないと**計測して**却下した。
  **exactly-once ではなく「回復つき best-effort」**。
- **招待トークンがロスターへの鍵になっている。** `/group/info` は参加せずともメンバーのID・
  公開鍵・表示名を返す。**当初これを「署名でメンバー限定にすれば内部で閉じられる」と評価したが、
  実装して誤りと判明した**: `/group/join` はトークンだけで参加でき(署名も承認も不要)、参加応答が
  ロスターをそのまま返す。つまり読み取りを塞いでも、攻撃者は join して同じものを、しかも
  メッセージ受信権つきで得る。**弱い読み取りを塞いで強い書き込みを開けておく制御は、
  セキュリティに見えて実効性がない**ので撤回した(既存13テストの失敗が再考の signal になった)。
  実効的な対策は *join* 側を絞ること(管理者承認など)であり、それはプライバシー修正ではなく
  プロダクト仕様の決定。現時点の正しい理解は **「招待リンク = グループ参加権とほぼ等価」** であり、
  リンクの取り扱いをそう説明することが唯一の緩和策。
- **失効の伝播が最大5分遅延。** 送信側キャッシュTTLに等しい。
- **バックグラウンドのポーリングが15秒間隔。** 前面なら3秒。PWAを裏に回すと着信が最大15秒遅れる。
- **クラウドバックアップは90日で消える。** 最終アップロードから。期限を返して表示するようにしたが、
  自動延命はしていない。

### 2-3b. 到達不能だった機能(発見と修正)
**マルチアカウントは完成していたのに、UIから一度も到達できなかった。** 切替・per-account DB・
未読バッジ・Ctrl+1〜9・改名/削除まで実装済みなのに、2個目を作る「+」が**アカウントタブバーの
内側**にあり、そのタブバーは「アカウント2個以上」で初めて描画される — ブートストラップ・
デッドロック(3セッション実測: `#acc-tabs` 0個・`.acc-add` 0個)。さらに作成できても、新
アカウントはIDが無くセットアップ画面に出るが、タブバーは `#msg-main` の内側にあり隠れるため
**新アカウントに閉じ込められる**(脱出は未公開のCtrl+1〜9のみ)。設定パネルに入口を追加し、
セットアップ画面でも切替可能にした。削除ではなく修正を選んだ根拠は、機能が首尾一貫して
完成しており欠陥が「条件1つ」だったこと。

**同じクラスがもう2件見つかった(死んだ配線)。** `_DOM.get('id')` は存在しないIDに `null` を
返し、コードは `?.` を多用するため、**要素の削除・改名はリスナーを静かに無力化する**。
全77件を照合したところ3件が不在IDを指していた:
- `b-msg-backup` → **ローカル暗号化バックアップの作成が到達不能**。復元側はサイドバーへの
  ドラッグ&ドロップで生きていたため、**作れないファイルを復元できる**という非対称な行き止まり。
  SECURITY.md が root鍵喪失の回復経路として案内しているのはこれであり、クラウド版が90日で
  消えるのに対しローカルファイルは無期限 — 失われていた側が価値の高い方だった。
  `/backup` パネルに「ファイルに保存/ファイルから復元」を追加して解決。
- `b-msg-panic` / `contact-sort` → 機能自体は `/panic`(+Ctrl+Shift+Backspace)と `/sort` で
  到達可能なため、残骸のリスナーのみ削除。
再発防止として `tools/dead-wiring.mjs` を新設し validate.sh に組み込み(40チェックに拡張)。

**4件目: `/api/alias/delete` — 完成・単体テスト完備・呼び出し元ゼロ。** Worker側のコメントが
意図を明記していた:「これがないとアカウント全体を消す以外に旧エイリアスを解放する方法がない」。
実際、クライアントの `/alias newname` は新エイリアスを設定するだけで**旧エイリアスを一度も
解放しておらず**、alias レコードにTTLは無い(「aliases are permanent」)ため、**改名するたびに
旧ハンドルが relay 上に永久に居座り、元の持ち主すら二度と取り戻せない**まま残っていた。
署名検証・所有権チェックまで含めて `handleAliasDelete` は7本のWorker単体テストで固められて
いたが、呼び出すコードがどこにも無かった。`/alias` 成功時に旧エイリアスを
`signMessage('breeze-account-delete:...')` と同一の署名パターンで解放するよう配線。

**5件目、修正の途中で発見: 成功トースト自体が例外を投げていた。** `/alias` の成功メッセージは
`showToast(t('toastAliasSet')(newAlias), 'success')` と書かれていた — `t()` は**常に文字列を
返す関数**であり(プレースホルダー引数は `t(key, ...args)` として渡す設計)、その戻り値の文字列を
関数として呼び出すコードは必ず `TypeError` を投げる。実際に何が起きるか: エイリアス変更・
予約送信・チャットインポート・GDPRエクスポートの4箇所全てが**この誤字を持っており、いずれも
本体の処理は成功した直後に例外を投げ**、グローバル `unhandledrejection` ハンドラが
「成功しました」の代わりに生の `t(...) is not a function` を赤トーストで表示していた。
`/schedule` は特に深刻で、例外が発生する行が実際の配信タイマー登録(`setTimeout`)の**手前**に
あったため、その場では配信タイマーが一度も張られず、次回リロード時の起動時回収スキャンが
拾うまで送信されないという実害を伴っていた。4箇所とも `t(key, args)` に修正し、
`tools/i18n-check.mjs` に検査8(`t('key')(...)` パターンの静的検出)を追加して再発を防止。

**6件目: マルチアカウント課金(Stripe)— 実装され、削除され、その記録だけが無かった。**
README・`.env.example`・`SPEC.md`・`docs/CRYPTO-SPEC.md`・アプリ内利用規約/プライバシーポリシー
の5箇所以上が Free/Lite/Plus/Pro のサブスクリプション課金を「動作する機能」として説明していた。
実際には `_worker.js` にチェックアウト・Webhook・ポータルのルートが一切無く、`api.stripe.com`
への呼び出しもリポジトリ全体でゼロ。`slots:{userId}` のKVスキーマ(`{ slots, plan, customerId,
updatedAt }`)は `handleAccountDelete` の削除処理が読み取り専用で参照するだけで、書き込む経路が
存在せず、クライアントの `addAccount()` もプラン上限を一切チェックしていない——現状は自己ホスト・
ホスト版問わず誰でも無制限にアカウントを追加できる。`index.html` に残っていたコメント
(「the billing system is gone but the TURN fetch must remain」)から、これは**未実装ではなく
実装後に削除された**機能だと判明したが、AI/翻訳/OGPの削除と異なり `SECURITY.md` に除去記録が
残されておらず、ドキュメント群だけが古い状態のまま取り残されていた。ユーザーに方針を確認し、
「AI/翻訳/OGPと同じ扱いで、削除済みとして文書化する」との判断を得て、上記ファイル群 + `AGENTS.md`
+ 死んだCSS(`.nudge-*`, `.upgrade-modal`)+ 孤立コメント2件を修正。Stripe実装の再構築は別途
明示的な依頼が無い限り着手しない。`docs/CATEGORY-RESEARCH-2.md`(カテゴリ16を✅として記述)と

**9件目: クライアント末尾の約190行が Electron 専用ブロックに閉じ込められていた。**
キーボードショートカットの実装と文書の突き合わせから芋づる式に判明。`// Global: Escape to
close modals + keyboard shortcuts (all platforms)` と**自ら「全プラットフォーム」と書いている
ブロックが、`if (PLATFORM === 'electron' && window.breeze)` の内側**にあった。閉じ括弧が約190行
下にあったため、以下がすべて web/PWA(主要プラットフォーム)で一度も実行されていなかった:

- Escape によるオーバーレイ/コンテキストメニューの閉じ処理、Ctrl+K / Ctrl+Shift+F / Ctrl+N /
  Ctrl+1..9
- スクロール最下部ボタン(`#scroll-fab`)、上スクロール中の未読バッジ加算
- 消えるメッセージのライブカウントダウン、チャット内検索バーの配線
- `if (IS_MOBILE)` ブロックと `if (PLATFORM === 'capacitor')` ブロック——**electron ガードの
  内側にあるため論理的に到達不可能**

実ブラウザで確認: web では Escape を押しても `.overlay` が消えず、`#scroll-fab` と
`#search-bar` は DOM に存在するだけの死んだ UI だった。`?` のショートカット一覧と
`helpKeysHint` は、これらを全ユーザーに宣伝し続けていた。

**閉じ込めを解いた瞬間に潜在バグが露出した**——`_intervals is not defined`。`_intervals` は
`initMessenger()` 内のアカウント切替用タイマー追跡配列で、ページレベルで一度だけ走るこの
コードからは見えない。死んだコードだったため誰も気づけなかった。ページ単位のインターバルは
アカウント切替でのクリーンアップを必要としないため、素の `setInterval` に修正。

インデントは意図的に元のまま残した: この範囲にはテンプレートリテラルが含まれ、先頭の空白が
出力HTMLの一部になるため、再インデントは整形ではなく**文字列の変更**になる。

副次的に修正した2件: (1) Ctrl+K が3重に束縛されており、コンポーザーで「コード書式」を使うと
書式は適用されるが**フォーカスが連絡先検索に奪われ**入力が中断されていた(重複ハンドラを削除
し、入力中は大域ハンドラを無効化)。(2) `helpKeysHint` が全プラットフォームで Ctrl+1..9 を
宣伝していたが、実装は Electron 限定。ブラウザは Ctrl+1..9 をタブ切替に予約しており web で
確実に動かせないため、主張の方を取り下げた(EN + 7ロケール)。

**8件目、最も重い: リロードしたタブがメッセージを受け取らなくなる(リーダーロック競合)。**
「E2Eが時々落ちる」を flake と片付けず追跡した結果、**実在するメッセージ消失**だった。計測:
リロード後の配送を6回試行して**4回が消失**。失敗時、受信側は14秒間で**APIリクエストを1本も
発行していなかった**——ポーリングループが完全に停止しており、メッセージはリレーの sealed
キューに残ったままだった(`/sealed/poll` を直接叩いて存在を確認)。

原因は `acquireLeaderLock()` の2つの欠陥。ポーリングはリーダータブだけが行う設計のため、
ここを誤ると「何も受信しない」に直結する:
1. **`navigator.locks.request()` を await していなかった。** `await acquireLeaderLock()` は
   コールバック実行前に解決するので、`startPolling()` は `_isLeaderTab === false` のまま走り
   即 return する——起動処理とコールバックの純粋な競合。
2. **`ifAvailable: true` かつ再試行なし。** リロード中は**直前のドキュメント**が一瞬ロックを
   保持しているため、新しいドキュメントは「フォロワー」と判定される。しかもリーダーは存在
   しないので、二度とポーリングされない——恒久的な無受信状態。

修正: ロックの**取得結果**(解放ではない——リーダーはタブの生存中ロックを保持し続けるのが
設計なので、request 自体を await すると起動が永久に止まる)を await するようにし、フォロワー
側は `ifAvailable` なしで再度キューイングして、現保持者が消えた瞬間に昇格して
`startPolling()` を開始するようにした。Web Locks が排他性を保証するので二重ポーリングは起きない。
検証: 同一の再現ハーネスで**消失 4/6 → 0/6**、以前は3回中1〜2回落ちていた smoke テストが
20/20、全E2E 34/34。

**7件目: 924言語テーブル(`lang.js`)は、UIに1文字も供給していなかった。**
569 KB ——アプリ全ペイロードの**44%**——を全ユーザーが毎回のコールドロードでダウンロードして
いたが、計測の結果、供給していた文字列は**ゼロ**だった。`t()` の解決順は
`完全ロケール → 英語 → lang.js` であり、インライン英語テーブルは完全なリファレンス
(`tools/i18n-check.mjs` が「使われる全キーは英語に存在する」を保証)なので、英語が毎回
短絡する。25キーのうち18キーがこの影で到達不能、残り7キーは**アプリ内のどこからも `t()` に
渡されていない**。

**そして、これは「修正済み」とされていた機能だった。** CHANGELOG(2026-08時点)には
「924言語テーブルが一度も届かない」問題の修正記録がある——`detectLang()` を再実行可能にし、
`lang.js` 到着時に再描画する、と。その修正は**検出側だけ**を直して完了とされた。実ブラウザで
スワヒリ語ロケールを前後で検証したところ、`LANG='sw'` は正しく解決されるのに、表示される文字列
は修正前後とも英語のままだった。つまり、その修正が防ごうとした結果そのものが、そのまま残って
いた。`docs/FIRST-PRINCIPLES.md` が「最も飛ばされやすい8番目の問い」と呼ぶ
**「その改善自体は検証されたか」**の、実例である。

修正ではなく**削除**を選んだ理由: 仮に解決順を直しても、届くのは667文字列中せいぜい25
(3.7%)——96%が英語のUIに外国語が25語混ざる状態は、翻訳ではなく故障に見える。第一原理で見れば
要件そのものが成立していない。完全な翻訳ファイルを持つ7ロケール(`ja`/`ko`/`zh-TW`/`es`/`th`/
`id`/`pt-BR`)は無傷で、削除後も実ブラウザで日本語UIを確認済み。RTL(アラビア語/ヘブライ語/
ペルシャ語/ウルドゥー語)も維持した——RTLは569 KBのテーブルを必要とせず `navigator.language`
だけで判定できるため、そちらを直接読むよう配線し直した(削除後も `dir=rtl` を実ブラウザで確認)。
副次的に、`/security` コマンドが削除済みの `/api/translate` と `/api/ai` を「✓ 有効」と
ユーザーに表示し続けていたことも発見・修正(実行時の文字列出力だったため、本セッションの
ドキュメント一掃をすり抜けていた)。SRIチェックは「外部スクリプトが存在しないこと」を
検証するゲートに置き換えた——ハッシュを固定するより強い保証になる。

**副次的発見、そして解決: `SPEC.md`の「5.4 Diagnostics」コマンド表の陳腐化は、根拠のある
意図的削除だった。** `/billing`行の検証中に同表の `/network`・`/peers`・`/storage`・`/perf`・
`/about`・`/uptime` も実際には存在しないことが判明(`val === '/xxx'` の呼び出しパターンで確認)。
次サイクルで `index.html` 内の孤立コメント(`// v3: /status — Show connection and crypto info`
の直後に無関係なコードが続く、既出パターンと同一)を追ったところ、**自己文書化された削除記録**を

/perf /speedtest /network /peers /storage /stats /uptime /status /about /changelog /keyboard.
582 lines and ~90 i18n keys × 8 locales spent on WebRTC candidate dumps, KV counters and an

validate.sh方式(固定数値でなくツールで都度計測)に倣い、SPEC.mdの見出しは実数を主張しない
注記に変更、READMEは「60+」という下限保証の表現に変更。

### 2-4. プロセスの弱点(本セッション最大の学び)
**E2Eが「初回セッション」に偏っていた。** 10本のspecのうちリロードを行うのは3本のみで、
その3本はすべて本セッションで追加したもの。結果、**復帰ユーザー全員でアプリが機能停止する
バグ(TDZによる起動中断 → 連絡先0件・メッセージ受信ゼロ)が29本の緑をすり抜けた**。
テストが緑であることは「テストした範囲が正しい」以上を意味しない。
→ 是正済み(リロード系3本を追加)。今後は**同種の偏りが他にないか**を点検軸とする。

### 2-5. 同種の偏りの第二例: 「存在するか」は測っていたが「どこにあるか」は一度も測っていなかった
2-4で立てた点検軸(**同種の偏りが他にないか**)が、そのまま次の重大欠陥を掘り当てた。

スクロールFAB(本セッションでElectron専用ブロックから解放した機能の一つ)が出ない理由を
実ブラウザで計測したところ、`#msg-messages` は `scrollHeight === clientHeight`、スクロール
イベント**ゼロ**。スクロールに失敗しているのではなく、高さを制約する祖先が無いため
**そもそも溢れていなかった**。親チェーンを辿ると `.msg-layout` が**丸ごと欠落**していた。

原因は連絡先リスト直後の `</div>` 一個の重複。HTMLに構文エラーは無い——パーサは
`.msg-layout` を約50行早く閉じ、以降を黙って別の親に付け替える。結果 `.chat-area` は
レイアウトの第2カラムではなく**その下に置かれるブロック**になり、1280×800で会話ペインは
**y=781(画面外)**、サイドバーだけが700pxの枠を占有して右三分の二が白紙。高さの制約が
消えたので `overflow-y: auto` は無意味になり、ページ側が伸びた(800pxのビューポートに
3022pxの文書)。これがFABを死んだUIにし、`scrollTop = scrollHeight` を全て無言のno-opに
していた。

**この状態で validate.sh 41項目・ユニット798本・E2E 35本が全て緑だった。** 要素は全て
存在し、可視で、クリック可能だった——Playwrightは画面外の要素も平然とクリックする。
誤っていたのは**画面上の位置だけ**で、このリポジトリのどの assertion も座標を一度も
測っていなかった。

→ 2層で是正。`tools/html-balance.mjs`(構造的原因: 閉じタグが最内の開タグと一致することを
機械的に要求。`</div>` が `<main>` を閉じるのは常にバグなので判断の余地も誤検知も無い)と
`tests/e2e/layout.spec.js`(症状: チャット列がサイドバーの右端・同じ行から始まり、長い会話が
**文書ではなくボックス**を溢れること。マークアップ無傷のCSS退行も捕捉する)。両方とも
修正前のファイルに対して失敗することを確認済み。
**教訓: 「テストした範囲」には、測っている属性の種類も含まれる。**

### 2-6. 同じ計測手法を未検証の面へ横展開し、3件を追加発見
2-5の教訓(座標を測る)をトースト・スラッシュコマンド送信・絵文字ピッカー・スワイプ操作という
未計測の面へ機械的に適用した結果、性質の異なる3件がさらに見つかった。

1. **トースト崩壊**: `.toast` がコンテナ側と同じ `position:fixed; left:50%` を重複保持。
   コンテナの `transform` が fixed 子孫の包含ブロックとなり、全子要素がフロー外のため
   コンテナ幅が**0px**——各トーストが min-content(143×234px、13行)に潰れていた。
   アプリ唯一のフィードバック経路(60箇所以上)が全画面で読めない状態。
2. **送信ボタンでコマンドが相手に送信される**: `sendMessage()` が先頭 `/` を見ておらず、
   送信ボタンをクリックするとコマンドがそのまま暗号化されて**相手に配信**されていた
   (相手側IndexedDBで確認)。Enter側には同じガードが既にあり「以前E2Eがリテラル送信を
   検出した」というコメントまで付いていたが、修正がEnterのみに適用されていた。
   `/drop <secret>`(秘密をチャットログに残さないための機能)がそのまま相手のチャットに
   残る、プライバシー上最も重い部類の欠陥。
3. **絵文字ピッカーの画面外はみ出し**: モバイル用オーバーライドが `width: calc(100vw-16px)`
   (ビューポート基準)と `left/right:8px`(実際の包含ブロック `#msg-input-bar` 基準——
   ビューポートより狭く内側にオフセットされている)を混在させ、3プロパティが過剰制約。
   仕様上 `right` が負けて右端が画面外へ3px はみ出す(差分は無関係な祖先の余白に依存し、
   デバイスや今後のレイアウト変更で悪化しうる)。
4. **スワイプ操作が見た目と逆の結果になる**: `touchmove` がインラインで
   `style.transform = translateX(dx)px` を設定し、`touchend` は `.swipe-back` クラスの
   `!important` でそれを一時的に**覆い隠す**だけで、インライン値自体は一度もクリアされ
   ない。250ms後にクラスが外れるとマスクが消え、消したはずのオフセットへ**無言で
   スナップバック**する。メッセージへのスワイプ返信・連絡先の左スワイプアーカイブの
   両方に同一パターン。連絡先側は閾値を超えた場合だけ `renderContacts()` が偶然もみ消す
   ため、閾値未満で離した(=よくある「やっぱりやめた」)ケースが唯一かつ永続的に
   壊れたままになる。

4件とも要素は存在しクリック可能で、既存の833本の緑テストはどれも気づかなかった——
座標・文字列を実測して初めて見える種類の欠陥である点で2-5と同じ。テスト自体の誤りも
2件見つかった(モバイル幅での送信ボタンクリックがコンセントバナー/サイドバーに
遮られていた/`history.back()`の非同期解決を待たずに次の操作へ進んでいた)ため、
「バグ修正前のファイルに対して実際に失敗するか」を毎回確認する手順が今回も機能した。

### 2-7. スコープ境界の見落としが3連鎖(Electron un-trapping fixの見えなかった副作用)
前回セッションの残タスク「un-trapされた機能の未検証分を確認」から着手し、1件の
バグ修正が次の隠れたバグを露出させる、という展開が3回続いた。

1. **Ctrl+N・Ctrl+Fが毎回 ReferenceError**: Electron専用ブロックの中括弧は前回正しく
   均衡させたが、その解放されたコードが `initMessenger()` **自身の閉じ括弧**より後ろ
   (トップレベル)に着地していたことは未確認だった。`dbGetAll`/`activeContact`/
   `openConversation` は同クロージャ内のローカルで、外側から参照すると即座に
   ReferenceError(実ブラウザの `pageerror` で確認)。すぐ隣の `_selectMode`/
   `togglePicker` チェックだけが `typeof x !== 'undefined'` で守られていたのは、
   書いた本人がこの境界の危うさを認識していた証拠——Ctrl+N/Ctrl+Fだけ同じ配慮が
   漏れていた。`e.preventDefault()` は実行済みのため、Ctrl+Fはブラウザ標準の検索も
   道連れで潰していた。是正: 該当関数を `window.*` に公開(`togglePicker` 等で
   既に使われている手法。300行規模の巻き戻しは「大規模リファクタリング禁止」に反する)。
2. **v3.5 delegated ハンドラの生き残り**: 同じ境界の見落としを軸に周辺を洗ったところ、
   `#msg-messages` 上の古い(v3.5)右クリックハンドラが、新しい per-message
   `showMsgMenu`(v3.6)追加後も削除されずに残っていた。両方が同じ右クリックで発火し、
   `showContextMenu()` は自分の描画前に既存 `.ctx-menu` を消すため、**後から実行される
   方(常に古い方)が勝つ**——新しいメニューは同一同期イベント内で生成・即破棄されて
   一度も描画されない。React・Bookmark・Select・Report が完全に到達不能(代替経路
   なし。複数選択モードの唯一の入口、デスクトップでの通報の唯一の手段)。是正:
   古いハンドラを削除(新しい方が真の上位互換であり、msgIdの型不一致バグも元から
   無く、返信UIも swipe-to-reply と共通の `startReply()` を再利用している)。
3. **削除して初めて見えた3つ目**: 重複が消えたことで `showMsgMenu` 自身の描画バグが
   露出。メニューをメッセージバブルの子要素として追加していたが、バブルには
   `content-visibility` 最適化のための `contain: content` が付いており、paint
   containment は fixed 配置の子孫も含めて**バブル自身の小さな箱にクリップ**する。
   7〜9項目中、先頭1〜2個しか描画・クリック可能にならない(実測: 「Select」の座標を
   クリックすると背後の `#msg-messages` がヒットした)。是正: `showContextMenu()` と
   同じ手法(`document.body` に追加し、ビューポート座標で明示配置)に統一。

3件とも既存の833本の緑テストが気づかなかった同じ理由——要素は存在しクリック可能で、
壊れていたのは「どこにも見えない場所で参照が外れている」「見えているが描画範囲外」
という、存在確認だけでは絶対に検出できない種類の欠陥だった。副産物として孤立した
CSSクラス2個・i18nキー1個(`toastUnpinned`)も削除。

**手作業で辿った境界チェックをそのまま恒久ゲート化**(`tools/closure-boundary.mjs`、
validate.sh 42→43項目)。`initMessenger()` の閉じ括弧より後ろで宣言されている名前
(`dbGetAll`/`activeContact`/`openConversation`/`exitSelectMode`)を無防備に参照して
いないかを機械的に検査する。ツール自体の誤検知を3種類作り込みながら修正した
(正規表現リテラル未マスクで`\d`が変数`d`と誤認識/`[^)]*`が外側の呼び出しの開き括弧
まで貪欲マッチ/`if (activeContact) {` がメソッド定義と区別できず制御構文キーワードを
除外)。現行ファイルで0件、直前コミット以前の5つの過去状態全てで正しく検出——
そのうち2状態では、今セッション既に発見・修正済みの `_intervals` バグまで名指しせずに
独立検出した。存在確認だけでは検出できない欠陥を機械が先に見つける、という2-5以降の
路線を実際にゲート化した初めての例。

## 4. この評価の使い方
新しい主張を足すときは、**まずそれを反証するテストを書く**。本セッションで見つかった重大な
欠陥(偽の監査ログ、届かない924言語テーブル、リレーに見えていた送信者、黙って消える
グループ送信、起動中断)は、すべて「主張はあるが検証が無い」箇所から出た。

そして**改善案そのものも検証対象**である。上記2-3の `/group/info` は「内部で閉じられる」と
書いた直後に実装し、**同じトークンで join できる以上まったく効かない**ことが分かって撤回した。
既存テストが13本落ちたことが「範囲が想定より広い=前提を疑え」という合図だった。
**塞ぐ前に、攻撃者がその制御を迂回する最短経路を数えること。**
