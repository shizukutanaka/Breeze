## 1. 長所(実証済みのもののみ)

- **広告ゼロ・トラッキングゼロ・登録ゼロ。** 鍵そのものがIDであり、メールも電話番号も
  Passkeyも要らない。「アカウント作成が面倒」という不満に対する解が *作成という工程の削除* に
  なっている。
- **送信者がリレーから暗号学的に隠れる(Sealed Sender v2)。** 送信者ID・公開鍵・表示名・
  署名鍵・返信プレビュー・マルチデバイス標識を受信者の鍵へ封印(ephemeral X25519 → HKDF
  `breeze-seal-v2` → AES-256-GCM、AADが宛先と時刻を束縛)。初回接触のX3DHヘッダが送信者の
  identity鍵を生バイトで露出していた欠陥も封印済み — **盗聴E2E(`seal.spec.js`)が実バイトを
  検査**して証明している。
- **マルチデバイスが実際に動く。** 受信の両デバイス配送、帰属(副デバイス送信が相手の同じ
  会話に入る)、自己同期(新品のPCが会話ごと復元)、編集・削除の伝播、添付のfan-out —
  すべて `multidevice.spec.js` の5幕で実ブラウザ実証。
- **暗号状態がリロードを生き延びる。** 1:1のDouble Ratchetもグループのsender keyも、
  リロード後に復号・送信が継続する(`lifecycle.spec.js`、本セッションで新規実証)。
- **主張とコードの一致を機械が守る。** ミラードリフト検査(インライン実装 vs 参照実装)、
  CSPハッシュピン留め、死にi18nキー検出、到達不能関数検出 — いずれも**歯があることを
  実証済み**(意図的に壊して BLOCKED を確認してから戻す運用)。
- **「静かなメッセンジャー」の設計。** 返信不要マーク(未読を増やさない)、遅延既読、
  集中モード、端末内だけの重要度判定。LINEが構造的に真似できない差別化(向こうの収益源は
  エンゲージメント)。

## 2. 短所(正直に、原因の所在で分類)

### 2-1. 外部要因で待つもの(こちらで閉じられない)
- **CIが未稼働。** 796+32+39のゲートが自動実行されていない。自動化アカウントに GitHub の
  `workflows` OAuthスコープが無く `.github/workflows/*` をpushできないため。
  手順とワークフロー内容は `docs/CI-SETUP.md` に保全済み。**メンテナが有効化すれば即動く。**
- **ポスト量子(PQXDH)未展開。** ML-KEM のブラウザ実装待ち(~2027)。`src/crypto/pq.js` は
  テスト済みだが未配線。今日の鍵合意は古典的(X25519)。

### 2-2. 意図的な設計上の制限(理由つきで選んだもの)
- **グループ送信はプライマリ端末限定。** 副デバイスを名簿に載せると、メンバー数×端末数の
  肥大とエポックchurnを招く。**黙って捨てず明示的に拒否**し、入力テキストを返す実装。
- **履歴同期なし。** 新しくリンクした端末は空から始まる(Signalと同じ判断)。`/backup` が移行経路。
- **root端末を失うとデバイス管理が不能。** 登記簿の署名者がrootのみ。既存端末のメッセージングは
  継続する。

### 2-3. 残る弱点(内部要因 — 改善余地あり)
- **sealed キューは best-effort。** Cloudflare KV は last-write-wins でトランザクションが無く、
  同時刻・別PoPの書き込みで封筒を失いうる。緩和策は内容キーdedup・再送キュー・溢れの告白
  (`dropped: n`)。**exactly-once ではない。**
- **`/group/info` が招待トークン保持者にロスター開示。** 参加せずともメンバーのID・公開鍵・
  表示名が読める。招待リンクは「その名簿への鍵」と等価に扱う必要がある。
- **失効の伝播が最大5分遅延。** 送信側キャッシュTTLに等しい。
- **バックグラウンドのポーリングが15秒間隔。** 前面なら3秒。PWAを裏に回すと着信が最大15秒遅れる。
- **クラウドバックアップは90日で消える。** 最終アップロードから。期限を返して表示するようにしたが、
  自動延命はしていない。

### 2-4. プロセスの弱点(本セッション最大の学び)
**E2Eが「初回セッション」に偏っていた。** 10本のspecのうちリロードを行うのは3本のみで、
その3本はすべて本セッションで追加したもの。結果、**復帰ユーザー全員でアプリが機能停止する
バグ(TDZによる起動中断 → 連絡先0件・メッセージ受信ゼロ)が29本の緑をすり抜けた**。
テストが緑であることは「テストした範囲が正しい」以上を意味しない。
→ 是正済み(リロード系3本を追加)。今後は**同種の偏りが他にないか**を点検軸とする。

## 4. この評価の使い方
新しい主張を足すときは、**まずそれを反証するテストを書く**。本セッションで見つかった重大な
欠陥(偽の監査ログ、届かない924言語テーブル、リレーに見えていた送信者、黙って消える
グループ送信、起動中断)は、すべて「主張はあるが検証が無い」箇所から出た。
