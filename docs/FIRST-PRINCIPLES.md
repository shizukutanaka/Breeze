# Breeze — 第一原理分解とソクラテス問答

*v3.7 / branch `claude/nice-ride-T6yb0`*

`ASSESSMENT.md` が「何が良く、何が悪いか」を計測値で並べた表であるのに対し、この文書は
**なぜそうなのか**を問答で掘る。結論だけでなく、**問いと反証**を残すことを目的とする。
数値はすべて再現可能(コマンドは各所に明記)。

---

## 第1部 — 第一原理への分解

### 問1「このプロダクトから削れないものは何か?」

機能を全部剥がして、残るものを探す。

- チャットUI → 削れる(CLIでも成立する)
- グループ → 削れる(1:1だけでもメッセンジャー)
- マルチデバイス → 削れる(1台でも成立)
- 通知・既読・リアクション・スタンプ → 全部削れる
- **リレー → 削れない?** ここは保留(問3で扱う)

残ったのは1つだけ:

> **二者が、その二者以外には読めない形でバイトを交換する。**

これが不可分な核である。他は全て**利便性**であり、核と衝突したら核が勝たなければならない。

### 計測: 核はコード全体の何%か

```
crypto core (hkdf 〜 Safety Number): 573 行
index.html 全体:                  13,886 行
→ 核は 4.1%
```

**残り95.9%は利便性である。** これは批判ではなく設計事実だが、重要な帰結を持つ:
*利便性の変更が核の性質を壊していないか*を機械が監視しなければ、95.9%の側から
静かに侵食される。本セッションで実際に起きたのがまさにそれだった(問7)。

### 問2「では核を守るとはどういうことか?」

「暗号が正しい」だけでは足りない。本セッションで見つけた欠陥はどれも暗号の誤りではなかった:

| 欠陥 | 暗号は正しかったか | それでも何が起きたか |
|---|---|---|
| Sealed Sender v1 | ✓ 正しい | 封筒の**外側**に送信者名が平文で載っていた |
| 起動TDZクラッシュ | ✓ 正しい | 復帰ユーザーに**1通も届かない** |
| 副デバイスのグループ送信 | ✓ 正しい | 受信側で**黙って破棄**、UIは「送信済み」 |
| 924言語テーブル | — | `async` 読込に間に合わず**一度も適用されない** |

→ **核を守るとは、核の周りの95.9%が核の約束を破っていないことを検証し続けること。**

### 問3「リレーは本当に必要か?」

P2P(WebRTC DataChannel)があるなら不要では? 反証を挙げる:

- NATトラバーサルは必ず失敗する場合がある(対称NAT同士)
- 相手がオフラインなら P2P は成立しない

→ リレーは**必要**。ただし必要なのは「サービス」ではなく**私書箱**である。
ここから設計上の唯一の問いが決まる:

> **その私書箱は何を学習できるか?**

Sealed Sender v2 はこの問いへの回答であり、v1 が回答になっていなかったことは
盗聴E2E(`seal.spec.js`)が実バイトを検査して証明した。

## 第2部 — マスク流アルゴリズムをプロダクト全体に適用する

### ① 要件を疑う

**疑った要件:「セッション自動リキー(500通/1時間)」** — SPEC.md が「✓実装済み」と主張。
実際は `dhRatchetStep` に文字列を渡して毎回throw、catchで握り潰し、その上で
`auditLog('crypto', 'Session rekeyed')` を書いていた。**一度も起きていないことを断言する
監査記録**。前方秘匿性はKDFチェーンとピア駆動のDHステップで既に確保されており、要件自体が
不要だった → 削除しSPECを正直に訂正。

**疑った要件:「sealed キューは exactly-once であるべき」** — どのメッセンジャーも保証して
いない。必要なのは「損失が稀 **かつ** 回復可能」。教科書的なキー分割は無料枠の最ホットパス
(1ユーザー28,800ポーリング/日)を破壊するため却下し、送信側の読み戻し回復を実装。

**疑った要件:「`/group/info` をメンバー限定にすべき」** — 実装した上で**撤回**。
同じ招待トークンで `join` できる以上、読み取りを塞いでも迂回される(しかも参加すれば
メッセージ受信権つき)。**弱い読み取りを塞いで強い書き込みを開けておく制御は装飾**。

### ② 削除する

| 削除物 | 行数 | 理由 |
|---|---|---|
| 診断コマンド11個 | 582 | ICE候補ダンプ・KVカウンタ・アプリ内チェンジログ。友達に連絡する人は打たない |
| 死にi18nキー | 267 | 翻訳面の31%が何もラベルしていなかった |
| リキー機構一式 | ~40 | 上記の偽監査ログ |
| 死んだリスナー2件 | ~3 | ボタンより長生きしたハンドラ |

**index.html: 14,483 → 13,886行。** 15,000行ゲートの余裕が約500行→1,100行に回復した。
削除こそが次の機能を可能にする。

### ③ 簡素化する

3箇所に複製されていたマルチデバイス fan-out(テキスト/添付/変異シグナル)を1関数に集約。
**この三重化こそが、添付だけfan-outを忘れた原因**だった。

### ④ 加速する

- **製品**: fan-out を並列化(ロックはピア単位なので安全) → N往復が1往復に
- **開発**: テストのPoW難易度を下げ、フルスイート **85秒 → 19.3秒(4.4倍)**
  (本番の難易度20ビットは不変 — 変えたのはテストが払うコスト)

### ⑤ 自動化する

削除しただけでは腐敗は再発する。**検出を自動化した**(validate.sh 38 → 40チェック):

| ゲート | 検出対象 | 歯の実証 |
|---|---|---|
| `csp-hash.mjs` | CSPハッシュの陳腐化 | ✓ |
| `i18n-check` 検査6 | 定義されているが参照されないキー | ✓ 植え込みでBLOCKED |
| `i18n-check` 検査7 | **参照されているが定義されないキー**(生キーが表示される) | ✓ |
| 到達不能関数 | 削除機能の残骸 | ✓ |
| `dead-wiring.mjs` | **存在しないDOM IDへの配線** | ✓ |

## 第3部 — 戦略的トレードオフ(明示的に議論する)

### 問4「このプロダクトの堀は機能か?」

違う。機能はLINEが全て模倣できる。**堀はLINEが構造的に実装できないもの**である:

| 差別化点 | LINEが実装できない理由 |
|---|---|
| 広告ゼロ(実コード確認済み: 一致4件は全てポリシー文と変数名) | 広告が収益源 |
| エンゲージメント最大化をしない設計(返信不要マーク・遅延既読・集中モード) | エンゲージメントが指標 |
| データ収集ゼロ(鍵=ID、登録なし) | データが資産 |

→ **設計判断の試金石:「これはLINEが出荷できるか?」Yesなら差別化ではない。**

### 問5「では最大の弱点は何か?」

技術ではなく**導入経路**である。この製品は「プライバシー最大化」を「導入しやすさ」より
優先する選択を一貫して行っている:

| 選択 | 得たもの | 失ったもの |
|---|---|---|
| ストア配布なし(利用者の明示的指定) | 審査・ストア依存からの自由 | 発見可能性、iOSの通知制約 |
| 鍵=ID、登録なし | 収集するデータが存在しない | **アカウント復旧が原理的に不可能**(バックアップが唯一の保険) |
| 単一ファイル・依存ゼロ | 監査可能、高速、ビルド不要 | 15,000行という物理的な天井 |
| PWA | どこでも動く | バックグラウンド時ポーリング15秒遅延 |

**これらは欠陥ではなく支払った代価である。** 正直に言えば、この製品は
「プライバシーを理解して選ぶ人」には強く、「とりあえず入れてみる人」には弱い。

### 問6「その代価は妥当か?」

利用者が設定した制約(ストア配布なし・スタンプなし)を前提とすれば妥当。ただし**代価は
文書化されなければ詐欺になる** — だから SECURITY.md は root鍵喪失・失効5分遅延・
バックアップ90日期限・招待リンク=参加権を全て明記している。

### 問7「このセッション最大の学びは何か?」

**「テストが緑」は「テストした範囲が正しい」以上を意味しない。**

証拠: **11本**のE2E specのうちリロードを行うのは**3本**のみで、その3本とも本セッションで追加した
(発見当時は10本中3本。以後 `account.spec.js` が加わった)。
つまり発見前のスイートは「初回セッション」しか検証しておらず、**復帰ユーザー全員でアプリが
機能停止するバグが29本の緑をすり抜けた**。

さらに同じ形が2度出た:
- **完成しているのに到達できない機能**(マルチアカウント: 2個目を作る「+」がタブバーの内側、
  タブバーは2個以上で描画 = ブートストラップ・デッドロック)
- **作れないファイルを復元できる**(ローカルバックアップの作成側だけ配線が死んでいた)

→ 個別修正ではなく**クラスごとゲート化**した(第2部⑤)。

### 問8「改善案そのものは検証されているか?」

これが最後の、そして最も見落とされやすい問い。**答えはNoだった**:
`/group/info` のメンバー限定化は「内部で閉じられる改善」と評価して実装したが、
**同じトークンでjoinできる以上まったく効かない**と判明して撤回した。既存テスト13本の失敗が
「範囲が想定より広い=前提を疑え」という合図だった。

> **改善案も主張である。塞ぐ前に、攻撃者がその制御を迂回する最短経路を数えること。**

## 結論

- **核は4.1%、残り95.9%は利便性。** 核を守るとは、95.9%が核の約束を破らないことを
  機械が監視し続けること。
- **堀は機能ではなく、LINEが構造的に選べない設計。** 試金石は「LINEが出荷できるか?」。
- **最大の弱点は技術ではなく導入経路。** それは支払った代価であり、文書化されている限り誠実。
- **最大の学びは、緑のテストは範囲の証明でしかないこと。** だから本セッションは
  バグを直すたびに**そのクラスを検出するゲート**を足した(40チェック)。

この文書自体も主張である。反証は歓迎する — 反証の作り方は
`ASSESSMENT.md` 第4節「この評価の使い方」に書いてある。
