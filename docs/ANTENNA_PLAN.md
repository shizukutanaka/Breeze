# Breeze アンテナ計画（ANTENNA_PLAN）

目的: 利用者自身の端末が P2P の「アンテナ」になる仕組みを設計する（2026-11-14、mi の指示: 利用者がアンテナになる仕組みを考えて、既定中継への依存と費用をさらに下げ、利用者の網そのものが基盤になる方向）。**本書は設計のみであり、実装は本書の報告を受けた後の別判断とする。** 本書の実態記述は全て現行 main（`980cbe07`、P2P_PLAN Step 2 取り込み済み）の実コードで裏を取ったものだけを書く。行番号は漂うため、根拠は関数名・CONFIG キー・ファイル名で示す。

位置づけ: 直接優先（`docs/P2P_PLAN.md` Step 2、PR #427）と使用量の自己負担（`docs/COST_MODEL.md` §10、PR #414）は完了済み。本書はその次段として、「オフラインの相手へ届ける仕事」の一部を、既定中継から利用者の端末へ移す設計である。

## 0. 前提条件

1. **アンテナは上乗せであり、保証は移さない（設計の大原則）**: 配送保証は従来どおりメールボックス預け＋送信側 outbox（永続再送キュー、IDB 保存）が担う。アンテナが封筒を失っても・捨てても・長期オフラインでも、従来経路で届く。アンテナを単一障害点にしないことが、全ステップ共通の絶対条件。
2. **ブラウザ／モバイルの実行制約**: Web 版の端末はタブを閉じれば（モバイルではアプリが背面で落とされれば）WebRTC 接続も保持キューも消える。アンテナは「アプリが開いている端末が、その間だけ担う」役であり、常時接続は前提にできない（第7節「やらないこと」）。
3. **無テレメトリの原則**（P2P_PLAN §0-3 と同一）: アンテナの実績（何件預かり、何件渡せたか）は端末内集計に限る。サーバー集計・ランキングはしない。
4. **行数予算**: index.html は実測 15,237 行（main `980cbe07`）、`validate.sh` の上限 16,000 行。本書のステップは将来の実装判断時に、この予算とモジュール切り出し（`src/app/`）の状況を見て配備形態を決める。本書では配備形態を固定しない。

## 1. 土台: 現行のピア預かりの実態（実測）

「アンテナ」はゼロから作るものではない。現行コードには既に第三者ピア経由の預かり（コメント上は "v3: PEER RELAY — All users relay for each other"）が存在する。本書はこれを正式な仕組みへ格上げする設計である。

| 項目 | 現行の実態 | 根拠 |
|---|---|---|
| 送信側の依頼 | 相手がオフラインで直接送れないとき、**接続中の連絡先ピアのうち最初の1台**に `peer_relay_request`（宛先ID＋暗号文）を DataChannel で送る。相手のホームリレー等への預けとは独立に、常時併用される | `sendMessage` の "Peer relay: try relaying via connected peers" 節 |
| アンテナ側の保持 | メモリ内キュー `_peerRelayQueue`。宛先ごとに**最大20件**、**TTL 1時間**。ペイロードは文字列長 64KB まで（暗号化済み1:1メッセージ ≤32KB 相当の上限として実装） | `handlePeerRelayRequest` |
| 受け渡し | 宛先がオンラインになり DataChannel が開いたら `peer_relay_deliver` で直接渡す。受信側は通常の `handleIncoming` に流すため、復号・重複排除（`_replayCache`＋IndexedDB）は通常経路と同一 | `deliverPeerRelayQueue`、DataChannel のメッセージ分岐 |
| 同意・設定 | **無い**。接続中の連絡先からの依頼は無条件に受理する。利用者が切る手段も、上限を変える手段もない | `handlePeerRelayRequest` に設定参照なし |
| 永続化 | **無い**。タブを閉じれば保持中の封筒は消える（配送保証はメールボックス側にあるため実害にはならない設計） | `_peerRelayQueue` は通常のオブジェクト |
| 費用との関係 | **預けは省略されない**。アンテナ経由で先に届いても、メールボックスへの預けと poll/ack は従来どおり発生する。現行のピア預かりは到達速度の上乗せであり、費用効果はゼロ | `sendMessage`（Step 2 の預け省略は直接 ack の場合のみ） |
| シグナリング補助 | **無い**。新規接続のランデブーはリレーの KV が必須のまま（P2P_PLAN W3） | P2P_PLAN §1.3・§1.5 |

つまり現行は「たまたま開いている連絡先の端末が、揮発的に、少量を預かる」機会的経路であり、(a) 同意と負担のコントロール、(b) 永続化、(c) 費用との接続、の3点が欠けたまま置かれている。本書の設計はこの3点を埋めることに集中し、配送の芯（封筒・重複排除・保証の所在）は変えない。

## 2. 役割の切り分け（設計判断 1）

**決定: アンテナの役割は (a) 封筒の一時預かり（store-and-forward）に限定する。(b) 接続の手助けは担わない。**

| 候補 | 担うか | 理由 |
|---|---|---|
| (a) オフラインの相手への封筒の一時預かり | **担う（本書の主題）** | 既存の土台があり、暗号文しか触らないため信頼を要しない部品にできる。既定中継の預け周期（第6節）の肩代わりが可能 |
| (b-1) シグナリングの置き場（SDP/ICE の交換） | **担わない** | ランデブーの置き場は「相手が探しに来たときに必ず応答できる」ことが要る。開いているときだけ存在する端末は置き場にならない。ランデブーの分散は P2P_PLAN Step 4（SDP の手動交換）が既に担う |
| (b-2) 在席の伝言（「宛先が今オンライン」を第三者経由で知る） | **将来の接続点として留保**（本書では実装計画に含めない） | 費用の支配項（シグナルポーリング、COST_MODEL レバー1）には効く可能性があるが、伝言の鮮度と悪用（偽の在席通知）の設計が別途要る。効果の見積りが立ってから判断する |
| (b-3) 通話メディアの中継（TURN の代替） | **担わない** | 帯域負担が預かりとは桁違い（COST_MODEL §8: 通話の受信は 2.8MB/分）で、モバイル端末の通信量・電池では成立しない。TURN は運営者設定の領分のまま（P2P_PLAN Step 5） |
| ファイルの中継・保持 | **担わない** | 封筒の上限（64KB 文字列）を超えるものは預からない現行規則を維持する。192KB 超のファイルは従来どおり P2P 直送のみ |

## 3. 誰のアンテナになるか（設計判断 2）

**決定: 信頼の輪の内側から段階を広げる。各段階は独立に判断し、前の段階の実測なしに次へ進まない。**

| 段階 | 誰の封筒を預かるか | 信頼の根拠 | 本書での扱い |
|---|---|---|---|
| A. 自分の複数端末 | 自分の他端末宛・自分宛 | 端末レジストリ（署名つき、root＋最大10台）で同一身元と証明できる | Step 1。設計の検証台 |
| B. 連絡先同士 | 自分の連絡先が送る／自分の連絡先宛の封筒 | 接続自体が連絡先関係を前提とする（DataChannel は連絡先同士でしか開かない）。現行の機会的預かりの正式化 | Step 2〜4 |
| C. 希望者の公開アンテナ | 見知らぬ利用者の封筒 | 根拠なし。同意した端末が不特定の宛先の封筒を預かる | Step 5。**別判断として分離**し、本書では「やるなら要る条件」だけを書く（第5.4節） |

段階 C を分離する理由: 段階 A・B では、アンテナから見える相手は全員「自分が知っている誰か」であり、メタ情報の増分が小さい（第5節）。段階 C では見知らぬ宛先の ID・量・時刻が端末に集まるようになり、悪用とプライバシーの性質が変わる。同じ仕組みの延長として扱わない。
