Breeze ரிலேவை இயக்க இரண்டு வழிகள் உள்ளன:

1. **சுய-ஹோஸ்ட் செய்யப்பட்டது (Node + Docker)** — உங்கள் சொந்தக் கணினியில் அல்லது
   VPS-இல் ரிலே: ஒரு கொள்கலன், ஒரு தரவுத் தொகுதி, பதிவு இயல்பாக
   மூடப்பட்டுள்ளது. ரிலே உங்களுக்கும் உங்கள் மக்களுக்கும் என்றால் இங்கிருந்து தொடங்கவும்.
2. **Cloudflare** — Cloudflare-இன் இலவச அடுக்கில் அதிகாரப்பூர்வ பாணியிலான பயன்படுத்தல்
   (Breeze தானே இயக்கும் ரிலே). பராமரிக்க சர்வர் இல்லாமல்
   ஒரு பொது ரிலே வேண்டுமென்றால் அங்கிருந்து தொடங்கவும்.

இரண்டும் ஒரே கையாளுநர் குறியீட்டை இயக்குகின்றன; எப்படியிருந்தாலும் ஒரு ரிலே என்பது ஒரு எளிய,
பரிமாற்றம் செய்யக்கூடிய அஞ்சல் பெட்டி, மேலும் ஒவ்வொரு கிளையண்டும் ஒவ்வொரு
ரிலேவுடனும் வேலை செய்கிறது.

## Docker உடன் சுய-ஹோஸ்ட் செய்யப்பட்டது

```bash
# 1. Get the code
git clone https://github.com/shizukutanaka/Breeze.git && cd Breeze

# 2. Start it, with your own Breeze ID admitted (see "Registration"
#    below for how to find it — you can also start closed-to-everyone
#    and add IDs later)
BREEZE_ALLOWLIST=<your Breeze ID> docker compose up -d

# 3. Watch the first-boot log — it prints your relay identity
#    fingerprint; write it down (see "Relay identity")
docker compose logs breeze
```

ரிலே கொள்கலனுக்குள் போர்ட் 8787-இல் எளிய HTTP-ஐ வழங்குகிறது.
**அதன் முன்னால் ஒரு தலைகீழ் ப்ராக்ஸியில் TLS-ஐ முடிக்கவும்** (Caddy, nginx,
Traefik, ஒரு Cloudflare Tunnel, …): உலாவிகள் ஒரு ரிலேவை
HTTPS/WSS வழியாக மட்டுமே பயன்படுத்தும். நீங்கள் அவ்வாறு செய்யும்போது, `docker-compose.yml`-இல்
`TRUST_PROXY: "true"` என அமைக்கவும், இதனால் வீத வரம்பு உண்மையான கிளையண்ட்
முகவரியை அடிப்படையாகக் கொள்ளும் — மேலும் அத்தகைய ப்ராக்ஸி இல்லாமல் அதை ஒருபோதும் அமைக்க வேண்டாம், ஏனெனில் அது
நம்பும் தலைப்பை நுழைவை நேரடியாக அடையக்கூடிய எவரும் போலியாக உருவாக்க முடியும்.

தரவுத் தொகுதிக்கு எதிராகச் சரியாக **ஒரு** கொள்கலனை இயக்கவும்: வீத
வரம்பிடுபவர் ஒவ்வொரு செயல்முறைக்கும் நினைவகத்தில் உள்ளார், ஒவ்வொரு அஞ்சல் பெட்டியின் செயல்பாடுகளும்
அந்தச் செயல்முறைக்குள் வரிசைப்படுத்தப்பட்டுள்ளன, எனவே இரண்டாவது பிரதி
இந்தப் பண்புகளில் எதையும் கொண்டிருக்காது. ஒரே செயல்முறைக்குப் பெரிய கணினியைக் கொடுத்து அளவை அதிகரிக்கவும்.

### பதிவு: இயல்பாக மூடப்பட்டுள்ளது

இணையத்தில் எவரும் பதிவு செய்யக்கூடிய ஒரு சுய-ஹோஸ்ட் ரிலே,
அதிகாரப்பூர்வ ரிலேவின் வரம்புகள் கட்டுப்படுத்த இருக்கும் ஸ்பேம்/தவறான பயன்பாட்டுப் பொருளாதாரத்தை மீண்டும் உருவாக்கும்,
எனவே **Docker பேக்கேஜிங் மூடிய நிலையில் வருகிறது**: கம்போஸ்
கோப்பு ஒரு `REGISTRATION_ALLOWLIST`-ஐ (ஒருவேளை காலியாக) அனுப்புகிறது, மேலும்
அதில் உள்ள Breeze ID-கள் மட்டுமே *கணக்குகளை உருவாக்க* முடியும் (முதல் ப்ரீகீ
பதிவேற்றம்). பதிவை மூடுவது ஏற்கனவே ரிலேவில் வசிக்கும் மக்களை ஒருபோதும் பாதிக்காது
— அவர்களின் பதிவேற்றங்கள், டெபாசிட்டுகள், சந்திப்புகள் மற்றும் வாக்கெடுப்புகள்
கட்டுப்படுத்தப்படவில்லை — மேலும் பதிவைத் திறப்பது ஒரு வெளிப்படையான தேர்வு, ஒருபோதும்
இயல்புநிலை அல்ல.

- **உங்கள் Breeze ID** என்பது உங்கள் அழைப்பு இணைப்பில் உள்ள 12-எழுத்து அடையாளங்காட்டி
  (அதன் `pub` மதிப்பின் முதல் 12 எழுத்துகள்). நீங்கள் அழைக்கும் ஒவ்வொருவரிடமும் அவர்களுடையதை அதே
  வழியில் கேளுங்கள் — ID என்பது தொடர்புகள் ஏற்கனவே பரிமாறிக்கொள்ளும் ஒரு பொது அடையாளங்காட்டி,
  இரகசியம் அல்ல.
- **மக்களை அனுமதிக்க**, அவர்களின் ID-களைப் பட்டியலிடுங்கள்: உங்கள் ஷெல்லில்
  `BREEZE_ALLOWLIST=id1,id2,…` என அமைக்கவும் அல்லது `docker-compose.yml`-க்கு அருகில் ஒரு `.env` கோப்பில்,
  பின்னர் மீண்டும் `docker compose up -d` செய்யவும்.
- **இப்போது தொடங்கி, பின்னர் அனுமதிக்கவும்**: `BREEZE_ALLOWLIST` அமைக்கப்படாவிட்டால், ரிலே
  அனைவருக்கும் மூடிய நிலையில் இயங்கும் — பூட் பதிவு அதையே கூறுகிறது — மேலும் நீங்கள் ID-களைச் சேர்க்கும் வரை யாரும்
  பதிவு செய்ய முடியாது.
- **திறந்த ரிலே** (எவரும் பதிவு செய்யலாம்): `docker-compose.yml`-இல்
  `REGISTRATION_OPEN: "1"` என்பதன் கருத்துரையை நீக்கவும். நீங்கள் அவ்வாறு செய்தால் தவறான பயன்பாட்டுப் பொருளாதாரம் உங்களுடையது.

### பயன்பாட்டு ஒதுக்கீடு: உங்கள் சொந்த ரிலேவில் அதை அணைக்கவும்

வேலையாள் ஒரு **நியாயமான-பயன்பாட்டுப் பயன்பாட்டு ஒதுக்கீடு** இயக்கப்பட்ட நிலையில் வருகிறார்: ஒவ்வொரு
அஞ்சல் பெட்டிக்கும், அதிகபட்சம் 10,000 டெபாசிட்டுகள்/நாள் மற்றும் 200,000/மாதம் (ஒரு டெபாசிட் என்பது
ஒரு முழு வழங்கல் சுழற்சி — கொள்கை மற்றும் எண்களுக்கு `docs/COST_MODEL.md` §10 ஐப் பார்க்கவும்). அந்தச் சட்டகம் *பகிரப்பட்ட இயல்புநிலை
ரிலேவுக்காக* உள்ளது, இது ஒரு இலவச நுழைவாக இயக்கப்படுகிறது, இதன் மாறுபடும் செலவுகளை
ஆபரேட்டர் இல்லையெனில் அனைவருக்காகவும் ஏற்க வேண்டியிருக்கும். **நீங்கள்
உங்களுக்காகவும் உங்கள் மக்களுக்காகவும் இயக்கும் ஒரு ரிலேவில், அந்தச் சட்டகம் அர்த்தமற்றது — அதை
முடக்கவும்**:

```bash
USAGE_QUOTA_ENABLED=false
```

உங்கள் ரிலே அதன் சூழலைப் படிக்கும் இடத்தில் அதை அமைக்கவும் (ஷெல் அல்லது
`docker-compose.yml`-க்கு அருகில் உள்ள `.env`, Node செயல்முறைச் சூழல்,
அல்லது Cloudflare Pages இரகசியங்கள்). நீங்கள்
ஒரு சமூக ரிலேவை இயக்கி, ஒரு சட்டகத்தை *விரும்பினால்* இரண்டு அருகிலுள்ள குமிழ்கள் உள்ளன:
`USAGE_QUOTA_DAILY` மற்றும் `USAGE_QUOTA_MONTHLY` ஆகியவை வரம்புகளை மீண்டும் சரிசெய்கின்றன.
முக்கியமான குறிப்புகள்:

- அஞ்சல் பெட்டிகள் Durable
  Objects-இல் (`MAILBOX_BACKEND=do`, இந்த ஹோஸ்டில் இயல்புநிலை) வசிக்கும்போது மட்டுமே ஒதுக்கீடு செயல்படுத்தப்படுகிறது; KV
  பின்னணியில் இது ஆவணப்படுத்தப்பட்ட ஒரு செயலற்ற செயல்பாடு.
- வரம்பைத் தாண்டிய பிறகு, அனுப்புநர்களுக்கு அமைதியாகக் கைவிடப்படுவதற்குப் பதிலாக ஒரு வெளிப்படையான `429 USAGE_QUOTA_EXCEEDED`
  (சாளரம் மற்றும் அதன் வரம்புடன்) கிடைக்கும் — செய்தி
  அனுப்புநரின் அனுப்பும் பெட்டியில் தங்கியிருக்கும், மேலும் பெறுநர்
  P2P வழியாகவும் வேறு எந்த வீட்டு ரிலே வழியாகவும் அணுகக்கூடியவராக இருப்பார்.

### ரிலே அடையாளம்

முதல் துவக்கத்தில் ரிலே *தரவுத் தொகுதிக்குள்* ஒரு நிலையான Ed25519 அடையாளச் சாவியை
உருவாக்கி, அதன் கைரேகையைப் பதிவில் அச்சிடுகிறது:

```
relay identity: NEW key generated — fingerprint 3F2A 9C41 …
```

கைரேகை *உங்கள்* ரிலேவை அடையாளம் காட்டுகிறது: அதை உங்கள் பயனர்களுக்கு
பட்டைக்கு வெளியே (நேரில், வேறொரு சேனல் வழியாக) கொடுங்கள், இதனால் அவர்கள் தங்களுக்கு வழங்கப்பட்ட ரிலே
நீங்கள் இயக்குவதுதான் என்பதை அடையாளம் காண முடியும். அதே கைரேகை
ஒவ்வொரு துவக்கத்திலும் அச்சிடப்படும்; அது எப்போதாவது மாறினால், தரவுத் தொகுதி
மாற்றப்பட்டது — பயனர்களிடம் புதியதை நம்பச் சொல்வதற்கு முன் விசாரிக்கவும்.

கிளையண்டுகள் இந்தச் சாவியைத் தானாகவே சரிபார்த்துப் பின் செய்கின்றன (நிலை-2 படி 4): முதல்
தொடர்பில் ஒரு கிளையண்ட் சாவியால் கையொப்பமிட ரிலேவுக்குச் சவால் விடுகிறது
(`/api/relay/attest`), சரிபார்க்கப்பட்ட சாவியைக் கணக்குடன் சேமிக்கிறது, மேலும்
ஒவ்வொரு அடுத்தடுத்த அமர்விலும் மீண்டும் சரிபார்க்கிறது. கிளையண்ட் காட்டும் கைரேகை
(`/security`-க்குக் கீழ், மற்றும் முதல் பின்னில் டோஸ்டில்) அதே
சாவியிலிருந்து பெறப்படுகிறது — அதை மேலே உள்ள பூட்-பதிவு வரியுடன் ஒப்பிடவும். சாவி
எப்போதாவது மாறினால், கிளையண்டுகள் **ரிலேவுடன் பேசுவதை நிறுத்தி** பயனரை
எச்சரிக்கின்றன; அவை ஒருபோதும் அமைதியாக மீண்டும் பின் செய்வதில்லை. கைரேகை மாற்றத்தை ஒரு
முறிவு நிகழ்வாகக் கருதவும்: படி 4-இல் ஆப்பில் "புதிய சாவியை நம்பு" பொத்தான் இல்லை,
எனவே உண்மையான தொகுதி இழப்புக்குப் பிறகு உங்கள் பயனர்கள் தங்கள் கணக்கிற்காக ஆப்பின் சேமிக்கப்பட்ட தரவை
அழித்து, முதல் தொடர்பில் மீண்டும் பின் செய்ய வேண்டும் —
புதிய கைரேகையை முதலில் பட்டைக்கு வெளியே அறிவிக்கவும், இல்லையெனில் அவர்களால் உங்கள் புதிய சாவியைத் தாக்குபவரின் சாவியிலிருந்து
வேறுபடுத்த முடியாது.

### காப்புப்பிரதி & மீட்டமைப்பு

**தரவுத் தொகுதியே முழு ரிலே நிலையாகும்**: கோப்பகம், அஞ்சல் பெட்டிகள்,
மற்றும் ரிலே அடையாளச் சாவியைக் கொண்ட ஒரு SQLite கோப்பு.
காப்புப்பிரதி எடுக்க வேறு எதுவும் இல்லை.

```bash
# Back up: copy the database out of the (stopped) container
docker compose stop
docker cp "$(docker compose ps -aq breeze)":/data/breeze-relay.db ./breeze-relay-backup.db
docker compose start

# Restore: copy the backup back in as /data/breeze-relay.db before
# starting, and the relay serves identically — same fingerprint.
docker compose stop
docker cp ./breeze-relay-backup.db "$(docker compose ps -aq breeze)":/data/breeze-relay.db
docker compose start
```

## வெறும் Node உடன் சுய-ஹோஸ்ட் செய்யப்பட்டது (Docker இல்லை)

```bash
node server/index.js   # Node ≥ 24, no npm dependencies to install
```

உள்ளமைவு சூழல் மாறிகள் மட்டுமே — `server/README.md`
அவை அனைத்தையும் பட்டியலிடுகிறது. Docker பாதையிலிருந்து இரண்டு வேறுபாடுகள்:

- **தரவுக் கோப்பு** இயல்பாக `./breeze-relay.db` (இதை `BREEZE_DB_PATH` மூலம் மாற்றவும்);
  இது ரிலே அடையாளம் உட்பட அதே ஒற்றைக் கோப்பு நிலை.
  அதே வழியில் அதைக் காப்புப்பிரதி எடுக்கவும்: நிறுத்தவும், நகலெடுக்கவும், மறுதொடக்கம் செய்யவும்.
- **நீங்கள் அதை மூடும் வரை பதிவு திறந்திருக்கும்**: மூடிய இயல்புநிலை
  என்பது Docker பேக்கேஜிங்கின் ஒரு பண்பு. ஒரு வெறும் நுழைவை மூட,
  `REGISTRATION_ALLOWLIST=id1,id2` என அமைக்கவும் (அல்லது
  அனைவருக்கும் மூடியதற்கு ஒரு காலி மதிப்பு); `REGISTRATION_OPEN=1` அதை வெளிப்படையாக மீண்டும் திறக்கிறது.

### விருப்ப அம்சங்களைச் சேர்ப்பது

#### புஷ் அறிவிப்புகள் (இலவசம்)

```bash
# Generate VAPID keys
npx web-push generate-vapid-keys

# Set secrets
wrangler pages secret put VAPID_PUBLIC_KEY
wrangler pages secret put VAPID_PRIVATE_KEY
```

#### TURN சர்வர் (கட்டுப்பாடான நெட்வொர்க்குகளுக்கு)

TURN என்பது அழைப்புகளும் ரிலே-மட்டும் (IP-மறைக்கும்) இணைப்புகளும்
கட்டுப்பாடான NAT-களைக் கடக்கும் வழியாகும். உங்கள் ரிலே எந்த TURN-ஐ வழங்குகிறது என்பது ஆபரேட்டராக **உங்கள்** விருப்பம்
— Worker வரிசையில் முயற்சிக்கிறது:

```bash
# Option A: Cloudflare Calls ($0.05/GB, global anycast)
wrangler pages secret put TURN_KEY_ID
wrangler pages secret put TURN_KEY_API_TOKEN

# Option B: your own coturn (HMAC time-limited credentials — the Worker
# mints a 24h username/credential per registered user from the secret)
#   coturn: use-auth-secret, static-auth-secret=<same secret>
wrangler pages secret put TURN_URL      # turn:your-server:3478
wrangler pages secret put TURN_SECRET

# Option C: static credentials (metered.ca, Twilio, …)
wrangler pages secret put TURN_URL
wrangler pages secret put TURN_USERNAME
wrangler pages secret put TURN_CREDENTIAL

# Option D: No config → free Open Relay (20GB/month). This is a third
# party's PUBLIC quota, shared with every unconfigured relay — fine for
# a first run, not a foundation. Opt out explicitly and callers get
# STUN only (some restrictive-NAT calls will then fail, visibly):
wrangler pages secret put TURN_OPENRELAY_FALLBACK   # set to: false
```

**நீங்கள் உண்மையில் என்ன உள்ளமைத்தீர்கள் என்பதைச் சரிபார்க்கவும்:** `GET /api/health` பயனுள்ள
முறையை `turnProvider` என அறிவிக்கிறது (`cloudflare` | `custom` | `static` |
`openrelay` | `none`). பழைய `turn` பூலியன்
`TURN_URL`-ஐ மட்டுமே பிரதிபலிக்கிறது, எனவே இது பரிந்துரைக்கப்பட்ட விருப்பம் A-க்கு `false` எனப் படிக்கிறது — `turnProvider`-ஐப் பயன்படுத்தவும். கிளையண்டுகள் `/security`-இல் அதே வழங்குநரைக் காட்டுகின்றன, எனவே
Open Relay மாற்று வழியில் உள்ள ஒரு பயனர், ஒரு மூன்றாம் தரப்பு தனது
அழைப்பு ஊடகத்தை ரிலே செய்கிறது என்பதைக் காணலாம் (மெட்டாடேட்டா மட்டும் — ஊடகம் தானே DTLS-SRTP மறையாக்கம் செய்யப்பட்டது).

#### அங்கீகார வலுப்படுத்தல் & எளிய ரிலே பாதை

ப்ரீகீ பதிவேற்றங்கள் இப்போது கையொப்ப உரிமையை `prekey-owner:<userId>` இல் **TTL இல்லாமல்** தனியாகப் பாதுகாக்கின்றன. ஏற்கனவே உள்ள தொகுப்பு உரிமை, மாற்றீடு ஏற்றுக்கொள்ளப்படுவதற்கு முன், அடுத்த பதிவேற்றத்தில் சோம்பலாக இடம்பெயர்கிறது. புதிய Ed25519 தொகுப்புகளும் அந்தப் பதிவை நிறுவுகின்றன. காலாவதியான ப்ரீகீ தொகுப்புகளைக் கத்தரிக்கும்போது இந்தப் பதிவுகளை வைத்திருக்கவும்: தொகுப்பு காலாவதிக்காகக் காத்திருப்பது ஒரு புதிய உரிமையாளரை அனுமதிக்கக் கூடாது. சுழற்சிக்கு முந்தைய உரிமையாளரால் கையொப்பமிடப்பட்ட ஒரு பதிவேற்றம் தேவை, இது ஏற்கனவே உள்ள பதிவேற்ற சுருக்கத்தில் புதிய சாவியைப் பிணைக்கிறது. அங்கீகரிக்கப்பட்ட `/account/delete` இரண்டு பதிவுகளையும் அழிக்கிறது, மேலும் தொகுப்பு காலாவதிக்குப் பிறகும் உரிமையாளருக்கு எதிராக அங்கீகரிக்க முடியும். இழந்த-உரிமையாளர்-சாவி மீட்டமைப்பு எதுவும் இல்லை.

இந்தப் பதிவைக் கொண்ட கணக்குகளுக்கு, பதிவேற்றம் மற்றும் செய்தி/சீல் செய்யப்பட்ட வாக்கெடுப்பு, சீல் செய்யப்பட்ட ACK மற்றும் அஞ்சல் பெட்டி WebSocket சான்றுகள் நீடித்த உரிமையாளரைப் பயன்படுத்த வேண்டும். **`PREKEY_REQUIRE_AUTH=false` அல்லது `QUEUE_REQUIRE_AUTH=false` என இருந்தாலும் கையொப்பமிடப்படாத கோரிக்கைகள் நிராகரிக்கப்படுகின்றன.** அந்தக் கொடிகள் உரிமையாளர் இல்லாத கணக்குகளுக்கு அவற்றின் ஏற்கனவே உள்ள இயல்புநிலைகளையும் மரபுவழி அர்த்தங்களையும் தக்கவைத்துக் கொள்கின்றன; கையொப்பமிடப்படாத பதிவேற்றம்/வரிசை கோரிக்கைகளின் வெளிப்படையான `false` ஏற்பு, உள்ளடக்கம் இல்லாத ஒரு நீக்க எச்சரிக்கையைப் பதிவு செய்கிறது. மற்ற அங்கீகாரக் கொடிகள் மாறாமல் உள்ளன. அஞ்சல் பெட்டி WebSocket-களுக்கு இன்னும் அனைவருக்கும் கையொப்பங்கள் தேவை.

கிளையண்ட், திரும்பி வரும் கணக்கின் துவக்கம், தலைவர் பதவி உயர்வு மற்றும் மறு இணைப்பு உட்பட, வரிசைச் செயல்பாட்டிற்கு முன் கையொப்பத் துவக்கத்திற்காகக் காத்திருக்கிறது. பகிரப்பட்ட காத்திருப்பு ஐந்து வினாடிகளில் வரம்பிடப்பட்டுள்ளது. ஆதரிக்கப்படாத இயக்க நேரங்கள் உடனடியாகக் கையொப்பமின்றித் தொடர்கின்றன; சிக்கிய IDB/சாவி-திறத்தல் வரம்புக்குப் பிறகு கையொப்பமின்றித் தொடர்கிறது, பின்னர் தயாரானதும் கையொப்பமிடுகிறது. இது வாக்கெடுப்பு வளையத்தை உயிருடன் வைத்திருக்கிறது, ஒரு புறவழி **அல்ல**: உரிமையாளர் ஆதரவு கொண்ட கணக்குகள், அவற்றின் கையொப்பச் சாவி பயன்படுத்தக்கூடியதாகும் வரை ரிலேவிலிருந்து பெற முடியாது. பழைய தொடக்கப் பந்தயத்தைத் தவிர்க்க Worker உடன் புதுப்பிக்கப்பட்ட கிளையண்ட் சொத்துகளைப் பயன்படுத்தவும்.

அதன் உரிமையாளர் பாதுகாக்கப்படுவதற்கு **முன்பே** காலாவதியான ஒரு தொகுப்பிலிருந்து இடம்பெயர்வால் உரிமையை மீட்க முடியாது. முதல் பதிவு TOFU ஆகவே இருக்கிறது. உரிமைப் பதிவுகள் ஏற்கனவே உள்ள KV பின்னணியைப் பயன்படுத்துகின்றன: இந்த மாற்றத்தால் இறுதி நிலைத்தன்மையும் ஒரே நேர எழுத்துகளும் நேரியல் ஆக்கப்படவில்லை. சான்றுகள் ஏற்கனவே உள்ள ஐந்து நிமிடப் புத்துணர்ச்சி சாளரத்தையும் செயல்பாடு/பேலோடு பிணைப்பையும் தக்கவைத்துக் கொள்கின்றன; சாளரத்திற்குள் ஒரே மாதிரியான மறு முயற்சிகள் ஒரு முறை மட்டுமேயான நான்ஸ் நெறிமுறை அல்ல.

இருப்பு எழுத்துகளுக்கும் TURN நற்சான்றிதழ் வழங்கலுக்கும் இயல்பாகவே ஏற்கனவே ஒரு *பதிவு செய்யப்பட்ட* கணக்கு (ப்ரீகீ தொகுப்பு உள்ளது) தேவை, மேலும் ஒவ்வொரு கிளையண்டும் தானாகவே பதிவு செய்கிறது. இருப்பு இதயத் துடிப்புகள் கூடுதலாக ஒரு Ed25519 உரிமைச் சான்றைக் கொண்டுள்ளன (துடிப்பு அது சேமிக்கும் புலங்களில் கையொப்பமிடுகிறது), இதை Worker ஒன்று வழங்கப்படும்போதெல்லாம் சரிபார்க்கிறது — `PRESENCE_SIGN_REQUIRE_AUTH=true` அந்தச் சான்றைக் கட்டாயமாக்குகிறது. மீதமுள்ள Ed25519-கையொப்பக் கொடிகள் விருப்பத்தேர்வாகவே இருக்கின்றன; `wrangler.toml` ஒவ்வொன்றையும் ஏன் என்பதையும் ஆவணப்படுத்துகிறது (WebCrypto Ed25519 இல்லாத இயக்க நேரங்களில் உள்ள கிளையண்டுகளால் கையொப்பமிடவே முடியாது).

மரபுவழி எளிய ரிலே (`/api/msg/send`, `/api/msg/poll`) நீக்கப்பட்டுள்ளது: அதன் பதில்கள் ஒரு `Deprecation: true` தலைப்பைக் கொண்டுள்ளன, மேலும் சீல் செய்யப்பட்ட பாதையே ஒவ்வொரு தற்போதைய கிளையண்டுக்கும் இயல்புநிலை வழியாகும். எந்த நேரடி கிளையண்டுக்கும் இனி மாற்று வழி தேவையில்லை என்பதை நீங்கள் உறுதிப்படுத்திய பிறகு, அதை முற்றிலும் முடக்கவும்:

```bash
wrangler pages secret put PLAIN_PATH_DISABLED   # set to: true
```

### இலவச அடுக்குக்கு அப்பால் அளவை அதிகரித்தல்

நீங்கள் இலவச அடுக்கைத் தாண்டி வளரும்போது ($5/மாதம் Workers Paid திட்டம்):

| வளம் | கட்டணத் திட்டம் |
|----------|-----------|
| Worker கோரிக்கைகள் | 10 மில்லியன்/மாதம் |
| KV எழுதுதல் | 1 மில்லியன்/மாதம் |
| KV சேமிப்பு | 1 GB சேர்க்கப்பட்டுள்ளது |
| CPU நேரம் | 30 வினாடிகள்/கோரிக்கை |

இது **ஆயிரக்கணக்கான ஒரே நேரப் பயனர்களை** ஆதரிக்கிறது.

### புதுப்பித்தல்

```bash
git pull origin main
wrangler pages deploy . --project-name=breeze
```

கட்டமைப்புப் படி இல்லை. நிறுவச் சார்புகள் இல்லை. வெறுமனே பயன்படுத்தவும்.
