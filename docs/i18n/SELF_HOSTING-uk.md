Є два способи запустити ретранслятор Breeze:

1. **Самостійне розміщення (Node + Docker)** — ретранслятор на вашій
   власній машині або VPS: один контейнер, один том даних, реєстрація
   закрита за замовчуванням. Почніть тут, якщо ретранслятор для вас і
   ваших людей.
2. **Cloudflare** — розгортання в офіційному стилі на безкоштовному
   тарифі Cloudflare (ретранслятор, який запускає сам Breeze). Почніть
   там, якщо хочете публічний ретранслятор без сервера, який треба
   обслуговувати.

Обидва запускають ідентичний код обробника; ретранслятор у будь-якому
разі є тупою, взаємозамінною поштовою скринькою, і кожен клієнт
працює з кожним ретранслятором.

## Самостійне розміщення з Docker

```bash
# 1. Get the code
git clone https://github.com/shizukutanaka/Breeze.git && cd Breeze

# 2. Start it, with your own Breeze ID admitted (see "Registration"
#    below for how to find it — you can also start closed-to-everyone
#    and add IDs later)
BREEZE_ALLOWLIST=<your Breeze ID> docker compose up -d

# 3. Watch the first-boot log — it prints your relay identity
#    fingerprint; write it down (see "Relay identity")
docker compose logs breeze
```

Ретранслятор обслуговує звичайний HTTP на порту 8787 усередині
контейнера. **Завершуйте TLS на зворотному проксі перед ним** (Caddy,
nginx, Traefik, Cloudflare Tunnel, …): браузери використовуватимуть
ретранслятор лише через HTTPS/WSS. Коли зробите це, встановіть
`TRUST_PROXY: "true"` у `docker-compose.yml`, щоб обмеження частоти
спиралося на справжню адресу клієнта, — і ніколи не встановлюйте це
без такого проксі, бо заголовок, якому він довіряє, може підробити
будь-хто, хто може напряму досягти входу.

Запускайте рівно **один** контейнер на том даних: обмежувач частоти
перебуває в пам'яті на процес, а операції кожної поштової скриньки
серіалізуються всередині цього процесу, тому друга репліка не
зберегла б жодної з цих властивостей. Масштабуйтеся, даючи одному
процесу більшу машину.

### Реєстрація: закрита за замовчуванням

Самостійно розміщений ретранслятор, на якому міг би зареєструватися
будь-хто в інтернеті, відтворив би економіку спаму/зловживань, для
контролю якої існують обмеження офіційного ретранслятора, тому **пакет
Docker постачається закритим**: файл compose передає
`REGISTRATION_ALLOWLIST` (можливо, порожній), і лише ID Breeze з нього
можуть *створювати акаунти* (перше завантаження prekey). Закриття
реєстрації ніколи не зачіпає людей, які вже оселилися на
ретрансляторі, — їхні завантаження, депозити, rendezvous та опитування
не обмежуються, — а відкриття реєстрації є явним вибором, ніколи не
значенням за замовчуванням.

- **Ваш ID Breeze** — це 12-символьний ідентифікатор у вашому
  посиланні-запрошенні (перші 12 символів його значення `pub`).
  Запитайте в кожного запрошеного його ID так само — ID є публічним
  ідентифікатором, яким контакти вже обмінюються, а не секретом.
- **Допускайте людей**, перераховуючи їхні ID: встановіть
  `BREEZE_ALLOWLIST=id1,id2,…` у вашій оболонці або у файлі `.env`
  поруч із `docker-compose.yml`, потім знову `docker compose up -d`.
- **Почніть зараз, допускайте пізніше**: без встановленого
  `BREEZE_ALLOWLIST` ретранслятор працює закритим для всіх — журнал
  завантаження каже про це — і ніхто не може зареєструватися, доки ви
  не додасте ID.
- **Відкритий ретранслятор** (зареєструватися може будь-хто):
  розкоментуйте `REGISTRATION_OPEN: "1"` у `docker-compose.yml`. Якщо
  зробите це, економіка зловживань — ваша.

### Квота використання: вимкніть її на власному ретрансляторі

Worker постачається з увімкненою **квотою добросовісного
використання**: на поштову скриньку — не більше 10 000 депозитів на
день і 200 000 на місяць (депозит — це один повний цикл доставлення;
див. `docs/COST_MODEL.md` §10 про політику й числа). Ця рамка існує
для *спільного ретранслятора за замовчуванням*, який працює як
безкоштовний вхід, змінні витрати якого оператору інакше довелося б
нести за всіх. **На ретрансляторі, який ви запускаєте для себе й
своїх людей, рамка безглузда — вимкніть її**:

```bash
USAGE_QUOTA_ENABLED=false
```

Встановіть це там, де ваш ретранслятор читає своє оточення (оболонка
або `.env` поруч із `docker-compose.yml`, оточення процесу Node або
секрети Cloudflare Pages). Існують два сусідні регулятори, якщо ви
запускаєте громадський ретранслятор і *хочете* рамку:
`USAGE_QUOTA_DAILY` і `USAGE_QUOTA_MONTHLY` переналаштовують межі.
Нотатки, які мають значення:

- Квота застосовується, лише коли поштові скриньки живуть у Durable
  Objects (`MAILBOX_BACKEND=do`, значення за замовчуванням на цьому
  хості); на бекенді KV вона є задокументованим no-op.
- За межею відправники отримують явний `429 USAGE_QUOTA_EXCEEDED`
  (з вікном і його межею) замість мовчазного скидання — повідомлення
  залишається у вихідних відправника, а отримувач залишається
  досяжним через P2P і через будь-який інший домашній ретранслятор.

### Ідентичність ретранслятора

Під час першого завантаження ретранслятор генерує постійний ключ
ідентичності Ed25519 *усередині тома даних* і друкує його відбиток у
журналі:

```
relay identity: NEW key generated — fingerprint 3F2A 9C41 …
```

Відбиток ідентифікує *ваш* ретранслятор: передайте його вашим
користувачам зовнішнім каналом (особисто, іншим каналом), щоб вони
могли впізнати ретранслятор, який їм передали, як той, який запускаєте
ви. Той самий відбиток друкується під час кожного завантаження; якщо
він колись зміниться, том даних було замінено — розслідуйте, перш ніж
казати користувачам довіряти новому.

Клієнти перевіряють і закріплюють цей ключ автоматично (етап 2, крок
4): під час першого контакту клієнт пропонує ретранслятору підписати
ключем (`/api/relay/attest`), зберігає перевірений ключ разом з
акаунтом і повторно перевіряє його на кожній наступній сесії.
Відбиток, який показує клієнт (у `/security` і у спливному повідомленні
під час першого закріплення), виводиться з того самого ключа —
порівняйте його з рядком журналу завантаження вище. Якщо ключ колись
зміниться, клієнти **перестануть розмовляти з ретранслятором** і
попередять користувача; вони ніколи не перезакріплюють мовчки.
Ставтеся до зміни відбитка як до ламаючої події: на кроці 4 немає
внутрішньозастосункової кнопки «довіряти новому ключу», тому після
справжньої втрати тома вашим користувачам доведеться очистити збережені
дані застосунку для їхнього акаунта й перезакріпитися під час першого
контакту — оголосіть новий відбиток зовнішнім каналом заздалегідь,
інакше вони не зможуть відрізнити ваш новий ключ від ключа нападника.

### Резервне копіювання та відновлення

**Том даних — це весь стан ретранслятора**: один файл SQLite, що
містить каталог, поштові скриньки та ключ ідентичності ретранслятора.
Більше нічого резервувати.

```bash
# Back up: copy the database out of the (stopped) container
docker compose stop
docker cp "$(docker compose ps -aq breeze)":/data/breeze-relay.db ./breeze-relay-backup.db
docker compose start

# Restore: copy the backup back in as /data/breeze-relay.db before
# starting, and the relay serves identically — same fingerprint.
docker compose stop
docker cp ./breeze-relay-backup.db "$(docker compose ps -aq breeze)":/data/breeze-relay.db
docker compose start
```

### Оновлення

```bash
git pull origin main
docker compose up -d --build
```

Стан живе в томі, а не в образі, тому оновлення ніколи не зачіпає
дані ваших користувачів.

## Самостійне розміщення з голим Node (без Docker)

```bash
node server/index.js   # Node ≥ 24, no npm dependencies to install
```

Конфігурація — лише змінні оточення — `server/README.md` перераховує
їх усі. Дві відмінності від шляху Docker:

- **Файл даних** за замовчуванням — `./breeze-relay.db`
  (перевизначається через `BREEZE_DB_PATH`); це той самий стан в
  одному файлі, включно з ідентичністю ретранслятора. Резервуйте його
  так само: зупиніть, скопіюйте, перезапустіть.
- **Реєстрація відкрита, якщо ви її не закриєте**: закрите значення за
  замовчуванням — властивість пакета Docker. Щоб закрити голий вхід,
  встановіть `REGISTRATION_ALLOWLIST=id1,id2` (або порожнє значення
  для закритого для всіх); `REGISTRATION_OPEN=1` явно відкриває знову.

## Розгортання на Cloudflare

### Мінімальне розгортання ($0/місяць, 5 хвилин)

```bash
# 1. Install Wrangler CLI
npm install -g wrangler

# 2. Login to Cloudflare
wrangler login

# 3. Deploy
wrangler pages deploy . --project-name=breeze

# 4. Create a KV namespace and declare it in wrangler.toml
wrangler kv:namespace create KV
# Copy the new namespace's ID and put it in wrangler.toml, replacing the
# id in the [[kv_namespaces]] section (binding = "KV"). Pages takes its
# bindings from wrangler.toml; a binding set only in the Dashboard is
# NOT applied while a wrangler.toml exists.
# Then deploy again so the binding takes effect:
wrangler pages deploy . --project-name=breeze

# 5. Visit your deployment's URL (https://<your-project>.pages.dev)
```

**Ось і все.** Усі функції працюють, крім push-сповіщень. Зверніть
увагу, що реєстрація під час розгортання на Cloudflare **відкрита**,
якщо ви самі не встановите `REGISTRATION_ALLOWLIST` (див.
`.env.example`); пакет, закритий за замовчуванням, — це шлях Docker
вище.

### Додавання необов'язкових функцій

#### Push-сповіщення (безкоштовно)

```bash
# Generate VAPID keys
npx web-push generate-vapid-keys

# Set secrets
wrangler pages secret put VAPID_PUBLIC_KEY
wrangler pages secret put VAPID_PRIVATE_KEY
```

#### Сервер TURN (для обмежувальних мереж)

TURN — це те, як дзвінки та з'єднання лише через ретранслятор
(приховування IP) перетинають обмежувальні NAT. Який TURN роздає ваш
ретранслятор — це **ваш** вибір як оператора: Worker пробує в такому
порядку:

```bash
# Option A: Cloudflare Calls ($0.05/GB, global anycast)
wrangler pages secret put TURN_KEY_ID
wrangler pages secret put TURN_KEY_API_TOKEN

# Option B: your own coturn (HMAC time-limited credentials — the Worker
# mints a 24h username/credential per registered user from the secret)
#   coturn: use-auth-secret, static-auth-secret=<same secret>
wrangler pages secret put TURN_URL      # turn:your-server:3478
wrangler pages secret put TURN_SECRET

# Option C: static credentials (metered.ca, Twilio, …)
wrangler pages secret put TURN_URL
wrangler pages secret put TURN_USERNAME
wrangler pages secret put TURN_CREDENTIAL

# Option D: No config → free Open Relay (20GB/month). This is a third
# party's PUBLIC quota, shared with every unconfigured relay — fine for
# a first run, not a foundation. Opt out explicitly and callers get
# STUN only (some restrictive-NAT calls will then fail, visibly):
wrangler pages secret put TURN_OPENRELAY_FALLBACK   # set to: false
```

**Перевірте, що ви насправді налаштували:** `GET /api/health`
повідомляє ефективний режим як `turnProvider` (`cloudflare` |
`custom` | `static` | `openrelay` | `none`). Старий булевий `turn`
відображає лише `TURN_URL`, тому для рекомендованого варіанта A він
читається як `false` — використовуйте `turnProvider`. Клієнти
показують того самого провайдера в `/security`, тому користувач на
запасному Open Relay може бачити, що третя сторона ретранслює медіа
його дзвінків (лише метадані — саме медіа зашифровано DTLS-SRTP).

#### Посилення автентифікації та шлях простого ретранслятора

Завантаження prekey тепер зберігають володіння підписом окремо в
`prekey-owner:<userId>` **без TTL**. Наявне володіння бандлами мігрує
ліниво під час наступного завантаження, перш ніж буде прийнято заміну.
Нові бандли Ed25519 також встановлюють цей запис. Зберігайте ці записи
під час очищення прострочених бандлів prekey: очікування завершення
бандла не повинно дозволяти нового власника. Ротація вимагає
завантаження, підписаного попереднім власником, що зв'язує новий ключ
у наявному дайджесті завантаження. Автентифіковане `/account/delete`
стирає обидва записи й може автентифікуватися проти власника навіть
після завершення бандла. Скидання за втрати ключа власника не існує.

Для акаунтів із цим записом завантаження й опитування
повідомлень/sealed, sealed ACK та докази WebSocket поштової скриньки
повинні використовувати стійкого власника. **Непідписані запити
відхиляються навіть за `PREKEY_REQUIRE_AUTH=false` або
`QUEUE_REQUIRE_AUTH=false`.** Ці прапори зберігають свої наявні
значення за замовчуванням і успадковану семантику для акаунтів без
власника; явне прийняття `false` непідписаних запитів
завантаження/черги записує попередження про застарівання без вмісту.
Інші прапори автентифікації без змін. WebSocket поштових скриньок
як і раніше вимагають підписи для всіх.

Клієнт чекає ініціалізації підпису перед активністю в черзі, включно
із завантаженням акаунта, що повертається, підвищенням лідера та
перепідключенням. Спільне очікування обмежене п'ятьма секундами.
Непідтримувані середовища виконання продовжують без підпису негайно;
застряглі IDB/розгортання ключа продовжують без підпису після межі,
потім підписують, коли готові. Це зберігає цикл опитування живим,
**не** є обходом: акаунти з власником не можуть отримувати від
ретранслятора, доки їхній ключ підпису не стане придатним.
Розгортайте оновлені клієнтські ресурси разом із Worker, щоб уникнути
старої гонки під час запуску.

Міграція не може відновити володіння з бандла, який завершився **до**
того, як його власника було збережено. Перша реєстрація залишається
TOFU. Записи володіння використовують наявний бекенд KV: кінцева
узгодженість і конкурентні записи не робляться цією зміною
лінеаризованими. Докази зберігають наявне п'ятихвилинне вікно свіжості
та прив'язку операція/корисне навантаження; ідентичні повтори всередині
вікна не є одноразовим протоколом nonce.

Записи присутності та видача облікових даних TURN уже вимагають
*зареєстрованого* акаунта (наявний бандл prekey) за замовчуванням, і
кожен клієнт реєструється автоматично. Heartbeat присутності додатково
несе доказ володіння Ed25519 (beat підписує поля, які зберігає), який
Worker перевіряє щоразу, коли його подано —
`PRESENCE_SIGN_REQUIRE_AUTH=true` робить цей доказ обов'язковим. Інші
прапори підпису Ed25519 залишаються opt-in; `wrangler.toml`
документує кожен із них і чому (клієнти в середовищах без WebCrypto
Ed25519 взагалі не можуть підписувати).

Застарілий простий ретранслятор (`/api/msg/send`, `/api/msg/poll`)
застарів: його відповіді несуть заголовок `Deprecation: true`, а шлях
sealed є маршрутом за замовчуванням для кожного поточного клієнта.
Щойно ви підтвердили, що жодному живому клієнту більше не потрібен
запасний варіант, вимкніть його повністю:

```bash
wrangler pages secret put PLAIN_PATH_DISABLED   # set to: true
```

### Масштабування за межі безкоштовного тарифу

Коли ви переростете безкоштовний тариф (платний план Workers Paid за
$5/місяць):

| Ресурс | Платний план |
|----------|-----------|
| Запити до Worker | 10 мільйонів/місяць |
| Записи KV | 1 мільйон/місяць |
| Сховище KV | 1 ГБ включено |
| Час CPU | 30 секунд/запит |

Це підтримує **тисячі одночасних користувачів**.
