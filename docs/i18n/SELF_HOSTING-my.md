Breeze အစားထိုးပို့ဆောင်သူ (relay) ကို လည်ပတ်ရန် နည်းလမ်း နှစ်ခု ရှိပါသည်:

1. **ကိုယ်တိုင်လက်ခံဆောင်ရွက်ခြင်း (Node + Docker)** — သင့်ကိုယ်ပိုင် စက် သို့မဟုတ်
   VPS ပေါ်ရှိ အစားထိုးပို့ဆောင်သူ: ကွန်တိန်နာ တစ်ခု၊ ဒေတာ သိုလှောင်ရာ တစ်ခု၊ မှတ်ပုံတင်ခြင်းကို
   မူလအတိုင်း ပိတ်ထားပါသည်။ အစားထိုးပို့ဆောင်သူသည် သင်နှင့် သင့်လူများအတွက် ဖြစ်ပါက ဤနေရာမှ စတင်ပါ။
2. **Cloudflare** — Cloudflare ၏ အခမဲ့အဆင့်ပေါ်တွင် တရားဝင်ပုံစံ တပ်ဆင်ခြင်း
   (Breeze ကိုယ်တိုင် လည်ပတ်နေသည့် အစားထိုးပို့ဆောင်သူ)။ ထိန်းသိမ်းရန် ဆာဗာ မရှိဘဲ
   အများသုံး အစားထိုးပို့ဆောင်သူ လိုချင်ပါက ထိုနေရာမှ စတင်ပါ။

နှစ်ခုစလုံးသည် တူညီသော ကိုင်တွယ်သူ ကုဒ်ကိုပင် လည်ပတ်ပါသည်။ မည်သည့်နည်းနှင့်ဖြစ်စေ အစားထိုးပို့ဆောင်သူသည် ရိုးရှင်းပြီး
အပြန်အလှန် လဲလှယ်နိုင်သော စာတိုက်ပုံးတစ်ခု ဖြစ်ပြီး ကလိုင်းယင့် အားလုံးသည်
အစားထိုးပို့ဆောင်သူ အားလုံးနှင့် အလုပ်လုပ်ပါသည်။

## Docker ဖြင့် ကိုယ်တိုင်လက်ခံဆောင်ရွက်ခြင်း

```bash
# 1. Get the code
git clone https://github.com/shizukutanaka/Breeze.git && cd Breeze

# 2. Start it, with your own Breeze ID admitted (see "Registration"
#    below for how to find it — you can also start closed-to-everyone
#    and add IDs later)
BREEZE_ALLOWLIST=<your Breeze ID> docker compose up -d

# 3. Watch the first-boot log — it prints your relay identity
#    fingerprint; write it down (see "Relay identity")
docker compose logs breeze
```

အစားထိုးပို့ဆောင်သူသည် ကွန်တိန်နာအတွင်း port 8787 ပေါ်တွင် ရိုးရိုး HTTP ဖြင့် ဝန်ဆောင်မှုပေးပါသည်။
**၎င်း၏ ရှေ့တွင် ပြောင်းပြန် ပရောက်ဆီ တစ်ခု၌ TLS ကို အဆုံးသတ်ပါ** (Caddy, nginx,
Traefik, Cloudflare Tunnel, …): ဘရောက်ဇာများသည် အစားထိုးပို့ဆောင်သူကို
HTTPS/WSS မှတစ်ဆင့်သာ အသုံးပြုပါမည်။ ထိုသို့ ပြုလုပ်သည့်အခါ `docker-compose.yml` တွင် `TRUST_PROXY: "true"` ကို သတ်မှတ်ပါ၊ သို့မှသာ နှုန်းကန့်သတ်ခြင်းသည် တကယ့် ကလိုင်းယင့်
လိပ်စာအပေါ် အခြေခံပါမည် — ထို့အပြင် ထိုသို့သော ပရောက်ဆီ မရှိဘဲ ဘယ်သောအခါမှ မသတ်မှတ်ပါနှင့်၊ အကြောင်းမှာ ၎င်း ယုံကြည်သည့် ခေါင်းစီးကို ဝင်ပေါက်သို့ တိုက်ရိုက်ရောက်နိုင်သူ မည်သူမဆို အတုလုပ်နိုင်သောကြောင့် ဖြစ်ပါသည်။

ဒေတာ သိုလှောင်ရာအပေါ် ကွန်တိန်နာ **တစ်ခု** ကိုသာ အတိအကျ လည်ပတ်ပါ: နှုန်း
ကန့်သတ်သူသည် လုပ်ငန်းစဉ် တစ်ခုချင်းစီအတွက် မှတ်ဉာဏ်အတွင်း ရှိပြီး စာတိုက်ပုံး တစ်ခုချင်းစီ၏ လုပ်ဆောင်မှုများကို
ထိုလုပ်ငန်းစဉ်အတွင်း အစဉ်လိုက် စီထားသည့်အတွက် ဒုတိယ မိတ္တူတစ်ခုသည်
ထိုဂုဏ်သတ္တိ နှစ်ခုစလုံးကို မထိန်းသိမ်းနိုင်ပါ။ လုပ်ငန်းစဉ်တစ်ခုတည်းကို ပိုကြီးသော စက်တစ်လုံး ပေးခြင်းဖြင့် အတိုင်းအတာကို ချဲ့ပါ။

### မှတ်ပုံတင်ခြင်း: မူလအတိုင်း ပိတ်ထားပါသည်

အင်တာနက်ပေါ်ရှိ မည်သူမဆို မှတ်ပုံတင်နိုင်သည့် ကိုယ်တိုင်လက်ခံဆောင်ရွက်သော အစားထိုးပို့ဆောင်သူ တစ်ခုသည်
တရားဝင် အစားထိုးပို့ဆောင်သူ၏ ကန့်သတ်ချက်များ ထိန်းချုပ်ရန် တည်ရှိနေသည့် စပမ်း/အလွဲသုံးစားမှု စီးပွားရေးကို ပြန်လည်ဖန်တီးလိမ့်မည် ဖြစ်သည့်အတွက် **Docker ထုပ်ပိုးမှုကို ပိတ်ထားသည့် အခြေအနေဖြင့် ပို့ဆောင်ပါသည်**: compose
ဖိုင်သည် `REGISTRATION_ALLOWLIST` (ဗလာ ဖြစ်နိုင်သည်) ကို ပေးပို့ပြီး
၎င်းအတွင်း စာရင်းပါသည့် Breeze ID များသာ *အကောင့်များ ဖန်တီးနိုင်* ပါသည် (ပထမဆုံး ကြိုတင်သော့
တင်ခြင်း)။ မှတ်ပုံတင်ခြင်းကို ပိတ်ခြင်းသည် အစားထိုးပို့ဆောင်သူပေါ်တွင် နေထိုင်ပြီးသား လူများကို ဘယ်သောအခါမှ မထိခိုက်ပါ — ၎င်းတို့၏ တင်ခြင်းများ၊ အပ်နှံခြင်းများ၊ တွေ့ဆုံခြင်းများနှင့် စစ်ဆေးခြင်းများသည်
ပိတ်ဆို့ခြင်း မခံရပါ — မှတ်ပုံတင်ခြင်းကို ဖွင့်ခြင်းသည် ရှင်းလင်းသော ရွေးချယ်မှုတစ်ခု ဖြစ်ပြီး မည်သည့်အခါမှ
မူလ မဟုတ်ပါ။

- **သင်၏ Breeze ID** မှာ သင့် ဖိတ်ခေါ်လင့်ခ်အတွင်းရှိ အက္ခရာ ၁၂ လုံးပါ အမှတ်အသား ဖြစ်ပါသည်
  (၎င်း၏ `pub` တန်ဖိုး၏ ပထမ အက္ခရာ ၁၂ လုံး)။ သင် ဖိတ်ခေါ်သည့် လူတစ်ဦးချင်းစီကို ၎င်းတို့၏ ID ကို တူညီသောနည်းဖြင့် တောင်းပါ — ID မှာ အဆက်အသွယ်များ မူလကပင် အပြန်အလှန် လဲလှယ်နေသည့် အများသုံး အမှတ်အသား ဖြစ်ပြီး လျှို့ဝှက်ချက် မဟုတ်ပါ။
- ID များကို စာရင်းပြုစုခြင်းဖြင့် **လူများကို ဝင်ခွင့်ပြုပါ**: သင့် shell တွင် သို့မဟုတ် `docker-compose.yml` ၏ ဘေးရှိ `.env` ဖိုင်တွင်
  `BREEZE_ALLOWLIST=id1,id2,…` ကို သတ်မှတ်ပြီး `docker compose up -d` ကို ထပ်မံ လုပ်ဆောင်ပါ။
- **ယခု စတင်ပြီး နောက်မှ ဝင်ခွင့်ပြုပါ**: `BREEZE_ALLOWLIST` ကို မသတ်မှတ်ထားပါက အစားထိုးပို့ဆောင်သူသည်
  အားလုံးအတွက် ပိတ်ထားသည့် အခြေအနေဖြင့် လည်ပတ်ပါသည် — စတင်မှု မှတ်တမ်းက ထိုအကြောင်း ပြောပါသည် — သင် ID များ မထည့်မချင်း မည်သူမှ
  မှတ်ပုံတင်၍ မရပါ။
- **ဖွင့်ထားသော အစားထိုးပို့ဆောင်သူ** (မည်သူမဆို မှတ်ပုံတင်နိုင်သည်): `docker-compose.yml` တွင်
  `REGISTRATION_OPEN: "1"` ကို မှတ်ချက်ဖြုတ်ပါ။ ထိုသို့ ပြုလုပ်ပါက အလွဲသုံးစားမှု စီးပွားရေးကို သင် ပိုင်ဆိုင်ရပါမည်။

### အသုံးပြုမှု ကိုတာ: ကိုယ်ပိုင် အစားထိုးပို့ဆောင်သူတွင် ပိတ်ထားပါ

Worker ကို **တရားမျှတစွာ အသုံးပြုမှု ကိုတာ** ဖွင့်ထားသည့် အခြေအနေဖြင့် ပို့ဆောင်ပါသည်: စာတိုက်ပုံး
တစ်ခုချင်းစီအတွက် တစ်နေ့လျှင် အပ်နှံမှု အများဆုံး ၁၀,၀၀၀ နှင့် တစ်လလျှင် ၂၀၀,၀၀၀ (အပ်နှံမှုတစ်ခုမှာ
ပို့ဆောင်မှု စက်ဝန်း အပြည့်အစုံ တစ်ခု ဖြစ်ပါသည် — မူဝါဒနှင့် ဂဏန်းများအတွက် `docs/COST_MODEL.md` §10 ကို ကြည့်ပါ)။ ထို ဘောင်သည် *မျှဝေထားသည့် မူလ အစားထိုးပို့ဆောင်သူ* အတွက် တည်ရှိပြီး
၎င်းကို အခမဲ့ ဝင်ပေါက်တစ်ခုအဖြစ် လည်ပတ်နေသည့်အတွက် မဟုတ်လျှင် ၎င်း၏ ပြောင်းလဲနိုင်သော ကုန်ကျစရိတ်များကို
လည်ပတ်သူက အားလုံးအတွက် ထမ်းရမည် ဖြစ်ပါသည်။ **သင်ကိုယ်တိုင်နှင့် သင့်လူများအတွက် လည်ပတ်သည့် အစားထိုးပို့ဆောင်သူတွင် ထိုဘောင်သည် အဓိပ္ပာယ်မရှိပါ — ၎င်းကို ပိတ်ထားပါ**:

```bash
USAGE_QUOTA_ENABLED=false
```

၎င်းကို သင့် အစားထိုးပို့ဆောင်သူက ၎င်း၏ ပတ်ဝန်းကျင်ကို ဖတ်သည့် မည်သည့်နေရာတွင်မဆို သတ်မှတ်ပါ (shell သို့မဟုတ်
`docker-compose.yml` ၏ ဘေးရှိ `.env`၊ Node လုပ်ငန်းစဉ် ပတ်ဝန်းကျင်၊
သို့မဟုတ် Cloudflare Pages လျှို့ဝှက်ချက်များ)။ သင်သည် ရပ်ရွာ အစားထိုးပို့ဆောင်သူ တစ်ခုကို လည်ပတ်ပြီး ဘောင်တစ်ခု *လိုချင်* ပါက အနီးအနားရှိ ခလုတ် နှစ်ခု ရှိပါသည်:
`USAGE_QUOTA_DAILY` နှင့် `USAGE_QUOTA_MONTHLY` တို့သည် အကန့်အသတ်များကို ပြန်လည်ညှိပေးပါသည်။
အရေးကြီးသည့် မှတ်စုများ:

- ကိုတာကို စာတိုက်ပုံးများသည် Durable
  Objects အတွင်း ရှိနေသည့်အခါတွင်သာ (`MAILBOX_BACKEND=do`၊ ဤဟို့စ်တွင် မူလ) အတည်ပြုပါသည်။ KV
  နောက်ခံတွင်မူ ၎င်းသည် စာရွက်စာတမ်းဖြင့် မှတ်တမ်းတင်ထားသည့် no-op တစ်ခု ဖြစ်ပါသည်။
- အကန့်အသတ်ကို ကျော်လွန်ပါက ပို့သူများသည် တိတ်တဆိတ် ပစ်ချခံရမည့်အစား ရှင်းလင်းသော `429 USAGE_QUOTA_EXCEEDED`
  (၎င်း၏ အချိန်ကာလနှင့် အကန့်အသတ် ပါဝင်သည်) ကို ရရှိပါသည် — စာသည်
  ပို့သူ၏ အထွက်ပုံးတွင် ကျန်ရှိနေပြီး လက်ခံသူသည်
  P2P မှတစ်ဆင့်ရော အခြား မူလ အစားထိုးပို့ဆောင်သူ မည်သည့်မှတစ်ဆင့်ပါ ဆက်သွယ်၍ ရနေပါသည်။

### အစားထိုးပို့ဆောင်သူ၏ အမှတ်အသား

ပထမဆုံး စတင်မှုတွင် အစားထိုးပို့ဆောင်သူသည် *ဒေတာ သိုလှောင်ရာအတွင်း* တွင် တည်မြဲသော Ed25519 အမှတ်အသား သော့တစ်ခုကို ဖန်တီးပြီး ၎င်း၏ လက်ဗွေရာကို မှတ်တမ်းတွင် ပုံနှိပ်ပါသည်:

```
relay identity: NEW key generated — fingerprint 3F2A 9C41 …
```

လက်ဗွေရာသည် *သင့်* အစားထိုးပို့ဆောင်သူကို ခွဲခြားဖော်ပြပါသည်: ၎င်းကို သင့် အသုံးပြုသူများကို
လမ်းကြောင်းပြင်ပမှ (လူကိုယ်တိုင်၊ အခြား ချန်နယ်တစ်ခုမှတစ်ဆင့်) ပေးပါ၊ သို့မှသာ ၎င်းတို့သည်
သူတို့ကို ပေးအပ်ထားသည့် အစားထိုးပို့ဆောင်သူမှာ သင် လည်ပတ်နေသည့်အရာ ဖြစ်ကြောင်း မှတ်မိနိုင်ပါမည်။ တူညီသော လက်ဗွေရာသည်
စတင်မှုတိုင်းတွင် ပုံနှိပ်ပါသည်။ ၎င်းသည် ဘယ်သောအခါမဆို ပြောင်းလဲသွားပါက ဒေတာ သိုလှောင်ရာကို
အစားထိုးလိုက်ခြင်း ဖြစ်ပါသည် — အသစ်ကို ယုံကြည်ရန် အသုံးပြုသူများကို မပြောမီ စုံစမ်းစစ်ဆေးပါ။

ကလိုင်းယင့်များသည် ဤသော့ကို အလိုအလျောက် စစ်ဆေးပြီး ပင်တွယ်ထားပါသည် (အဆင့်-၂ အဆင့် ၄): ပထမဆုံး
ဆက်သွယ်မှုတွင် ကလိုင်းယင့်တစ်ခုသည် အစားထိုးပို့ဆောင်သူကို ထိုသော့ဖြင့် လက်မှတ်ထိုးရန် စိန်ခေါ်ပြီး
(`/api/relay/attest`)၊ စစ်ဆေးထားသည့် သော့ကို အကောင့်နှင့်အတူ သိမ်းဆည်းပြီး
နောက်ပိုင်း session တိုင်းတွင် ပြန်လည်စစ်ဆေးပါသည်။ ကလိုင်းယင့် ပြသသည့် လက်ဗွေရာ
(`/security` အောက်တွင်၊ ပထမဆုံး ပင်တွယ်မှုတွင် toast တွင်) သည်
တူညီသော သော့မှပင် ဆင်းသက်လာပါသည် — ၎င်းကို အထက်ပါ စတင်မှု မှတ်တမ်း စာကြောင်းနှင့် နှိုင်းယှဉ်ပါ။ သော့သည်
ဘယ်သောအခါမဆို ပြောင်းလဲသွားပါက ကလိုင်းယင့်များသည် **အစားထိုးပို့ဆောင်သူနှင့် စကားပြောခြင်းကို ရပ်တန့်ပြီး** အသုံးပြုသူကို သတိပေးပါသည်။ ၎င်းတို့သည် တိတ်တဆိတ် ပြန်လည်ပင်တွယ်ခြင်း ဘယ်သောအခါမှ မလုပ်ပါ။ လက်ဗွေရာ ပြောင်းလဲမှုကို
ပြတ်တောက်စေသည့် ဖြစ်ရပ်တစ်ခုအဖြစ် သဘောထားပါ: အဆင့် ၄ တွင် အက်ပ်အတွင်း "သော့အသစ်ကို ယုံကြည်ရန်" ခလုတ် မရှိသည့်အတွက် စစ်မှန်သော သိုလှောင်ရာ ဆုံးရှုံးမှုတစ်ခု ဖြစ်ပွားပြီးနောက် သင့် အသုံးပြုသူများသည်
၎င်းတို့ အကောင့်အတွက် အက်ပ်၏ သိမ်းဆည်းထားသည့် ဒေတာကို ရှင်းလင်းပြီး ပထမဆုံး ဆက်သွယ်မှုတွင် ပြန်လည်ပင်တွယ်ရပါမည် —
လက်ဗွေရာအသစ်ကို လမ်းကြောင်းပြင်ပမှ ဦးစွာ ကြေညာပါ၊ မဟုတ်လျှင် ၎င်းတို့သည်
သင့် သော့အသစ်နှင့် တိုက်ခိုက်သူ၏ သော့ကို ခွဲခြား၍ မရနိုင်ပါ။

### အရန်သိမ်းဆည်းခြင်းနှင့် ပြန်လည်ရယူခြင်း

**ဒေတာ သိုလှောင်ရာသည် အစားထိုးပို့ဆောင်သူ၏ အခြေအနေ တစ်ခုလုံး ဖြစ်ပါသည်**: လမ်းညွှန်စာအုပ်၊ စာတိုက်ပုံးများနှင့် အစားထိုးပို့ဆောင်သူ၏ အမှတ်အသား သော့ကို ကိုင်ဆောင်ထားသည့် SQLite ဖိုင် တစ်ခုတည်း ဖြစ်ပါသည်။
အရန်သိမ်းဆည်းရန် အခြားအရာ မရှိပါ။

```bash
# Back up: copy the database out of the (stopped) container
docker compose stop
docker cp "$(docker compose ps -aq breeze)":/data/breeze-relay.db ./breeze-relay-backup.db
docker compose start

# Restore: copy the backup back in as /data/breeze-relay.db before
# starting, and the relay serves identically — same fingerprint.
docker compose stop
docker cp ./breeze-relay-backup.db "$(docker compose ps -aq breeze)":/data/breeze-relay.db
docker compose start
```

### အပ်ဒိတ်လုပ်ခြင်း

```bash
git pull origin main
docker compose up -d --build
```

အခြေအနေသည် ရုပ်ပုံတွင်မဟုတ်ဘဲ သိုလှောင်ရာတွင် နေထိုင်သည့်အတွက် အပ်ဒိတ်လုပ်ခြင်းသည်
သင့် အသုံးပြုသူများ၏ ဒေတာကို ဘယ်သောအခါမှ မထိပါ။

## Node သက်သက်ဖြင့် ကိုယ်တိုင်လက်ခံဆောင်ရွက်ခြင်း (Docker မပါဘဲ)

```bash
node server/index.js   # Node ≥ 24, no npm dependencies to install
```

ပြင်ဆင်သတ်မှတ်ခြင်းသည် ပတ်ဝန်းကျင် ကိန်းရှင်များသာ ဖြစ်ပါသည် — `server/README.md`
တွင် အားလုံးကို စာရင်းပြုစုထားပါသည်။ Docker လမ်းကြောင်းနှင့် ကွာခြားချက် နှစ်ခု:

- **ဒေတာဖိုင်** ၏ မူလမှာ `./breeze-relay.db` ဖြစ်ပါသည် ( `BREEZE_DB_PATH` ဖြင့် အစားထိုးနိုင်သည်)။ ၎င်းသည် အစားထိုးပို့ဆောင်သူ အမှတ်အသား အပါအဝင် တူညီသော ဖိုင်တစ်ခုတည်း အခြေအနေ ဖြစ်ပါသည်။ တူညီသောနည်းဖြင့် အရန်သိမ်းဆည်းပါ: ရပ်တန့်ပါ၊ ကူးယူပါ၊ ပြန်စပါ။
- **သင် ပိတ်မထားပါက မှတ်ပုံတင်ခြင်း ဖွင့်ထားပါသည်**: ပိတ်ထားသည့် မူလသည်
  Docker ထုပ်ပိုးမှု၏ ဂုဏ်သတ္တိ ဖြစ်ပါသည်။ ရိုးရိုး ဝင်ပေါက်တစ်ခုကို ပိတ်ရန်
  `REGISTRATION_ALLOWLIST=id1,id2` ကို သတ်မှတ်ပါ (သို့မဟုတ် အားလုံးအတွက် ပိတ်ထားရန် ဗလာတန်ဖိုး)။ `REGISTRATION_OPEN=1` သည် ရှင်းလင်းစွာ ပြန်ဖွင့်ပါသည်။

## Cloudflare တပ်ဆင်ခြင်း

### အနည်းဆုံး တပ်ဆင်ခြင်း (တစ်လလျှင် $0၊ ၅ မိနစ်)

```bash
# 1. Install Wrangler CLI
npm install -g wrangler

# 2. Login to Cloudflare
wrangler login

# 3. Deploy
wrangler pages deploy . --project-name=breeze

# 4. Create a KV namespace and declare it in wrangler.toml
wrangler kv:namespace create KV
# Copy the new namespace's ID and put it in wrangler.toml, replacing the
# id in the [[kv_namespaces]] section (binding = "KV"). Pages takes its
# bindings from wrangler.toml; a binding set only in the Dashboard is
# NOT applied while a wrangler.toml exists.
# Then deploy again so the binding takes effect:
wrangler pages deploy . --project-name=breeze

# 5. Visit your deployment's URL (https://<your-project>.pages.dev)
```

**ဒါပါပဲ။** တွန်းအား အကြောင်းကြားချက်များမှလွဲ၍ လုပ်ဆောင်ချက်အားလုံး အလုပ်လုပ်ပါသည်။ မှတ်ချက်
Cloudflare တပ်ဆင်မှုတစ်ခုတွင် မှတ်ပုံတင်ခြင်းသည် သင်ကိုယ်တိုင် `REGISTRATION_ALLOWLIST` ကို မသတ်မှတ်ထားပါက **ဖွင့်ထားပါသည်** (`.env.example` ကို ကြည့်ပါ)။ မူလအတိုင်း ပိတ်ထားသည့် ထုပ်ပိုးမှုမှာ အထက်ပါ Docker လမ်းကြောင်း ဖြစ်ပါသည်။

### ရွေးချယ်နိုင်သော လုပ်ဆောင်ချက်များ ထည့်ခြင်း

#### တွန်းအား အကြောင်းကြားချက်များ (အခမဲ့)

```bash
# Generate VAPID keys
npx web-push generate-vapid-keys

# Set secrets
wrangler pages secret put VAPID_PUBLIC_KEY
wrangler pages secret put VAPID_PRIVATE_KEY
```

#### TURN ဆာဗာ (ကန့်သတ်ထားသော ကွန်ရက်များအတွက်)

TURN သည် ခေါ်ဆိုမှုများနှင့် အစားထိုးပို့ဆောင်သူသက်သက် (IP ဖုံးကွယ်ထားသော) ချိတ်ဆက်မှုများ ကန့်သတ်ထားသော NAT များကို ဖြတ်ကျော်နည်း ဖြစ်ပါသည်။ သင့် အစားထိုးပို့ဆောင်သူက မည်သည့် TURN ကို ပေးအပ်သည်ဆိုသည်မှာ လည်ပတ်သူအဖြစ် **သင့်** ရွေးချယ်မှု ဖြစ်ပါသည် — Worker သည် အစဉ်လိုက် ကြိုးစားပါသည်:

```bash
# Option A: Cloudflare Calls ($0.05/GB, global anycast)
wrangler pages secret put TURN_KEY_ID
wrangler pages secret put TURN_KEY_API_TOKEN

# Option B: your own coturn (HMAC time-limited credentials — the Worker
# mints a 24h username/credential per registered user from the secret)
#   coturn: use-auth-secret, static-auth-secret=<same secret>
wrangler pages secret put TURN_URL      # turn:your-server:3478
wrangler pages secret put TURN_SECRET

# Option C: static credentials (metered.ca, Twilio, …)
wrangler pages secret put TURN_URL
wrangler pages secret put TURN_USERNAME
wrangler pages secret put TURN_CREDENTIAL

# Option D: No config → free Open Relay (20GB/month). This is a third
# party's PUBLIC quota, shared with every unconfigured relay — fine for
# a first run, not a foundation. Opt out explicitly and callers get
# STUN only (some restrictive-NAT calls will then fail, visibly):
wrangler pages secret put TURN_OPENRELAY_FALLBACK   # set to: false
```

**သင် အမှန်တကယ် ပြင်ဆင်သတ်မှတ်ထားသည့်အရာကို စစ်ဆေးပါ:** `GET /api/health` သည် ထိရောက်သော ပုံစံကို `turnProvider` အဖြစ် အစီရင်ခံပါသည် (`cloudflare` | `custom` | `static` | `openrelay` | `none`)။ ယခင် `turn` boolean သည် `TURN_URL` ကိုသာ ထင်ဟပ်သည့်အတွက် အကြံပြုထားသည့် Option A အတွက် `false` ဟု ဖတ်ရပါသည် — `turnProvider` ကို အသုံးပြုပါ။ ကလိုင်းယင့်များသည် တူညီသော ပေးသွင်းသူကို `/security` တွင် ပြသသည့်အတွက် Open Relay အရန်ပေါ်ရှိ အသုံးပြုသူတစ်ဦးသည် တတိယပါတီတစ်ခုက ၎င်းတို့၏ ခေါ်ဆိုမှု မီဒီယာကို အစားထိုးပို့ဆောင်နေကြောင်း မြင်နိုင်ပါသည် (metadata သာ — မီဒီယာ ကိုယ်နှိုက်ကို DTLS-SRTP ဖြင့် ကုဒ်ဝှက်ထားပါသည်)။

#### စစ်မှန်ကြောင်း အတည်ပြုခြင်း ခိုင်မာစေခြင်းနှင့် ရိုးရိုး အစားထိုးပို့ဆောင်မှု လမ်းကြောင်း

ကြိုတင်သော့ တင်ခြင်းများသည် ယခုအခါ လက်မှတ်ထိုးခြင်း ပိုင်ဆိုင်မှုကို `prekey-owner:<userId>` တွင် **TTL မရှိဘဲ** သီးခြား ထိန်းသိမ်းထားပါသည်။ ရှိပြီးသား bundle ပိုင်ဆိုင်မှုသည် အစားထိုးတစ်ခုကို လက်မခံမီ နောက်တစ်ကြိမ် တင်ခြင်းတွင် ပျင်းရိစွာ ရွှေ့ပြောင်းပါသည်။ Ed25519 bundle အသစ်များသည်လည်း ထိုမှတ်တမ်းကို တည်ထောင်ပါသည်။ သက်တမ်းကုန်သွားသည့် ကြိုတင်သော့ bundle များကို ဖြတ်တောက်သည့်အခါ ဤမှတ်တမ်းများကို ထိန်းသိမ်းထားပါ: bundle သက်တမ်းကုန်ခြင်းကို စောင့်ဆိုင်းခြင်းသည် ပိုင်ရှင်အသစ်ကို ခွင့်မပြုသင့်ပါ။ အလှည့်ကျပြောင်းခြင်းသည် ယခင် ပိုင်ရှင်က လက်မှတ်ထိုးထားသည့် တင်ခြင်းတစ်ခု လိုအပ်ပြီး သော့အသစ်ကို ရှိပြီးသား တင်ခြင်း digest အတွင်း ချိတ်ဆက်ပါသည်။ စစ်မှန်ကြောင်း အတည်ပြုထားသည့် `/account/delete` သည် မှတ်တမ်း နှစ်ခုစလုံးကို ဖျက်ပြီး bundle သက်တမ်းကုန်ပြီးနောက်တွင်ပင် ပိုင်ရှင်နှင့် စစ်မှန်ကြောင်း အတည်ပြုနိုင်ပါသည်။ ဆုံးရှုံးသွားသည့် ပိုင်ရှင်သော့ကို ပြန်လည်သတ်မှတ်ခြင်း မရှိပါ။

ဤမှတ်တမ်း ရှိသည့် အကောင့်များအတွက် တင်ခြင်းနှင့် စာ/sealed စစ်ဆေးခြင်း၊ sealed ACK နှင့် စာတိုက်ပုံး WebSocket သက်သေများသည် တည်မြဲသော ပိုင်ရှင်ကို အသုံးပြုရပါမည်။ **လက်မှတ်မပါသည့် တောင်းဆိုမှုများကို `PREKEY_REQUIRE_AUTH=false` သို့မဟုတ် `QUEUE_REQUIRE_AUTH=false` ဖြင့်ပင် ငြင်းပယ်ပါသည်။** ထို အလံများသည် ပိုင်ရှင် မရှိသည့် အကောင့်များအတွက် ၎င်းတို့၏ ရှိပြီးသား မူလများနှင့် အမွေဆက် သဘောတရားများကို ထိန်းသိမ်းထားပါသည်။ လက်မှတ်မပါသည့် တင်ခြင်း/တန်းစီခြင်း တောင်းဆိုမှုများကို ရှင်းလင်းသော `false` လက်ခံခြင်းသည် အကြောင်းအရာ မပါသည့် ရှေးကျခြင်း သတိပေးချက်ကို မှတ်တမ်းတင်ပါသည်။ အခြား စစ်မှန်ကြောင်း အတည်ပြုခြင်း အလံများ မပြောင်းလဲပါ။ စာတိုက်ပုံး WebSocket များသည် အားလုံးအတွက် လက်မှတ်များ လိုအပ်နေဆဲ ဖြစ်ပါသည်။

ကလိုင်းယင့်သည် ပြန်လာသည့် အကောင့် စတင်ခြင်း၊ ခေါင်းဆောင် ရာထူးတိုးခြင်းနှင့် ပြန်လည်ချိတ်ဆက်ခြင်း အပါအဝင် တန်းစီခြင်း လုပ်ဆောင်မှု မတိုင်မီ လက်မှတ်ထိုးခြင်း စတင်မှုကို စောင့်ဆိုင်းပါသည်။ မျှဝေထားသည့် စောင့်ဆိုင်းမှုကို စက္ကန့် ငါးစက္ကန့်တွင် ကန့်သတ်ထားပါသည်။ မထောက်ပံ့သည့် runtime များသည် လက်မှတ်မပါဘဲ ချက်ချင်း ဆက်လုပ်ပါသည်။ ပိတ်နေသည့် IDB/သော့ဖြုတ်ခြင်းသည် ကန့်သတ်ချက်ပြီးနောက် လက်မှတ်မပါဘဲ ဆက်လုပ်ပြီး အဆင်သင့်ဖြစ်သည့်အခါ လက်မှတ်ထိုးပါသည်။ ဤသည်မှာ စစ်ဆေးခြင်း ကွင်းဆက်ကို အသက်ရှင်စေပြီး ရှောင်ကွင်းလမ်း **မဟုတ်ပါ**: ပိုင်ရှင် ကျောထောက်နောက်ခံ ရှိသည့် အကောင့်များသည် ၎င်းတို့၏ လက်မှတ်ထိုးသော့ အသုံးပြုနိုင်သည်အထိ အစားထိုးပို့ဆောင်သူထံမှ လက်ခံ၍ မရပါ။ စတင်မှု အပြိုင်အဆိုင် အဟောင်းကို ရှောင်ရှားရန် အပ်ဒိတ်လုပ်ထားသည့် ကလိုင်းယင့် ပိုင်ဆိုင်မှုများကို Worker နှင့်အတူ တပ်ဆင်ပါ။

ရွှေ့ပြောင်းခြင်းသည် ပိုင်ရှင်ကို မထိန်းသိမ်းမီ **သက်တမ်းကုန်သွားသည့်** bundle တစ်ခုမှ ပိုင်ဆိုင်မှုကို ပြန်လည်ရယူ၍ မရပါ။ ပထမဆုံး မှတ်ပုံတင်ခြင်းသည် TOFU အတိုင်း ကျန်ရှိပါသည်။ ပိုင်ဆိုင်မှု မှတ်တမ်းများသည် ရှိပြီးသား KV နောက်ခံကို အသုံးပြုပါသည်: နောက်ဆုံးတွင် ကိုက်ညီမှုနှင့် တစ်ပြိုင်နက် ရေးသားမှုများကို ဤပြောင်းလဲမှုဖြင့် linear ဖြစ်အောင် မလုပ်ပါ။ သက်သေများသည် ရှိပြီးသား ငါးမိနစ် လတ်ဆတ်မှု အချိန်ကာလနှင့် လုပ်ဆောင်မှု/payload ချိတ်ဆက်မှုကို ထိန်းသိမ်းထားပါသည်။ အချိန်ကာလအတွင်း တူညီသော ပြန်လည်ကြိုးစားမှုများသည် တစ်ကြိမ်သုံး nonce ပရိုတိုကော မဟုတ်ပါ။

ရှိနေမှု ရေးသားမှုများနှင့် TURN အထောက်အထား ထုတ်ပေးမှုများသည် မူလအတိုင်းပင် *မှတ်ပုံတင်ထားသည့်* အကောင့် (ကြိုတင်သော့ bundle ရှိနေခြင်း) ကို လိုအပ်နေပြီး ကလိုင်းယင့်တိုင်းသည် အလိုအလျောက် မှတ်ပုံတင်ပါသည်။ ရှိနေမှု နှလုံးခုန်သံများသည် Ed25519 ပိုင်ဆိုင်မှု သက်သေ တစ်ခုကိုလည်း သယ်ဆောင်ပါသည် (နှလုံးခုန်သံသည် ၎င်း သိမ်းဆည်းသည့် အကွက်များကို လက်မှတ်ထိုးပါသည်)၊ ၎င်းကို တင်ပြသည့်အခါတိုင်း Worker က စစ်ဆေးပါသည် — `PRESENCE_SIGN_REQUIRE_AUTH=true` သည် ထိုသက်သေကို မဖြစ်မနေ လိုအပ်စေပါသည်။ ကျန်ရှိသည့် Ed25519-လက်မှတ် အလံများသည် ရွေးချယ်ပါဝင်နိုင်သည့် အတိုင်း ကျန်ရှိပါသည်။ `wrangler.toml` သည် တစ်ခုချင်းစီနှင့် အကြောင်းရင်းကို မှတ်တမ်းတင်ထားပါသည် (WebCrypto Ed25519 မရှိသည့် runtime များပေါ်ရှိ ကလိုင်းယင့်များသည် လုံးဝ လက်မှတ်မထိုးနိုင်ပါ)။

အမွေဆက် ရိုးရိုး အစားထိုးပို့ဆောင်မှု (`/api/msg/send`, `/api/msg/poll`) ကို ရှေးကျအောင် လုပ်ထားပါသည်: ၎င်း၏ တုံ့ပြန်မှုများတွင် `Deprecation: true` ခေါင်းစီး ပါရှိပြီး sealed လမ်းကြောင်းသည် လက်ရှိ ကလိုင်းယင့်တိုင်းအတွက် မူလ လမ်းကြောင်း ဖြစ်ပါသည်။ အသက်ရှင်နေသည့် ကလိုင်းယင့် တစ်ခုမှ အရန်ကို မလိုအပ်တော့ကြောင်း သင် အတည်ပြုပြီးသည်နှင့် ၎င်းကို လုံးဝ ပိတ်ထားပါ:

```bash
wrangler pages secret put PLAIN_PATH_DISABLED   # set to: true
```

### အခမဲ့အဆင့်ထက် ကျော်လွန်၍ အတိုင်းအတာ ချဲ့ခြင်း

အခမဲ့အဆင့်ကို ကျော်လွန်သွားသည့်အခါ (တစ်လလျှင် $5 Workers Paid အစီအစဉ်):

| အရင်းအမြစ် | ငွေပေးရသည့် အစီအစဉ် |
|----------|-----------|
| Worker တောင်းဆိုမှုများ | တစ်လလျှင် ၁၀ သန်း |
| KV ရေးခြင်းများ | တစ်လလျှင် ၁ သန်း |
| KV သိမ်းဆည်းခြင်း | 1 GB ပါဝင်သည် |
| CPU အချိန် | တောင်းဆိုမှုတစ်ခုလျှင် စက္ကန့် ၃၀ |

ဤသည်မှာ **တစ်ပြိုင်နက် အသုံးပြုသူ ထောင်ပေါင်းများစွာကို** ထောက်ပံ့ပါသည်။

### အပ်ဒိတ်လုပ်ခြင်း

```bash
git pull origin main
wrangler pages deploy . --project-name=breeze
```

တည်ဆောက်ခြင်း အဆင့် မရှိပါ။ ထည့်သွင်းရန် မှီခိုမှုများ မရှိပါ။ တပ်ဆင်ရုံသာ ဖြစ်ပါသည်။
