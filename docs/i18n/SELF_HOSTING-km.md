មានវិធីពីរយ៉ាងដើម្បីដំណើរការឧបករណ៍បញ្ជូនបន្ត (relay) របស់ Breeze៖

1. **ដំឡើងលើម៉ាស៊ីនផ្ទាល់ខ្លួន (Node + Docker)** — ឧបករណ៍បញ្ជូនបន្តនៅលើម៉ាស៊ីនផ្ទាល់ខ្លួនរបស់អ្នក ឬ
   VPS៖ កុងតឺន័រមួយ វ៉ុលល្យូមទិន្នន័យមួយ ការចុះឈ្មោះត្រូវបានបិទតាម
   លំនាំដើម។ ចាប់ផ្តើមនៅទីនេះ ប្រសិនបើឧបករណ៍បញ្ជូនបន្តគឺសម្រាប់អ្នក និងមនុស្សរបស់អ្នក។
2. **Cloudflare** — ការដាក់ឱ្យប្រើប្រាស់តាមរចនាប័ទ្មផ្លូវការនៅលើកម្រិត
   ឥតគិតថ្លៃរបស់ Cloudflare (ឧបករណ៍បញ្ជូនបន្តដែល Breeze ខ្លួនឯងដំណើរការ)។ ចាប់ផ្តើមនៅទីនោះ ប្រសិនបើអ្នកចង់បាន
   ឧបករណ៍បញ្ជូនបន្តសាធារណៈដោយគ្មានម៉ាស៊ីនមេត្រូវថែទាំ។

ទាំងពីរដំណើរការកូដដោះស្រាយដូចគ្នា។ ឧបករណ៍បញ្ជូនបន្តគឺជាប្រអប់សំបុត្រដ៏សាមញ្ញមួយ
ដែលអាចជំនួសគ្នាបានតាមវិធីណាក៏ដោយ ហើយកម្មវិធីអតិថិជនទាំងអស់ដំណើរការជាមួយ
ឧបករណ៍បញ្ជូនបន្តទាំងអស់។

## ដំឡើងលើម៉ាស៊ីនផ្ទាល់ខ្លួនជាមួយ Docker

```bash
# 1. Get the code
git clone https://github.com/shizukutanaka/Breeze.git && cd Breeze

# 2. Start it, with your own Breeze ID admitted (see "Registration"
#    below for how to find it — you can also start closed-to-everyone
#    and add IDs later)
BREEZE_ALLOWLIST=<your Breeze ID> docker compose up -d

# 3. Watch the first-boot log — it prints your relay identity
#    fingerprint; write it down (see "Relay identity")
docker compose logs breeze
```

ឧបករណ៍បញ្ជូនបន្តបម្រើ HTTP ធម្មតានៅលើច្រក 8787 នៅខាងក្នុងកុងតឺន័រ។
**បញ្ចប់ TLS នៅប្រូកស៊ីបញ្ច្រាសនៅពីមុខវា** (Caddy, nginx,
Traefik, Cloudflare Tunnel, …)៖ កម្មវិធីរុករកនឹងប្រើឧបករណ៍បញ្ជូនបន្ត
តែតាមរយៈ HTTPS/WSS ប៉ុណ្ណោះ។ នៅពេលអ្នកធ្វើដូច្នេះ សូមកំណត់ `TRUST_PROXY: "true"` នៅក្នុង
`docker-compose.yml` ដើម្បីឱ្យការកំណត់អត្រាផ្អែកលើអាសយដ្ឋានអតិថិជន
ពិតប្រាកដ — ហើយកុំកំណត់វាដោយគ្មានប្រូកស៊ីបែបនោះឡើយ ពីព្រោះក្បាលទំព័រ
ដែលវាទុកចិត្តអាចត្រូវបានក្លែងបន្លំដោយនរណាម្នាក់ដែលអាចទៅដល់ច្រកចូលដោយផ្ទាល់។

ដំណើរការ **មួយ** កុងតឺន័រយ៉ាងពិតប្រាកដទល់នឹងវ៉ុលល្យូមទិន្នន័យ៖ ឧបករណ៍កំណត់
អត្រាស្ថិតនៅក្នុងអង្គចងចាំក្នុងមួយដំណើរការ ហើយប្រតិបត្តិការរបស់ប្រអប់សំបុត្រនីមួយៗ
ត្រូវបានរៀបជាជួរនៅខាងក្នុងដំណើរការនោះ ដូច្នេះច្បាប់ចម្លងទីពីរនឹងមិនរក្សា
លក្ខណសម្បត្តិទាំងពីរនោះទេ។ ពង្រីកទំហំដោយផ្តល់ឱ្យដំណើរការតែមួយនោះនូវម៉ាស៊ីនធំជាង។

### ការចុះឈ្មោះ៖ បិទតាមលំនាំដើម

ឧបករណ៍បញ្ជូនបន្តដែលដំឡើងលើម៉ាស៊ីនផ្ទាល់ខ្លួន ដែលនរណាម្នាក់នៅលើអ៊ីនធឺណិតអាចចុះឈ្មោះបាន
នឹងបង្កើតឡើងវិញនូវសេដ្ឋកិច្ចសារឥតបានការ/ការរំលោភបំពាន ដែលដែនកំណត់របស់ឧបករណ៍បញ្ជូនបន្តផ្លូវការមានដើម្បី
គ្រប់គ្រង ដូច្នេះ **ការវេចខ្ចប់ Docker ត្រូវបានដឹកជញ្ជូនក្នុងស្ថានភាពបិទ**៖ ឯកសារ
compose បញ្ជូន `REGISTRATION_ALLOWLIST` (អាចទទេ) ហើយ

លើកដំបូង)។ ការបិទការចុះឈ្មោះមិនដែលប៉ះពាល់ដល់មនុស្សដែលបានតាំងលំនៅនៅលើ
ឧបករណ៍បញ្ជូនបន្តរួចហើយទេ — ការបញ្ចូល ការដាក់ប្រាក់ ការណាត់ជួប និងការស្ទង់មើលរបស់ពួកគេមិន
ត្រូវបានរារាំងទេ — ហើយការបើកការចុះឈ្មោះគឺជាជម្រើសច្បាស់លាស់ មិនដែលជា
លំនាំដើមទេ។

- **Breeze ID របស់អ្នក** គឺជាអត្តសញ្ញាណ ១២ តួអក្សរនៅក្នុងតំណភ្ជាប់អញ្ជើញ
  របស់អ្នក (១២ តួអក្សរដំបូងនៃតម្លៃ `pub` របស់វា)។ សូមសុំពីមនុស្សម្នាក់ៗ
  ដែលអ្នកអញ្ជើញនូវ ID របស់ពួកគេតាមវិធីដូចគ្នា — ID គឺជាអត្តសញ្ញាណសាធារណៈ
  ដែលទំនាក់ទំនងផ្លាស់ប្តូរគ្នារួចហើយ មិនមែនជាអាថ៌កំបាំងទេ។
- **អនុញ្ញាតមនុស្ស** ដោយរាយ ID របស់ពួកគេ៖ កំណត់
  `BREEZE_ALLOWLIST=id1,id2,…` នៅក្នុងសែលរបស់អ្នក ឬឯកសារ `.env` នៅជាប់
  `docker-compose.yml` បន្ទាប់មកដំណើរការ `docker compose up -d` ម្តងទៀត។
- **ចាប់ផ្តើមឥឡូវនេះ អនុញ្ញាតនៅពេលក្រោយ**៖ ដោយមិនបានកំណត់ `BREEZE_ALLOWLIST` ឧបករណ៍បញ្ជូនបន្ត
  ដំណើរការក្នុងស្ថានភាពបិទចំពោះមនុស្សគ្រប់គ្នា — កំណត់ហេតុចាប់ផ្តើមនិយាយដូច្នេះ — ហើយគ្មាននរណា
  អាចចុះឈ្មោះបានទេ រហូតដល់អ្នកបន្ថែម ID។
- **ឧបករណ៍បញ្ជូនបន្តបើកចំហ** (នរណាក៏អាចចុះឈ្មោះបាន)៖ ដកការអធិប្បាយចេញពី
  `REGISTRATION_OPEN: "1"` នៅក្នុង `docker-compose.yml`។ អ្នកជាម្ចាស់នៃ
  សេដ្ឋកិច្ចនៃការរំលោភបំពាន ប្រសិនបើអ្នកធ្វើដូច្នេះ។

បោះពុម្ពនៅរាល់ការចាប់ផ្តើម។ ប្រសិនបើវាផ្លាស់ប្តូរ វ៉ុលល្យូមទិន្នន័យត្រូវបាន
ជំនួស — សូមស៊ើបអង្កេតមុនពេលប្រាប់អ្នកប្រើប្រាស់ឱ្យទុកចិត្តអាថ្មី។

### ការបម្រុងទុក និងការស្តារឡើងវិញ

**វ៉ុលល្យូមទិន្នន័យគឺជាស្ថានភាពទាំងមូលរបស់ឧបករណ៍បញ្ជូនបន្ត**៖ ឯកសារ SQLite មួយ
ដែលកាន់កាប់បញ្ជីឈ្មោះ ប្រអប់សំបុត្រ និងសោអត្តសញ្ញាណរបស់ឧបករណ៍បញ្ជូនបន្ត។
គ្មានអ្វីផ្សេងទៀតដែលត្រូវបម្រុងទុកទេ។

```bash
# Back up: copy the database out of the (stopped) container
docker compose stop
docker cp "$(docker compose ps -aq breeze)":/data/breeze-relay.db ./breeze-relay-backup.db
docker compose start

# Restore: copy the backup back in as /data/breeze-relay.db before
# starting, and the relay serves identically — same fingerprint.
docker compose stop
docker cp ./breeze-relay-backup.db "$(docker compose ps -aq breeze)":/data/breeze-relay.db
docker compose start
```

## ការដាក់ឱ្យប្រើប្រាស់ Cloudflare

### ការដាក់ឱ្យប្រើប្រាស់អប្បបរមា ($0/ខែ ៥ នាទី)

```bash
# 1. Install Wrangler CLI
npm install -g wrangler

# 2. Login to Cloudflare
wrangler login

# 3. Deploy
wrangler pages deploy . --project-name=breeze

# 4. Create a KV namespace and declare it in wrangler.toml
wrangler kv:namespace create KV
# Copy the new namespace's ID and put it in wrangler.toml, replacing the
# id in the [[kv_namespaces]] section (binding = "KV"). Pages takes its
# bindings from wrangler.toml; a binding set only in the Dashboard is
# NOT applied while a wrangler.toml exists.
# Then deploy again so the binding takes effect:
wrangler pages deploy . --project-name=breeze

# 5. Visit https://breeze.pages.dev
```

**នោះហើយ។** មុខងារទាំងអស់ដំណើរការ លើកលែងតែការជូនដំណឹងរុញ។ សូមកត់សម្គាល់
ថាការចុះឈ្មោះនៅលើការដាក់ឱ្យប្រើប្រាស់ Cloudflare គឺ **បើកចំហ** លុះត្រាតែអ្នក
កំណត់ `REGISTRATION_ALLOWLIST` ដោយខ្លួនឯង (សូមមើល `.env.example`)។ ការវេចខ្ចប់

#### ម៉ាស៊ីនមេ TURN (សម្រាប់បណ្តាញដែលមានការរឹតបន្តឹង)

TURN គឺជាវិធីដែលការហៅ និងការតភ្ជាប់តាមរយៈឧបករណ៍បញ្ជូនបន្តតែប៉ុណ្ណោះ (លាក់ IP) ឆ្លងកាត់
NAT ដែលមានការរឹតបន្តឹង។ តើឧបករណ៍បញ្ជូនបន្តរបស់អ្នកផ្តល់ TURN ណាគឺជាជម្រើសរបស់ **អ្នក**
ក្នុងនាមជាអ្នកប្រតិបត្តិការ — Worker សាកល្បងតាមលំដាប់៖

```bash
# Option A: Cloudflare Calls ($0.05/GB, global anycast)
wrangler pages secret put TURN_KEY_ID
wrangler pages secret put TURN_KEY_API_TOKEN

# Option B: your own coturn (HMAC time-limited credentials — the Worker
# mints a 24h username/credential per registered user from the secret)
#   coturn: use-auth-secret, static-auth-secret=<same secret>
wrangler pages secret put TURN_URL      # turn:your-server:3478
wrangler pages secret put TURN_SECRET

# Option C: static credentials (metered.ca, Twilio, …)
wrangler pages secret put TURN_URL
wrangler pages secret put TURN_USERNAME
wrangler pages secret put TURN_CREDENTIAL

# Option D: No config → free Open Relay (20GB/month). This is a third
# party's PUBLIC quota, shared with every unconfigured relay — fine for
# a first run, not a foundation. Opt out explicitly and callers get
# STUN only (some restrictive-NAT calls will then fail, visibly):
wrangler pages secret put TURN_OPENRELAY_FALLBACK   # set to: false
```

**ផ្ទៀងផ្ទាត់អ្វីដែលអ្នកពិតជាបានកំណត់រចនាសម្ព័ន្ធ៖** `GET /api/health` រាយការណ៍
របៀបដែលមានប្រសិទ្ធភាពជា `turnProvider` (`cloudflare` | `custom` | `static` |
`openrelay` | `none`)។ ប៊ូលីន `turn` ចាស់ជាងនេះឆ្លុះបញ្ចាំងតែ
`TURN_URL` ប៉ុណ្ណោះ ដូច្នេះវាអានថា `false` សម្រាប់ជម្រើស A ដែលបានណែនាំ — សូមប្រើ
`turnProvider`។ កម្មវិធីអតិថិជនបង្ហាញអ្នកផ្តល់ដូចគ្នានៅក្នុង `/security` ដូច្នេះ
អ្នកប្រើប្រាស់នៅលើជម្រើសបម្រុង Open Relay អាចឃើញថាភាគីទីបីបញ្ជូនបន្ត
មេឌៀការហៅរបស់ពួកគេ (តែទិន្នន័យមេតាប៉ុណ្ណោះ — មេឌៀខ្លួនឯងត្រូវបានអ៊ីនគ្រីបដោយ DTLS-SRTP)។

#### ការពង្រឹងការផ្ទៀងផ្ទាត់ភាពត្រឹមត្រូវ និងផ្លូវបញ្ជូនបន្តធម្មតាចាស់

ការបញ្ចូលសោជាមុនឥឡូវនេះរក្សាភាពជាម្ចាស់នៃការចុះហត្ថលេខាដាច់ដោយឡែកនៅ
`prekey-owner:<userId>` **ដោយគ្មាន TTL**។ ភាពជាម្ចាស់បណ្តុំដែលមានស្រាប់ផ្លាស់ទីដោយខ្ជិល
នៅការបញ្ចូលបន្ទាប់ មុនពេលការជំនួសត្រូវបានទទួលយក។ បណ្តុំ Ed25519 ថ្មីក៏
បង្កើតកំណត់ត្រានោះផងដែរ។ រក្សាកំណត់ត្រាទាំងនេះនៅពេលកាត់បន្ថយបណ្តុំសោជាមុនដែលផុតកំណត់៖
ការរង់ចាំការបណ្តុំផុតកំណត់មិនត្រូវអនុញ្ញាតឱ្យមានម្ចាស់ថ្មីទេ។ ការបង្វិលត្រូវការ
ការបញ្ចូលដែលបានចុះហត្ថលេខាដោយម្ចាស់មុន ដោយភ្ជាប់សោថ្មីចូលទៅក្នុង digest បញ្ចូល
ដែលមានស្រាប់។ `/account/delete` ដែលបានផ្ទៀងផ្ទាត់ភាពត្រឹមត្រូវលុបកំណត់ត្រាទាំងពីរ ហើយអាចផ្ទៀងផ្ទាត់ភាពត្រឹមត្រូវ
ជាមួយម្ចាស់បានសូម្បីតែបន្ទាប់ពីបណ្តុំផុតកំណត់ក៏ដោយ។ គ្មានការកំណត់សោម្ចាស់ដែលបាត់បង់ឡើងវិញទេ។

សម្រាប់គណនីដែលមានកំណត់ត្រានេះ ការបញ្ចូល និងការស្ទង់មើលសារ/sealed, sealed ACK និង
ភស្តុតាង WebSocket ប្រអប់សំបុត្រត្រូវតែប្រើម្ចាស់ដែលជាប់លាប់។ **សំណើដែលគ្មានហត្ថលេខា
ត្រូវបានបដិសេធ សូម្បីតែជាមួយ `PREKEY_REQUIRE_AUTH=false` ឬ `QUEUE_REQUIRE_AUTH=false` ក៏ដោយ។**
ទង់ទាំងនោះរក្សាតម្លៃលំនាំដើមដែលមានស្រាប់ និងអត្ថន័យចាស់របស់ពួកវាសម្រាប់គណនី
ដែលគ្មានម្ចាស់។ ការទទួលយក `false` យ៉ាងច្បាស់លាស់សម្រាប់សំណើបញ្ចូល/តម្រង់ជួរដែលគ្មានហត្ថលេខា
កត់ត្រាការព្រមានអំពីការបញ្ឈប់ប្រើប្រាស់ដែលគ្មានខ្លឹមសារ។ ទង់ផ្ទៀងផ្ទាត់ភាពត្រឹមត្រូវផ្សេងទៀតមិនផ្លាស់ប្តូរទេ។
WebSocket ប្រអប់សំបុត្រនៅតែត្រូវការហត្ថលេខាសម្រាប់មនុស្សគ្រប់គ្នា។

កម្មវិធីអតិថិជនរង់ចាំការចាប់ផ្តើមការចុះហត្ថលេខាមុនសកម្មភាពតម្រង់ជួរ រួមទាំង

ត្រូវបានកំណត់ត្រឹមប្រាំវិនាទី។ បរិស្ថានដំណើរការដែលមិនគាំទ្របន្តដោយគ្មានហត្ថលេខាភ្លាមៗ។
IDB/ការស្រាយសោដែលជាប់គាំងបន្តដោយគ្មានហត្ថលេខាបន្ទាប់ពីដែនកំណត់ បន្ទាប់មកចុះហត្ថលេខានៅពេលរួចរាល់។
នេះរក្សារង្វង់ស្ទង់មើលឱ្យនៅមានជីវិត **មិនមែនជា** ផ្លូវវាងទេ៖ គណនីដែលមានម្ចាស់គាំទ្រមិនអាច
ទទួលពីឧបករណ៍បញ្ជូនបន្តបានទេ រហូតដល់សោចុះហត្ថលេខារបស់ពួកគេអាចប្រើបាន។ ដាក់ឱ្យប្រើប្រាស់ទ្រព្យសកម្មកម្មវិធីអតិថិជនដែលបានធ្វើបច្ចុប្បន្នភាព

ការផ្លាស់ទីមិនអាចស្តារភាពជាម្ចាស់ពីបណ្តុំដែលបានផុតកំណត់ **មុនពេល**
ម្ចាស់របស់វាត្រូវបានរក្សាទុកទេ។ ការចុះឈ្មោះលើកដំបូងនៅតែជា TOFU។ កំណត់ត្រាភាពជាម្ចាស់ប្រើ
