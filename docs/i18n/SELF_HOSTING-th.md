มีสองวิธีในการรันเซิร์ฟเวอร์ส่งต่อ (relay) ของ Breeze:

1. **โฮสต์ด้วยตัวเอง (Node + Docker)** — เซิร์ฟเวอร์ส่งต่อบนเครื่องของคุณเองหรือ
   VPS: หนึ่งคอนเทนเนอร์ หนึ่งโวลุ่มข้อมูล การลงทะเบียนปิดอยู่ตาม
   ค่าเริ่มต้น เริ่มที่นี่หากเซิร์ฟเวอร์ส่งต่อมีไว้สำหรับคุณและคนของคุณ
2. **Cloudflare** — การติดตั้งแบบทางการบนระดับ
   ฟรีของ Cloudflare (เซิร์ฟเวอร์ส่งต่อที่ Breeze เองเป็นผู้รัน) เริ่มที่นั่นหากคุณต้องการ
   เซิร์ฟเวอร์ส่งต่อสาธารณะโดยไม่มีเซิร์ฟเวอร์ที่ต้องดูแล

ทั้งสองวิธีรันโค้ดตัวจัดการเดียวกัน เซิร์ฟเวอร์ส่งต่อเป็นกล่องจดหมายที่เรียบง่าย
ใช้แทนกันได้ไม่ว่าจะแบบใด และไคลเอนต์ทุกตัวทำงานร่วมกับ
เซิร์ฟเวอร์ส่งต่อทุกตัว

## โฮสต์ด้วยตัวเองด้วย Docker

```bash
# 1. Get the code
git clone https://github.com/shizukutanaka/Breeze.git && cd Breeze

# 2. Start it, with your own Breeze ID admitted (see "Registration"
#    below for how to find it — you can also start closed-to-everyone
#    and add IDs later)
BREEZE_ALLOWLIST=<your Breeze ID> docker compose up -d

# 3. Watch the first-boot log — it prints your relay identity
#    fingerprint; write it down (see "Relay identity")
docker compose logs breeze
```

เซิร์ฟเวอร์ส่งต่อให้บริการ HTTP ธรรมดาบนพอร์ต 8787 ภายในคอนเทนเนอร์
**ให้สิ้นสุด TLS ที่พร็อกซีย้อนกลับด้านหน้าของมัน** (Caddy, nginx,
Traefik, Cloudflare Tunnel, …): เบราว์เซอร์จะใช้เซิร์ฟเวอร์ส่งต่อ
ผ่าน HTTPS/WSS เท่านั้น เมื่อทำเช่นนั้น ให้ตั้ง `TRUST_PROXY: "true"` ใน
`docker-compose.yml` เพื่อให้การจำกัดอัตราผูกกับที่อยู่ไคลเอนต์
จริง — และอย่าตั้งค่านี้โดยไม่มีพร็อกซีดังกล่าว เพราะส่วนหัว
ที่มันเชื่อถือสามารถปลอมแปลงได้โดยใครก็ตามที่เข้าถึงทางเข้าได้โดยตรง

ให้รัน **หนึ่ง** คอนเทนเนอร์เท่านั้นต่อโวลุ่มข้อมูล: ตัวจำกัด
อัตราอยู่ในหน่วยความจำต่อกระบวนการ และการดำเนินการของกล่องจดหมายแต่ละกล่อง
ถูกจัดลำดับภายในกระบวนการนั้น ดังนั้นสำเนาที่สองจะไม่รักษา
คุณสมบัติทั้งสองนั้น ขยายขนาดโดยให้กระบวนการเดียวนั้นใช้เครื่องที่ใหญ่กว่า

### การลงทะเบียน: ปิดอยู่ตามค่าเริ่มต้น

เซิร์ฟเวอร์ส่งต่อแบบโฮสต์เองที่ใครก็ตามบนอินเทอร์เน็ตสามารถลงทะเบียนได้
จะสร้างระบบเศรษฐกิจของสแปม/การละเมิดขึ้นมาอีกครั้ง ซึ่งขีดจำกัดของเซิร์ฟเวอร์ส่งต่อทางการมีไว้
เพื่อควบคุม ดังนั้น **แพ็กเกจ Docker ถูกจัดส่งมาในสภาพปิด**: ไฟล์
compose ส่ง `REGISTRATION_ALLOWLIST` (อาจว่างเปล่า) และ
เฉพาะ ID ของ Breeze ที่อยู่ในรายการเท่านั้นที่สามารถ *สร้างบัญชี* ได้ (การอัปโหลดกุญแจล่วงหน้า
ครั้งแรก) การปิดการลงทะเบียนไม่เคยส่งผลกระทบต่อผู้ที่ประจำอยู่บน
เซิร์ฟเวอร์ส่งต่อแล้ว — การอัปโหลด การฝาก การนัดพบ และการสำรวจของพวกเขาไม่
ถูกปิดกั้น — และการเปิดการลงทะเบียนเป็นทางเลือกที่ชัดเจน ไม่เคยเป็น
ค่าเริ่มต้น

- **ID ของ Breeze ของคุณ** คือตัวระบุ 12 อักขระในลิงก์คำเชิญ
  ของคุณ (12 อักขระแรกของค่า `pub` ของมัน) ขอ ID ของแต่ละคน
  ที่คุณเชิญด้วยวิธีเดียวกัน — ID เป็นตัวระบุสาธารณะ
  ที่ผู้ติดต่อแลกเปลี่ยนกันอยู่แล้ว ไม่ใช่ความลับ
- **อนุญาตผู้คน** โดยระบุ ID ของพวกเขา: ตั้งค่า
  `BREEZE_ALLOWLIST=id1,id2,…` ในเชลล์ของคุณหรือไฟล์ `.env` ข้าง ๆ
  `docker-compose.yml` จากนั้นรัน `docker compose up -d` อีกครั้ง
- **เริ่มตอนนี้ อนุญาตภายหลัง**: หากไม่ได้ตั้งค่า `BREEZE_ALLOWLIST` เซิร์ฟเวอร์
  ส่งต่อจะทำงานในสภาพปิดสำหรับทุกคน — บันทึกการบูตระบุเช่นนั้น — และไม่มีใคร
  สามารถลงทะเบียนได้จนกว่าคุณจะเพิ่ม ID
- **เซิร์ฟเวอร์ส่งต่อแบบเปิด** (ใครก็ลงทะเบียนได้): ยกเลิกการคอมเมนต์
  `REGISTRATION_OPEN: "1"` ใน `docker-compose.yml` คุณเป็นเจ้าของ
  ระบบเศรษฐกิจของการละเมิดหากคุณทำเช่นนั้น

### โควตาการใช้งาน: ปิดมันบนเซิร์ฟเวอร์ส่งต่อของคุณเอง

Worker ถูกจัดส่งมาพร้อมกับ **โควตาการใช้งานอย่างเป็นธรรม** ที่เปิดใช้งาน: ต่อ
กล่องจดหมาย สูงสุด 10,000 การฝากต่อวัน และ 200,000 ครั้งต่อเดือน (การฝากหนึ่งครั้งคือ
วงจรการส่งมอบเต็มรูปแบบหนึ่งรอบ — ดู `docs/COST_MODEL.md` §10 สำหรับ
นโยบายและตัวเลข) กรอบนั้นมีไว้สำหรับ *เซิร์ฟเวอร์ส่งต่อเริ่มต้นที่ใช้ร่วมกัน*
ซึ่งดำเนินการเป็นทางเข้าฟรีที่ต้นทุนผันแปรของมัน
ผู้ให้บริการจะต้องแบกรับแทนทุกคนหากไม่มีกรอบนี้ **บนเซิร์ฟเวอร์ส่งต่อที่คุณรัน
สำหรับตัวเองและคนของคุณ กรอบนั้นไม่มีความหมาย — ปิดใช้งาน
มัน**:

```bash
USAGE_QUOTA_ENABLED=false
```

ตั้งค่ามันไว้ที่ใดก็ตามที่เซิร์ฟเวอร์ส่งต่อของคุณอ่านสภาพแวดล้อมของมัน (เชลล์หรือ
`.env` ข้าง ๆ `docker-compose.yml` สภาพแวดล้อมของกระบวนการ Node
หรือความลับของ Cloudflare Pages) มีปุ่มปรับใกล้เคียงอีกสองปุ่มหากคุณ
รันเซิร์ฟเวอร์ส่งต่อสำหรับชุมชนและ *ต้องการ* กรอบ:
`USAGE_QUOTA_DAILY` และ `USAGE_QUOTA_MONTHLY` ปรับขีดจำกัดใหม่
หมายเหตุที่สำคัญ:

- โควตาจะถูกบังคับใช้เฉพาะเมื่อกล่องจดหมายอยู่ใน Durable
  Objects (`MAILBOX_BACKEND=do` ซึ่งเป็นค่าเริ่มต้นบนโฮสต์นี้) บน
  แบ็กเอนด์ KV มันเป็น no-op ที่มีการบันทึกไว้
- เมื่อเกินขีดจำกัด ผู้ส่งจะได้รับ `429 USAGE_QUOTA_EXCEEDED` อย่างชัดเจน
  (พร้อมช่วงเวลาและขีดจำกัดของมัน) แทนที่จะถูกทิ้งอย่างเงียบ ๆ — ข้อความ
  ยังคงอยู่ในกล่องขาออกของผู้ส่ง และผู้รับยังคง
  ติดต่อได้ผ่าน P2P และผ่านเซิร์ฟเวอร์ส่งต่อประจำบ้านตัวอื่นใด

### ตัวตนของเซิร์ฟเวอร์ส่งต่อ

ในการบูตครั้งแรก เซิร์ฟเวอร์ส่งต่อจะสร้างกุญแจตัวตน Ed25519 ที่คงอยู่
*ภายในโวลุ่มข้อมูล* และพิมพ์ลายนิ้วมือของมันลงในบันทึก:

```
relay identity: NEW key generated — fingerprint 3F2A 9C41 …
```

ลายนิ้วมือระบุเซิร์ฟเวอร์ส่งต่อ *ของคุณ*: มอบให้ผู้ใช้ของคุณ
นอกช่องทาง (ด้วยตนเอง ผ่านช่องทางอื่น) เพื่อให้พวกเขาจดจำได้ว่า
เซิร์ฟเวอร์ส่งต่อที่ได้รับมาคือตัวที่คุณรัน ลายนิ้วมือเดียวกัน
จะพิมพ์ในทุกการบูต หากมันเปลี่ยนแปลงไป แสดงว่าโวลุ่มข้อมูลถูก
แทนที่ — ตรวจสอบก่อนบอกให้ผู้ใช้เชื่อถืออันใหม่

ไคลเอนต์ตรวจสอบและตรึงกุญแจนี้โดยอัตโนมัติ (ระยะที่ 2 ขั้นตอนที่ 4): ใน
การติดต่อครั้งแรก ไคลเอนต์จะท้าทายเซิร์ฟเวอร์ส่งต่อให้ลงนามด้วยกุญแจ
(`/api/relay/attest`) จัดเก็บกุญแจที่ตรวจสอบแล้วไว้กับบัญชี และ
ตรวจสอบซ้ำในทุกเซสชันหลังจากนั้น ลายนิ้วมือที่ไคลเอนต์แสดง
(ภายใต้ `/security` และในข้อความแจ้งเตือนตอนตรึงครั้งแรก) อนุมานมาจาก
กุญแจเดียวกัน — เปรียบเทียบกับบรรทัดบันทึกการบูตข้างต้น หากกุญแจ
เปลี่ยนแปลงไป ไคลเอนต์ **จะหยุดคุยกับเซิร์ฟเวอร์ส่งต่อ** และเตือน
ผู้ใช้ พวกมันจะไม่ตรึงใหม่เงียบ ๆ จงถือว่าการเปลี่ยนแปลงลายนิ้วมือเป็น
เหตุการณ์ที่ทำให้เกิดการหยุดชะงัก: ไม่มีปุ่ม "เชื่อถือกุญแจใหม่" ในแอปใน
ขั้นตอนที่ 4 ดังนั้นหลังจากการสูญเสียโวลุ่มอย่างแท้จริง ผู้ใช้ของคุณต้องล้าง
ข้อมูลที่จัดเก็บของแอปสำหรับบัญชีของตน และตรึงใหม่ในการติดต่อครั้งแรก —
ประกาศลายนิ้วมือใหม่นอกช่องทางก่อน มิฉะนั้นพวกเขาจะแยกไม่ออก
ระหว่างกุญแจใหม่ของคุณกับกุญแจของผู้โจมตี

### การสำรองข้อมูลและการกู้คืน

**โวลุ่มข้อมูลคือสถานะทั้งหมดของเซิร์ฟเวอร์ส่งต่อ**: ไฟล์ SQLite หนึ่งไฟล์
ที่เก็บไดเรกทอรี กล่องจดหมาย และกุญแจตัวตนของเซิร์ฟเวอร์ส่งต่อ
ไม่มีสิ่งอื่นใดที่ต้องสำรอง

```bash
# Back up: copy the database out of the (stopped) container
docker compose stop
docker cp "$(docker compose ps -aq breeze)":/data/breeze-relay.db ./breeze-relay-backup.db
docker compose start

# Restore: copy the backup back in as /data/breeze-relay.db before
# starting, and the relay serves identically — same fingerprint.
docker compose stop
docker cp ./breeze-relay-backup.db "$(docker compose ps -aq breeze)":/data/breeze-relay.db
docker compose start
```

### การอัปเดต

```bash
git pull origin main
docker compose up -d --build
```

สถานะอยู่ในโวลุ่ม ไม่ใช่ในอิมเมจ ดังนั้นการอัปเดตจึงไม่เคยแตะต้อง
ข้อมูลของผู้ใช้ของคุณ

## โฮสต์ด้วยตัวเองด้วย Node เปล่า (ไม่มี Docker)

```bash
node server/index.js   # Node ≥ 24, no npm dependencies to install
```

การกำหนดค่าใช้ตัวแปรสภาพแวดล้อมเท่านั้น — `server/README.md`
แสดงรายการทั้งหมด สองความแตกต่างจากเส้นทาง Docker:

- **ไฟล์ข้อมูล** ค่าเริ่มต้นคือ `./breeze-relay.db` (แทนที่ด้วย
  `BREEZE_DB_PATH`) เป็นสถานะไฟล์เดียวเดียวกัน ตัวตนของเซิร์ฟเวอร์ส่งต่อ
  รวมอยู่ด้วย สำรองด้วยวิธีเดียวกัน: หยุด คัดลอก เริ่มใหม่
- **การลงทะเบียนเปิดอยู่เว้นแต่คุณจะปิดมัน**: ค่าเริ่มต้นแบบปิด
  เป็นคุณสมบัติของแพ็กเกจ Docker หากต้องการปิดทางเข้าแบบเปล่า ให้ตั้งค่า
  `REGISTRATION_ALLOWLIST=id1,id2` (หรือค่าว่างสำหรับ
  ปิดสำหรับทุกคน) `REGISTRATION_OPEN=1` เปิดอีกครั้งอย่างชัดเจน

## การติดตั้งบน Cloudflare

### การติดตั้งขั้นต่ำ ($0/เดือน 5 นาที)

```bash
# 1. Install Wrangler CLI
npm install -g wrangler

# 2. Login to Cloudflare
wrangler login

# 3. Deploy
wrangler pages deploy . --project-name=breeze

# 4. Create a KV namespace and declare it in wrangler.toml
wrangler kv:namespace create KV
# Copy the new namespace's ID and put it in wrangler.toml, replacing the
# id in the [[kv_namespaces]] section (binding = "KV"). Pages takes its
```

#### เซิร์ฟเวอร์ TURN (สำหรับเครือข่ายที่เข้มงวด)

TURN คือวิธีที่การโทรและการเชื่อมต่อแบบผ่านเซิร์ฟเวอร์ส่งต่อเท่านั้น (ซ่อน IP) ข้ามผ่าน
NAT ที่เข้มงวดได้ TURN ใดที่เซิร์ฟเวอร์ส่งต่อของคุณแจกจ่ายเป็นทางเลือกของ **คุณ**
ในฐานะผู้ให้บริการ — Worker จะลองตามลำดับ:

```bash
# Option A: Cloudflare Calls ($0.05/GB, global anycast)
wrangler pages secret put TURN_KEY_ID
wrangler pages secret put TURN_KEY_API_TOKEN

# Option B: your own coturn (HMAC time-limited credentials — the Worker
# mints a 24h username/credential per registered user from the secret)
#   coturn: use-auth-secret, static-auth-secret=<same secret>
wrangler pages secret put TURN_URL      # turn:your-server:3478
wrangler pages secret put TURN_SECRET

# Option C: static credentials (metered.ca, Twilio, …)
wrangler pages secret put TURN_URL
wrangler pages secret put TURN_USERNAME
wrangler pages secret put TURN_CREDENTIAL

# Option D: No config → free Open Relay (20GB/month). This is a third
# party's PUBLIC quota, shared with every unconfigured relay — fine for
# a first run, not a foundation. Opt out explicitly and callers get
# STUN only (some restrictive-NAT calls will then fail, visibly):
wrangler pages secret put TURN_OPENRELAY_FALLBACK   # set to: false
```

**ตรวจสอบสิ่งที่คุณกำหนดค่าจริง:** `GET /api/health` รายงาน
โหมดที่มีผลเป็น `turnProvider` (`cloudflare` | `custom` | `static` |
`openrelay` | `none`) บูลีน `turn` แบบเก่าสะท้อนเฉพาะ
`TURN_URL` เท่านั้น ดังนั้นจึงอ่านได้เป็น `false` สำหรับตัวเลือก A ที่แนะนำ — ใช้
`turnProvider` ไคลเอนต์แสดงผู้ให้บริการเดียวกันใน `/security` ดังนั้น
ผู้ใช้ที่ใช้ Open Relay สำรองสามารถเห็นได้ว่ามีบุคคลที่สามส่งต่อ
สื่อการโทรของตน (เฉพาะข้อมูลเมตา — ตัวสื่อเองถูกเข้ารหัส DTLS-SRTP)

#### การเสริมความแข็งแกร่งของการยืนยันตัวตน และเส้นทางเซิร์ฟเวอร์ส่งต่อธรรมดาแบบเดิม

การอัปโหลดกุญแจล่วงหน้าขณะนี้เก็บรักษาความเป็นเจ้าของการลงนามแยกไว้ที่
`prekey-owner:<userId>` **โดยไม่มี TTL** ความเป็นเจ้าของชุดกุญแจที่มีอยู่จะย้ายแบบขี้เกียจ
ในการอัปโหลดครั้งถัดไป ก่อนที่ตัวแทนที่จะได้รับการยอมรับ ชุดกุญแจ Ed25519 ใหม่ก็
สร้างบันทึกนั้นเช่นกัน เก็บบันทึกเหล่านี้ไว้เมื่อตัดแต่งชุดกุญแจล่วงหน้าที่หมดอายุ:
การรอให้ชุดกุญแจหมดอายุต้องไม่อนุญาตให้มีเจ้าของใหม่ การหมุนเวียนต้องการ
การอัปโหลดที่ลงนามโดยเจ้าของก่อนหน้า ผูกกุญแจใหม่เข้าไปในไดเจสต์การอัปโหลด
ที่มีอยู่ `/account/delete` ที่ยืนยันตัวตนแล้วจะลบทั้งสองบันทึกและสามารถยืนยันตัวตน
กับเจ้าของได้แม้หลังจากชุดกุญแจหมดอายุ ไม่มีการรีเซ็ตกุญแจเจ้าของที่สูญหาย

สำหรับบัญชีที่มีบันทึกนี้ การอัปโหลดและการสำรวจข้อความ/sealed, ACK แบบ sealed และ
หลักฐาน WebSocket ของกล่องจดหมายต้องใช้เจ้าของที่คงทน **คำขอที่ไม่มีลายเซ็น
จะถูกปฏิเสธแม้จะมี `PREKEY_REQUIRE_AUTH=false` หรือ `QUEUE_REQUIRE_AUTH=false`**
แฟล็กเหล่านั้นคงค่าเริ่มต้นที่มีอยู่และซีแมนติกส์แบบเดิมไว้สำหรับบัญชี
ที่ไม่มีเจ้าของ การยอมรับ `false` อย่างชัดเจนสำหรับคำขออัปโหลด/เข้าคิวที่ไม่มีลายเซ็น
จะบันทึกคำเตือนเรื่องการเลิกใช้ที่ไม่มีเนื้อหา แฟล็กการยืนยันตัวตนอื่น ๆ ไม่เปลี่ยนแปลง
WebSocket ของกล่องจดหมายยังคงต้องใช้ลายเซ็นสำหรับทุกคน

ไคลเอนต์รอการเริ่มต้นการลงนามก่อนกิจกรรมเข้าคิว รวมถึง
การบูตบัญชีที่กลับมา การเลื่อนเป็นผู้นำ และการเชื่อมต่อใหม่ การรอที่ใช้ร่วมกัน
ถูกจำกัดไว้ที่ห้าวินาที รันไทม์ที่ไม่รองรับจะดำเนินการต่อโดยไม่มีลายเซ็นทันที
IDB/การแกะกุญแจที่ค้างอยู่จะดำเนินการต่อโดยไม่มีลายเซ็นหลังครบกำหนด จากนั้นลงนามเมื่อพร้อม
สิ่งนี้ทำให้วงจรการสำรวจยังคงอยู่ **ไม่ใช่** ช่องทางเลี่ยง: บัญชีที่มีเจ้าของหนุนหลังไม่สามารถ
รับจากเซิร์ฟเวอร์ส่งต่อได้จนกว่ากุญแจลงนามของตนจะใช้งานได้ ติดตั้งสินทรัพย์ไคลเอนต์ที่อัปเดต
พร้อมกับ Worker เพื่อหลีกเลี่ยงการแข่งขันตอนเริ่มต้นแบบเก่า

การย้ายไม่สามารถกู้คืนความเป็นเจ้าของจากชุดกุญแจที่หมดอายุ **ก่อนที่**
เจ้าของของมันจะถูกเก็บรักษาไว้ การลงทะเบียนครั้งแรกยังคงเป็น TOFU บันทึกความเป็นเจ้าของใช้
แบ็กเอนด์ KV ที่มีอยู่: ความสอดคล้องในที่สุดและการเขียนพร้อมกันไม่ได้ถูกทำให้
เป็นเชิงเส้นได้โดยการเปลี่ยนแปลงนี้ หลักฐานคงช่วงความสดใหม่ห้านาที
ที่มีอยู่และการผูกการดำเนินการ/เพย์โหลดไว้ การลองใหม่ที่เหมือนกันภายในหน้าต่างไม่ใช่
โปรโตคอล nonce แบบใช้ครั้งเดียว

การเขียนสถานะการปรากฏตัวและการออกข้อมูลประจำตัว TURN ต้องการบัญชีที่ *ลงทะเบียนแล้ว*
(มีชุดกุญแจล่วงหน้าอยู่) ตามค่าเริ่มต้นอยู่แล้ว และไคลเอนต์ทุกตัวลงทะเบียน
โดยอัตโนมัติ การเต้นของหัวใจสถานะการปรากฏตัวยังพกหลักฐานความเป็นเจ้าของ Ed25519
(การเต้นลงนามในฟิลด์ที่มันจัดเก็บ) ซึ่ง Worker ตรวจสอบ
เมื่อใดก็ตามที่มีการนำเสนอ — `PRESENCE_SIGN_REQUIRE_AUTH=true` ทำให้
หลักฐานนั้นเป็นข้อบังคับ แฟล็กลายเซ็น Ed25519 ที่เหลือยังคงเป็นแบบเลือกเข้าร่วม
`wrangler.toml` บันทึกแต่ละแฟล็กและเหตุผล (ไคลเอนต์บนรันไทม์ที่ไม่มี
WebCrypto Ed25519 ไม่สามารถลงนามได้เลย)

เซิร์ฟเวอร์ส่งต่อธรรมดาแบบเดิม (`/api/msg/send`, `/api/msg/poll`) ถูกเลิกใช้แล้ว: การตอบกลับของมัน
มีส่วนหัว `Deprecation: true` และเส้นทางแบบ sealed เป็น
เส้นทางเริ่มต้นสำหรับไคลเอนต์ปัจจุบันทุกตัว เมื่อคุณยืนยันแล้วว่าไม่มีไคลเอนต์ที่ยังมีชีวิต
ต้องการทางสำรองอีก ให้ปิดการใช้งานมันโดยสิ้นเชิง:

```bash
wrangler pages secret put PLAIN_PATH_DISABLED   # set to: true
```
