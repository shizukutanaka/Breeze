# Breeze シェア獲得計画（SHARE_PLAN）

目的: LINE と Signal のシェアを根こそぎ取りに行く前提で、Breeze の現在地・勝ち筋・不足・段階計画を定める（2026-11-14、mi の指示）。本書の機能の有無は全て現行 main（`3572d0a8`、v3.6.1）の実コードで裏を取ったものだけを書く。競合の事実は出典つきのものだけを使い、古い情報には時点を明記する。

前提の資産: 段階1（メールボックス）・段階2（置き場所を選べるリレー、自前運用、複数リレーの冗長預け）は完了。段階3（量子耐性 PQXDH、`docs/PQ_STAGE3_PLAN.md`）は計画済みで実装中。本書の段階計画は段階3の完了を前提に、その先（段階4以降）を組む。

## 0. 前提条件（これが無いと計画全体が空転する）

1. **既定インスタンスの復旧**: README が案内する https://breeze.pages.dev は 2026-11-14 実測で **404**。Cloudflare 側に Pages プロジェクト／デプロイが存在しないことが原因で、復旧は所有者の操作（手順は `~/workspace/goals/74/files/所有者アクション-3バッチ手順.md` の 2-5 に登録済み）。この URL は配布済みアプリの既定の接続先でもあるため、デモの死はそのまま製品の死を意味する。
2. **配布物の鮮度**: Release の実ファイルは v3.6.0（2026-03-16）で約8ヶ月古く、段階1・2の成果が配布物に届いていない（普及監査 2026-11-14）。repo 内の版数は全パッケージ 3.6.1 で揃っているので、残るのはリリース実行の仕組み化（段階6 Step 4）。
3. **既定インスタンスの本番構成**: 段階1のフラグ（`MAILBOX_BACKEND=do`、`PRESENCE_BACKEND=do`、`MAILBOX_WS_ENABLED=true`）が既定インスタンスで有効かどうかは repo からは確認できない（Pages の secret は所有者だけが見える）。第6節の通り、このフラグの有無が無料枠の耐量を桁で変えるため、復旧時にあわせて確認・固定すること。

## 2. 競合との差分表（出典のある事実のみ）

| 項目 | Breeze | Signal | LINE |
|---|---|---|---|
| 登録 | 鍵ペアのみ。電話番号・メール不要 | **電話番号が必須**（ユーザー名は番号を隠すためのもので、登録自体は番号が必要）[S1] | 電話番号（または連携アカウント） |
| 利用規模 | — | 月間 約7,000万人（2025年4月時点、Whittaker 発言としての引用）[P1] | 日本の月間利用者 **1億アカウント**（2025年12月末、LINEヤフー発表）。台湾2,200万・タイ5,400万・インドネシア500万 MAU（2026年度Q1資料）[L1] |
| 中央サーバー依存 | **なし**。リレーは置き場所を選べて自前運用でき、連絡先ごとにホームリレーが違ってよい。複数リレーへ冗長預け | あり。公式サーバーが唯一の基盤（自前運用しても相互接続しない） | あり。公式基盤のみ |
| E2EE の範囲 | 1:1・グループ（100人まで）の全メッセージ。通話シグナリングは既定 OFF（第1節） | 1:1・グループ（**1,000人まで**）の全て＋通話。グループの所属情報すらサーバーに残さない [S2] | Letter Sealing が対象は **1:1 と50人までのグループ**のテキスト・位置・メディアと 1:1 通話のみ。グループ通話・ミーティング・アルバム・ノートは転送暗号のみ。ボットが入室するとその時点から保護対象外 [L2] |
| 量子耐性 | 段階3で実装中（PQXDH、ML-KEM-768 を X3DH に混合） | **配備済み**。PQXDH（2023年9月、X25519＋Kyber のハイブリッド）＋ SPQR（2025年10月発表、継続ラチェットへの ML-KEM-768 追加＝Triple Ratchet）[S3] | 公表資料の範囲では量子耐性の計画なし（Encryption Report 2025 に記載なし）[L2] |
| 広告・追跡 | なし（構造上、運営が読めない） | なし（非営利＋寄付）[P1] | あり（広告が事業の柱。有償公式アカウント 50.0万件 [L1]）。URL プレビューはサーバー側で生成 [L2] |
| グループ規模 | 100人 | 1,000人 [S2] | グループ自体は大規模可。ただし E2EE は50人まで [L2] |
| 通話 | 1:1 音声・ビデオのみ | 1:1＋グループ通話 | 1:1＋グループ通話（E2EE は 1:1 のみ [L2]） |
| 自己ホスティング | できる（Cloudflare でも Docker／Node でも。登録を閉じる allowlist つき） | 実質できない | できない |
| 移行のしやすさ | 招待リンク＋履歴取り込み（LINE／WhatsApp／Telegram の書き出し形式）を実装済み。ただし導線はコマンド裏側 | ユーザー名・QR・グループリンク。電話番号の壁は残る [S1] | プラットフォーム内完結（外への移行導線は当然ない） |
| 運営の持続形 | 本体無料＋寄付のみ（mi の方針）。既定リレーの費用構造は第6節 | 非営利団体＋寄付 | 広告・決済・公式アカウント課金 |

差分表から見える非対称性: Signal には「暗号の完成度と実績」でまだ負けている（量子耐性は配備済み対実装中、グループは1,000人対100人）。LINE には「暗号の範囲」では勝っている（E2EE は全グループ対50人まで）が、「日常の道具としての厚み」では大きく負けている。勝ち筋はこの非対称の上に組む。

## 3. 勝ち筋の設計

正面から全機能で勝つ計画は立てない。シェアは「集団が、理由を持って、まとめて移る」ときにだけ動く。集団ごとに、移る理由と「乗り換えの最後の障害」を特定する。

### 集団A: プライバシー事件の受け皿待ち（型3）
- 誰か: LINE や WhatsApp のポリシー変更・情報漏洩・検閲がニュースになるたびに「逃げ先」を探す層。2021年1月に Signal が5日で約750万ダウンロード・Telegram が72時間で2,500万人増を得た実証がある [P1]。
- 移る理由: 「運営が読めない」「番号を出さない」「サーバーを信用しなくてよい」。Breeze の構造そのものが理由になる唯一の集団。
- 最後の障害: **波の日に完成品として居ること** — 既定インスタンスが生きている、配布物が新しい、招待が摩擦なく通る。この3点が第0節と段階4・6の主題。暗号の不足（量子耐性・通話シグナリング）は「逃げ先としての格」を疑わせるので、段階3と段階5 Step 1 がこの集団の障害でもある。

### 集団B: 電話番号を出したくない層
- 誰か: 副業・創作活動・コミュニティ運営などで、本名義の番号と切り離した連絡手段が要る層。Signal に来ても番号登録の壁で止まる層がここに残る。
- 移る理由: Breeze は登録自体に番号が要らない。@alias と招待リンクで到達できる。
- 最後の障害: **発見の導線がコマンドと完全一致の alias しかない**こと。「相手の @ を正確に聞き取る」摩擦が日常の利用を止める。段階4 Step 1・3 が対象。

### 集団C: サーバーを自分で持ちたいコミュニティ
- 誰か: 学校・サークル・小規模組織・家族など、「自分たち専用の置き場所」で話したい集団。Signal はこの需要に応えない（自前運用しても閉じた輪にしかならないし、公式はそれを製品にしていない）。
- 移る理由: 段階2で実装済みの「リレーを選べる・自前で閉じられる（allowlist）」がそのまま答えになる。Docker／Node の自前ホストも実在する。
- 最後の障害: **自前リレーを立てた後の到達性** — 自分のリレーの利用者を、既定リレーの利用者がどう見つけて話しかけるか（ホームリレーの発見の一般化）。段階6 Step 2 が対象。あわせて運営手順の平易さ（SELF_HOSTING.md はあるが、非技術者の集団にはまだ硬い）。

### 集団D: 遮断・検閲への耐性が要る層
- 誰か: 特定ドメインや公式ストアが塞がれる環境の利用者。
- 移る理由: 単一ファイルの Web アプリ＋置き場所を各自が選べるリレー＋P2P 直送、という形は「塞ぐ点が1か所に無い」構造に近い。
- 最後の障害: 既定ドメイン自体が塞がれた場合の代替の入口（ミラー、配布物の直接入手、別リレーからのクライアント配信）の整備がまだ無い。段階6の範囲で扱うが、優先度は A〜C の後。

### 集団E: LINE の「重さ・広告・E2EE 範囲」に不満な日本の小グループ
- 誰か: 家族・友人・趣味の数人〜数十人のグループ。LINE の E2EE が50人までしか効かないこと自体を知らない層が大半だが、「広告と公式アカウントの通知に疲れた」「アカウントを消すと全部消える」不満は言語化されている。
- 移る理由: 軽さ、広告なし、全グループ E2EE、ブラウザだけで入れる（アプリのインストール不要）。
- 最後の障害: **グループ全員が一緒に移る摩擦そのもの** — 招待リンクを LINE グループに貼る動線は実装済みだが /newgroup というコマンドの裏側にある。全員が「開いて、相手がいて、1通目が送れる」ところまで、コマンド知識なしで辿り着けることが条件。段階4 Step 1 がこの計画の最重要ステップである理由。

## 4. 不足の棚卸し（物差し: 友人グループ全員が一緒に移れるか）

### (a) 移行を止める致命的な不足
1. **既定インスタンスの死（404）と配布物の陳腐化** — 第0節。移ろうとした最初の1人がここで落ちると集団ごと止まる。
2. **招待・移行の導線がスラッシュコマンドの裏側** — /invite・/qr・/newgroup・移行ガイド・/import は全て実装済みだが、通常のボタンと初回導線から到達できない。「実装はあるが存在しないのと同じ」状態。
3. **端末リンクが公開鍵コピペで、履歴が移らない** — 「スマホで始めて PC でも続き」は現代の物差しでは前提。新規端末が空の履歴から始まることは、移行した本人が「前の会話が消えた」と受け取る。
4. **グループ通話がない** — 日本の家族・友人グループではグループ通話は日常の機能で、これが無いグループは「通話のときだけ LINE に戻る」になり、戻る先が残ると移行は完了しない。
5. **通話シグナリング E2EE が既定 OFF** — 集団A（受け皿）の格に関わる。Signal は通話も含め全体が既定で E2EE であり、「逃げ先」として比較された瞬間にここが見える。配線と交渉の設計は済んでいて、残るのはロールアウト（第1節の CONFIG コメントが示す通り）。

### (b) 日常の不便
1. **グループ上限100人** — Signal は1,000人。学校・大きなサークル・イベント運営では100では足りない場面が出る。
2. **ステッカーがない** — 日本の LINE 文化では表現の中心。E2EE で配るパック形式の設計から要る。
3. **写真アバターがない**（絵文字のみ）— 誰の発言かの一目瞭然さが落ちる。プロフィールの E2EE 配布の設計が要る。
4. **位置情報共有がない** — 待ち合わせの日常利用。1回送信とライブ共有の両方が無い。
5. **画面共有がない** — 仕事・支援の文脈で効く。
6. **連絡先の発見が完全一致のみ** — alias の前方一致検索は列挙攻撃と衝突するため安易に足せないが、QR と招待リンクを表側に出すことで大半は代替できる（段階4 Step 3）。
7. 実装済みで不足でないもの（誤解防止）: 既読、入力中、検索（会話内・全体）、投票、編集、消えるメッセージ、ファイル50MB、ボイスメモ、複数アカウント、プッシュ通知は既にある。

### (c) あとで良いもの
1. チャンネル／公開コミュニティ（LINE OpenChat・Telegram チャンネル相当）— 発信の面。受け皿が完成してから。
2. 公式アカウント／ボット基盤 — 事業者側の面。同じく後。
3. 決済 — mi の方針（本体無料・寄付のみ）の外。やらない。
4. Safety Number の強化版（fingerprint.js）の配備 — reference 実装はあるが、表示の移行は能力交渉とセットでないと誤警報を生む（CLAUDE.md の注記）。
5. SPQR 級の「継続ラチェットへの量子耐性」— 段階3（PQXDH＝開始時のみ）の先。Signal は2025年にここへ進んだ [S3]。段階3の完了後に計画を切る。

## 5. 規模の設計（数字）

### 既定リレーの消費構造（コードから）
- 前面ポーリングは3秒間隔（`POLL_FAST_MS`）。ただし段階1 Step 5 の WS 起床を有効にすると「push＋低速の安全ポーリング」に置き換わる（wrangler.toml の MAILBOX_WS_ENABLED の説明）。
- presence のハートビートは前面30秒／背面2分（`PRESENCE_INTERVAL_MS`／`PRESENCE_BG_INTERVAL_MS`）。
- メールボックスの書き込みは受信者ごとの預け。送信は相手の全端末分＋連絡先のホームリレー分（既定 fanout 2）に増える。

### 無料枠の天井（出典つき）
- Workers 無料: **100,000 リクエスト/日**、CPU 10ms/回 [C1]。
- KV 無料: 読み 100,000/日、**書き 1,000/日**、容量1GB（repo の README「Running Costs」表と Cloudflare 公式価格の集計による）[C1][C2]。
- presence を KV に置いた場合、ハートビートだけで1人あたり前面1時間で120書き込み。**無料枠の KV 書き込み（1,000/日）は、常時接続なら数人〜十数人で尽きる**。wrangler.toml 自身が「presence は無料枠の1,000書き込み/日の最大の消費源だった」と記録しており、段階1で presence とメールボックスを Durable Objects へ移したのはこのため。結論: **既定インスタンスは DO バックエンド＋WS のフラグを有効にして初めて「無料で回る」と言える**。フラグ無しの KV 構成は、シェアを取りに行く前提では成立しない。

### 有料枠の単価（出典つき、2026年8〜10月に公式価格で再確認された集計）
- Workers Paid は **月 $5 がアカウント全体の最低額**で、Workers・Pages Functions・KV・Durable Objects をまとめて含む [C2]。
- Workers: 10M リクエスト/月 込み、超過 **$0.30/100万**。CPU 30M ms 込み、超過 $0.02/100万ms。帯域（egress）は無料 [C2]。
- KV: 読み 10M/月 込み（超過 $0.50/100万）、書き・削除・リスト 各1M/月 込み（超過 **$5.00/100万**）[C2]。KV の書きは高い — メールボックスを KV に置く構成は規模で破綻する。これも DO 化が正解である裏付け。
- Durable Objects: 1M リクエスト/月 込み（超過 **$0.15/100万**）、持続時間 400,000 GB-秒 込み（超過 $12.50/100万 GB-秒）[C2]。メールボックスの DO は「預け・取り出し・起床」の短い処理なので、リクエスト単価が支配的。

### 試算（前提を明記した概算）
前提: DO バックエンド＋WS 起床で運用。アクティブ1人あたり月 2,000 リクエスト（送信・起床・安全ポーリング・presence・prekey 取得の合計。前面3秒ポーリングが残る構成ではこの数倍になるため、WS 前提を崩さないこと）。
- 月間アクティブ 5,000人 → 10M リクエスト → **$5 の込み範囲内**（KV は alias・prekey 等の小さな読み書きのみで込み範囲を想定）。
- 月間アクティブ 100万人 → 20億リクエスト → Workers 超過 約 $597＋DO 超過 約 $300 で、**月 約 $900 台**。帯域無料が効いており、破綻する水準ではない。
- 本当の変動費は TURN（通話の中継）。既定は第三者の無料 Open Relay（20GB/月、README 記載）で、これは規模の土台にはできない。Cloudflare Calls の TURN は $0.05/GB（wrangler.toml 記載）。通話が増える段階では、P2P 直通率の実測と TURN 上限の管理が段階6 Step 3 の主題になる。

### 構造の効き方（段階2が規模の答えになっていること）
- 既定リレーは「最初の入口」であって、恒久の中心である必要がない。利用者は自分のリレーを選べ、コミュニティは自前リレーを立てられ、連絡先のホームリレーへ直接預けられる。つまり**利用者の増加を、既定リレーの増強ではなく、リレーの総数の増加で吸収できる**。Signal 型の「1つの運営が全員分を担う」構造より、運営コストの伸びが構造的に緩い。
- 逆に弱点は発見可能性（第4節 (b)-6 と段階6 Step 2）で、規模の設計と発見の設計は同じコインの裏表である。

## 6. 段階計画（段階4以降）

各ステップは単独でマージ可能に切り、完了条件はテストか実測で証明できる形にする。順序は段階3（量子耐性）の完了を前提とする。

### 段階4 — 移行の摩擦ゼロ化（集団A・B・E の障害を消す）
- **Step 1: 招待導線の表側化** — /invite・/qr・/newgroup・移行ガイドを、初回起動直後の案内と通常ボタンから到達できる形にする（実装は既にあるものの配線のみ）。完了条件: コマンドを知らない新規ユーザーを想定した導線テスト（招待リンク発行→着地→1通目送信まで）を通し、既存導線の退行ゼロ。
- **Step 2: 端末リンクの QR 化** — /link の公開鍵コピペを、既存の QR 表示・読み取りを使った相互確認フローに置き換える（信頼のアンカーは root の Ed25519 ピン留めを維持）。完了条件: 2端末相当のテストで、コピペなしにリンクが完了し、署名検証が従来と同等に効くこと。
- **Step 3: リンク済み端末への履歴の暗号化転送** — 既存端末から新規端末へ、会話履歴を端末間暗号化で渡す（リレーには平文もメタデータも増やさない）。完了条件: リンク直後の端末で、転送対象の会話がバイト単位で一致すること。転送しない選択も残す。
- **Step 4: 連絡先追加の統合画面** — 招待リンク・QR・@alias・公開鍵の4導線を1つの追加画面にまとめ、alias は完全一致のまま（列挙対策を維持）。完了条件: 4導線すべてが従来と同じ検証を通り、追加までの操作数が現行以下になること。

### 段階5 — 日常の物差し合わせ（集団E の日常と集団A の格）
- **Step 1: 通話シグナリング E2EE の既定 ON 化** — `CALL_E2E_SIGNAL` の段階的ロールアウト（交渉つきで旧クライアントと混在可能にする）。完了条件: 旧・新クライアント混在の通話テスト行列が全通過し、偽造シグナルの遮断が実測できること。
- **Step 2: グループ通話（小規模メッシュ）** — まず数人規模のメッシュ型で音声のみ先行、映像は次段。SFrame 等の本格化は既存 ROADMAP の C5 と接続する。完了条件: 3者以上の通話が実測で成立し、1:1 通話の退行ゼロ。
- **Step 3: グループ上限の引き上げ** — 100 → 300 → 1,000 の段階引き上げ。各段で roster 同期・sender key 配布・fan-out の実測（遅延と失敗率）を取る。完了条件: 上限人数での配布実測が基準内であること。
- **Step 4: プロフィールの E2EE 配布（写真アバター＋表示名）** — 連絡先ごとに開示するプロフィール形式を設計し、絵文字アバターと併存させる。完了条件: プロフィールがリレーに平文で残らず、旧クライアントでは従来表示に落ちること。
- **Step 5: ステッカーパック（E2EE 配布）** — パックの形式・配布・キャッシュを設計し、同梱の初期パックを用意する。完了条件: パックの送受信が E2EE の内側で完結し、大きなパックでも送信遅延が基準内であること。
- **Step 6: 位置情報共有** — 1回送信→ライブ共有の順で。完了条件: 位置が E2EE の内側でのみ流れ、ライブ共有の停止が確実に効くこと。

### 段階6 — 規模と運営
- **Step 1: 既定インスタンスの本番構成の固定と実測** — DO バックエンド＋WS の有効化を前提に、リクエスト内訳と費用の実測を取り、第5節の試算と突き合わせる。完了条件: 実測ベースの運営表（利用者数→費用）が文書化され、試算との乖離の説明がつくこと。
- **Step 2: ホームリレーの発見の一般化** — alias 解決に連絡先のホームリレー情報を安全に含め、別リレーの利用者同士が既定リレーを経由せずに会話を始められるようにする（段階2 Step 6 の一般化）。完了条件: 2つの独立した自前リレーの利用者同士で、招待なしに会話が成立すること。
- **Step 3: TURN の自前化と上限管理** — Cloudflare Calls の従量に上限と監視を付け、P2P 直通率を計測する。完了条件: 通話量に対する TURN 転送量の比率が継続計測でき、上限超過時に劣化ではなく通知になること。
- **Step 4: リリースの自動化** — repo の版数（3.6.1 系）から配布物（Web／Electron／Tauri／モバイル）を機械的に作る経路を整え、「配布物が古い」を二度と起こさない。完了条件: 版上げ1回で全配布物が同版で揃い、公開手順が所有者の1操作に減ること。

### 段階7 — 受け皿の完成度（型3 の仕上げ）
- **Step 1: 比較表の公開と検証可能性** — 第2節の差分表を、第三者が検証できる形（再現手順つき）で公開面に置く。完了条件: 主張の全行に検証手段が対応すること。
- **Step 2: 外部のセキュリティ監査の受け入れ準備** — CRYPTO-SPEC の整備、監査向けのテストベクトルの公開。完了条件: 監査者が repo だけで暗号の全体像を再構成できること。
- **Step 3: 透明性の定期化** — リレーの運営状態（障害・費用・リクエスト集計のみ、内容には触れない）の定期公開。完了条件: 初回の公開が済み、次の周期の手順が文書化されていること。

## 7. 測り方（分析を入れない製品で、進捗をどう知るか）

Breeze は追跡を入れない設計なので、利用者数の計測自体が製品の約束と衝突する。測れるのは運営側の集計だけに限る: 既定リレーのリクエスト数と登録 ID 数の推移（内容・連絡先には触れない集計）、配布物のダウンロード数、公開リレーの総数の推移。これらを「シェア獲得の代理指標」として段階6 Step 1 の運営表に含める。個人を追う計測は、集団A の移行理由そのものを壊すので入れない。
